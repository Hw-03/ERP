# 품목 공통 표시 순서

## 목표

대시보드와 관리자 > 품목 관리가 동일한 품목 순서를 표시한다. 기본 순서는 품목코드의 공정 코드와 일련번호에서 결정하며, 관리자는 드래그로 전체 순서를 재배열할 수 있다.

## 기본 정렬 규칙

초기 적용 시 활성 품목을 다음 순서로 정렬한다.

1. 공정: 튜브, 고압, 진공, 튜닝, 조립, 출하
2. 각 공정 안의 단계: 원자재, 중간공정, 공정완료
3. 같은 공정 코드 안: 품목코드의 일련번호 오름차순

공정 코드는 다음과 같이 해석한다.

| 공정 | 원자재 | 중간공정 | 공정완료 |
| --- | --- | --- | --- |
| 튜브 | TR | TA | TF |
| 고압 | HR | HA | HF |
| 진공 | VR | VA | VF |
| 튜닝 | NR | NA | NF |
| 조립 | AR | AA | AF |
| 출하 | PR | PA | PF |

현재 항목이 없는 `TA`, `NA`도 신규 품목이 추가되면 같은 공정의 원자재와 공정완료 사이에 배치한다.

## 저장 및 표시

- `Item.sort_order`를 공통 표시 순서의 단일 출처로 사용한다.
- 활성 품목 목록 API는 기존처럼 `sort_order`를 우선하여 반환한다. 따라서 대시보드와 관리자 품목 관리가 같은 API 결과 순서를 공유한다.
- 기존 `sort_order`를 변경하기 전에 현재 DB 전체를 SQLite 백업 API로 복제한다. 백업 파일은 `_attic/runtime/backups/mes-before-item-display-order-YYYYMMDD-HHMMSS.db` 형식으로 저장해, 품목 표시 순서 변경 전 상태임을 파일명만으로 알 수 있게 한다.
- 백업 파일을 열어 `items` 테이블과 기존 `sort_order` 값이 복제됐는지 확인한 뒤에만 기본 재정렬을 실행한다. 백업 생성 또는 검증에 실패하면 DB의 표시 순서를 변경하지 않는다.
- 최초 적용용 서버 동작은 위 기본 정렬 규칙으로 모든 활성 품목의 `sort_order`를 연속 재번호화한다.
- 삭제 품목은 활성 품목의 기본 재번호화 대상에서 제외한다. 기존 목록 API의 삭제 품목 처리 규칙은 유지한다.

## 신규 품목 추가

- 신규 품목은 일련번호를 비교하지 않는다.
- 해당 공정 코드 그룹의 마지막 품목 뒤에 삽입한다. 예를 들어 `HR` 신규 품목은 현재 표시 중인 `HR` 품목의 마지막 뒤에 놓인다.
- 해당 공정 코드 그룹이 비어 있으면, 위 공정·단계 순서에서 그 코드가 속한 위치에 삽입한다.
- 삽입 지점 뒤의 활성 품목 `sort_order`는 한 칸씩 밀어 연속된 전체 순서를 유지한다.

## 관리자 커스텀

- 관리자 품목 관리의 현행 드래그 재정렬과 PIN 검증을 유지한다.
- 드래그 저장 후의 `sort_order`가 기본 정렬보다 우선한다.
- 이후 신규 품목은 당시 목록에서 자기 공정 코드 그룹의 마지막에 들어가므로, 관리자가 만든 다른 그룹의 순서는 보존된다.

## 오류 처리

- 알려지지 않은 공정 코드가 생성되는 경우에는 기존의 목록 마지막 배치 규칙을 사용해 저장 실패를 피한다. 현재 등록 화면은 공정 코드 마스터에서만 선택하므로 정상 흐름에서는 발생하지 않는다.
- 재정렬 요청에 없는 품목을 건드리지 않는 기존 부분 재정렬 계약은 변경하지 않는다.

## 검증

- DB 변경 전 백업 파일의 이름, 생성 여부, `items.sort_order` 복제 여부를 확인한다.
- 서버: 기본 정렬 규칙, 같은 코드의 일련번호 정렬, 새 품목의 코드 그룹 마지막 삽입, 빈 코드 그룹 삽입을 테스트한다.
- 프런트엔드: 관리자 드래그 저장 요청과 정렬된 API 결과를 그대로 표시하는 동작을 관련 기존 테스트로 확인한다.
- 통합: 대시보드와 관리자 품목 관리가 동일한 API 순서를 사용하는지 확인한다.
