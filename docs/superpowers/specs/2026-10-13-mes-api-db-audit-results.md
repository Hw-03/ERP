## API 연결 단절

001의 보조 재고 GET과 002의 직원 fixture 정리 PUT은 Playwright→프론트 연결에서 `ECONNRESET`이었다. 정리 PUT의 백엔드 성공/실패 기록은 없었다. 로그 부재만으로 요청을 받지 않았거나 어느 쪽이 소켓을 종료했다고 확정하지 않는다.

설치된 Next·Playwright의 DB 없는 프록시 재현에서는 GET/PUT·동시 1/2/4·본문 복제 유무의 요청이 모두 200이었다. 프록시 정상 종료가 항상 재사용 연결을 끊는다는 가설은 반증됐다. 기본 keep-alive 만료보다 긴 동기 자식 작업 이후에는 이미 수신된 FIN을 처리하고 새 소켓을 사용했다. 이는 정확한 만료 경계의 경쟁까지 반증한 결과가 아니다.

실제 실패 흐름 두 건을 새 합성 QA 사본에서 최초 시도부터 계측했다. 두 흐름 모두 통과·재시도 0·실제 종료 코드 0이었다. 보조 Playwright API 45요청은 전부 200이고 재사용 연결 38건에서 연결 오류는 없었다. 같은 실행의 프록시 오류 5건은 모두 브라우저 응답이 미완료 상태로 닫힌 뒤 백엔드 연결 종료·오류가 이어진 순서였다. 따라서 이번 5건은 화면 요청 취소의 전파로 설명한다. 과거 보조 API 실패 두 건의 근본 원인은 여전히 미확정이다.

과거 첫 시도는 `on-first-retry`와 재시도 0의 조합 때문에 trace가 없었으며 화면·영상·서버 원문은 그대로 보존한다. 실행기와 Playwright 설정을 `retain-on-failure`로 보완하고, 기대값 실행의 출력 경로를 새 run·그룹별 ignored 폴더로 분리했다. 재시도·timeout·단언·프록시·업무 API·재고 계산식은 변경하지 않았다.

DB 없는 서버의 강제 소켓 단절로 관측 계약을 검증했다. 기존 설정은 최초 실패 1건·재시도 0·trace 0개, 새 옵션은 같은 실패 1건·재시도 0·정확한 run 경로의 trace 첨부/파일 각각 1개였다. 두 의도적 실패의 native exit 1을 확인한 검증 도구는 exit 0이었다. 기존 trace·보고서 SHA도 불변이었다. 이것은 실패 자료 보존의 검증이며 제품 결함이나 역사 실패 원인 재현이 아니다. 전용 서버 종료와 포트 해제를 확인했다.

원문 계측·실제 두 흐름·관측 계약 영수증은 로컬 `_attic/runtime/api-disconnect-audit-20261013/`에 보존한다. trace ZIP에는 QA 요청 원문이 있으므로 저장소에 넣지 않는다.

### 새 최초 실패와 만료 경계 조사

`api-db-final-20261013-001`의 주 브라우저 그룹에서 HISTORY03의 직원 fixture 정리 PUT이 다시 `ECONNRESET`으로 실패했고, 새 설정으로 최초 실패 trace를 확보했다. 화면의 최신 검색·선택 상세 단언 이후 실패한 정리 단계라는 점을 유지한다. 실제 실패를 반복 통과로 덮어쓰지 않는다.

DB 없는 실제 Playwright runner 진단에서는 동기·비동기 hook 모두 재시도 없이 종료 코드 0이었다. 동기 실행에서도 서버의 idle 종료 뒤 FIN을 먼저 처리하고 새 소켓으로 PUT했다. 이 결과는 동기 정리만으로 단절이 필연적으로 생긴다는 설명을 지지하지 않는다. 진단의 API 경로와 idle 간격이 원래 `route.fetch` 경로 및 정확한 만료 경계와 달라 그 경쟁까지 반증했다고도 기록하지 않는다. 원인 증거 없이 정리 방식을 교체하거나 재시도를 추가하지 않았다. 실제 실패 경로의 추가 조사는 좁은 계측으로 한정한다.

정제 시각·소스/trace SHA는 로컬 `failure-20261013-001-timeline.json`, 진단 원문과 native 결과·프로세스 종료는 `fixture-idle-probe/`에 보존한다. 해당 진단은 원인 해결 PASS가 아니다.

원래 HISTORY03 소스·설정·실행기를 포함한 사본의 입력 2,203파일 SHA를 시작/종료에 비교한 별도 계측에서는 세 번 모두 재시도 없이 native exit 0이었다. 진단의 런타임만 3057/8057 포트와 dependency junction을 허용하는 Turbopack root로 분리했고 실제 테스트·동기 정리·단언은 그대로였다. 같은 API 연결 풀과 소켓을 재사용한 직원 정리 PUT이 정상 200이었으며 마지막 `route.fetch` 응답 뒤 간격은 각각 5,137·5,305·4,793ms로, 실패 당시의 6,125.499ms보다 짧았다.

정확한 만료 간격의 단일 통제 진단도 수행했다. 이 진단은 원형 검사와 구분해, 실제 Python 정리 후 6,125ms까지 동기 차단하는 계측 어댑터만 적용했다. 당시 Python 정리 자체가 길어져 실제 간격은 6,538.838ms였고 추가 차단은 0이었다. 따라서 목표 간격을 충족한 검사로 기록하지 않는다. 이 조사는 API 연결 단절의 근본 원인 해결이 아니다. 최종 브라우저 재개가 통과하더라도 근본 원인 미확정은 별도로 유지하며 과거 실패와 이번 최초 실패를 삭제하지 않는다.
