# 출하 픽업 실제 처리자 귀속 설계

## 문제

직원 서버에서 2026-09-15 16:12 KST에 김건호가 두 출하 요청의 `pickup-complete`를 성공 처리했지만, 입출고 이력에는 준비 완료자 김현우가 담당자로 표시됐다. 활동 감사 로그에는 김건호가 남아 있으나, 픽업 업무 작업 원장과 거래 로그가 `ShippingRequest.prepared_by_*`를 재사용해 김현우로 저장된 것이 원인이다.

이 동작은 2026-09-14 롤백 커밋 `0aacf11a`에서 픽업 실제 작업자 전달이 제거되면서 재발했다.

## 선택지

1. **실제 픽업 작업자를 기존 원장에 기록한다 — 채택.** 라우터가 기존 `X-MES-Employee-Code` 헤더를 `_load_shipping_actor`로 검증하고, 서비스 경계에 필수 `Employee actor`를 전달한다. 스키마 변경 없이 `InventoryOperation.actor_*`와 픽업 `TransactionLog.produced_by`/`producer_employee_id`가 실제 처리자를 보존한다.
2. `ShippingRequest.picked_up_by_*` 컬럼을 추가한다. 조회는 편하지만 기존 원장과 중복되고 마이그레이션·DTO 범위가 커져 현재 결함 수정에는 과하다.
3. 화면에서 활동 감사 로그를 조회해 담당자를 덮어쓴다. 표시만 맞고 업무 원장은 계속 틀리므로 채택하지 않는다.

## 동작 계약

- 준비 완료자와 픽업 완료자는 서로 다른 업무 행위자로 취급한다.
- 픽업 완료 라우터는 로그인 작업자 헤더가 없거나 직원이 비활성 상태면 상태·재고·원장을 변경하지 않고 거부한다.
- 픽업 완료 서비스와 트랜잭션 래퍼는 `actor: Employee`를 필수 인자로 받고 서비스에서도 기존 `_require_actor` 검증을 적용한다. 준비자·요청자로 대체하는 fallback은 두지 않는다.
- 픽업 업무 작업 원장의 `actor_name`/`actor_employee_id`와 모든 PICKUP 거래 로그의 `produced_by`/`producer_employee_id`에는 같은 실제 작업자를 기록한다.
- `ShippingRequest.prepared_by_*`는 준비 완료자 증빙으로 유지하며 픽업 때 덮어쓰지 않는다.
- 입출고 화면은 이미 SHIP 행에서 `produced_by`를 우선하므로 프런트 렌더링 코드는 변경하지 않는다.
- 프런트 공통 쓰기 요청이 `X-MES-Employee-Code`를 보내는 계약을 테스트로 고정한다.

## 기존 오기록 복구

직원 DB의 재고 수량·출하 상태·시각은 변경하지 않는다. 성공한 `activity_audit_logs`의 픽업 완료 행과 `related_id`가 일치하고, 같은 요청에 감사 작업자가 정확히 한 명으로 확정되는 경우에만 다음 귀속 필드를 보정한다.

- `transaction_logs.produced_by`
- `transaction_logs.producer_employee_id`
- 연결된 `inventory_operations.actor_name`
- 연결된 `inventory_operations.actor_employee_id`

복구 도구는 기본 dry-run이며 KST 기간을 필수로 받는다. 모호한 요청, 존재하지 않는 직원, 감사 로그와 거래 시각이 허용 범위를 벗어난 요청이 하나라도 있으면 `--apply`를 거부한다. 적용 전 SQLite 온라인 백업을 만들고, 단일 `BEGIN IMMEDIATE` 트랜잭션으로 귀속 필드만 수정한다.

현재 확인된 보정 후보는 요청 `f1312280-ba9e-4ec1-8e05-317aac636f87`, `7e613cc3-89ab-46f1-ad9b-79b6143ac542` 두 건이며 실제 처리자는 김건호(E04)다. 실행 시점에 같은 기간의 추가 후보가 있으면 dry-run 결과를 별도로 검토한다.

## 검증과 배포

- 준비자 A와 픽업자 B가 다른 통합 테스트로 거래 로그·업무 작업 원장이 모두 B를 가리키고 준비자 필드는 A로 남는지 검증한다.
- 누락·비활성 작업자 요청이 어떤 상태 변화도 만들지 않는지 검증한다.
- 서비스·동시성·컷오버 테스트의 모든 직접 호출에 명시적 작업자를 전달해 필수 인자 계약을 컴파일·테스트 수준에서 고정한다.
- 복구 도구는 정상, 무변경, 모호, 미등록 직원, dry-run, 트랜잭션 롤백을 임시 SQLite DB로 검증한다.
- 직원 배포는 `deploy-to-employee` 절차를 따른다. `sync-to-employee.ps1`가 `C:\ERP` 전체를 미러링하므로 현재의 무관한 미커밋 변경이 정리되거나 배포 범위가 안전하게 격리되기 전에는 배포하지 않는다.

## 제외 범위

- 출하 상태 머신, 재고 계산, 화면 레이아웃, 주간보고 동결 파일은 변경하지 않는다.
- `picked_up_by_*` 신규 컬럼과 과거 감사 로그가 없는 행의 추정 보정은 하지 않는다.
- 커밋·푸시·직원 서버 반영은 사용자의 별도 실행 승인 없이 수행하지 않는다.
