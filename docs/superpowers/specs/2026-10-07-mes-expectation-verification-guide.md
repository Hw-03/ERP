# DEXCOWIN MES 기대값 검증 안내

기대값 원장은 원문·사용자 피드백, 최종 정책, 개별 조건, 실제 검사와 실행 근거를 연결한다. 기존 관찰이나 테스트 이름만으로 현재 통과를 표시하지 않는다. 항목 수와 상태는 원장의 `metrics`에서 계산한다.

## 상태 읽기

- `unreviewed`: 복합 문장을 개별 조건으로 검토하는 작업이 남았다. 정책 문구가 확정됐더라도 검증 조건 검토가 끝났다는 뜻은 아니다.
- `missing` / `browser-needed`: 현재 조건의 실제 검사 연결이 남았다.
- `linked`: 테스트 선언과 실제 assertion을 연결했다. 실행 통과와 다르다.
- `NOT_RUN` / `PARTIAL` / `FAIL` / `PASS`: 현재 근거로 확인한 조건과 항목의 실행 상태다. 일부 조건만 통과한 항목은 `PASS`가 아니다.
- `deferred`: 승인된 보류 범위다. 전체 실행의 분모에서 제외하며 원문·피드백은 보존한다.

`historicalBindings`와 `historicalExecutions`는 재검토에 사용할 과거 연결·실행 기록이다. 현재 실행으로 계산하지 않는다. 전환 전 정책과 연결 자료도 `2026-10-07-mes-expectations.sources/`에 해시와 함께 보존한다.

2026-10-10 사용자가 추가 최적화와 전체 검사 반복을 중단하도록 범위를 조정했다. C13의 전체 실행 성공은 이력으로 보존하고, 소스 snapshot이 달라진 현재 조건은 `NOT_RUN`으로 남긴다. 일반 품목·상세의 국소 성능 근거, 복구 검증, 해당 브랜치 HEAD의 CI 결과는 별도로 보고한다. 새 원장 CI의 `--check` 성공은 구조·선택자·증거 상태의 유효성을 뜻하며, `--require-complete` 전체 완료를 뜻하지 않는다. 최신 소스의 전체 실행·재승격과 무거운 조회의 모든 부하 절대 상한 달성은 후속 과제다.

## 실행

저장소 루트에서 저장소 전용 Node 20과 Python·pytest, 프론트 의존성을 준비한다. 실행 대상은 먼저 계획으로 확인한다.

```powershell
$node = (Get-Content _attic/runtime/frontend-node-path.txt -Raw).Trim()
& $node scripts/dev/run-mes-expectations.mjs --ids PC-DELTA-TEST-01 --plan
& $node scripts/dev/run-mes-expectations.mjs --ids PC-DELTA-TEST-01 --run-id review-tools-01
```

`--ids` 대신 `--tier smoke`, `--tier P0`, `--tier full`을 사용할 수 있다. `full`은 보류를 제외한 전체 원장이다. 미검토·미연결 조건을 포함한 실행 계획은 실패하며, 준비가 끝난 것처럼 자동으로 건너뛰지 않는다. 같은 run ID는 덮어쓰지 않는다.

선택한 테스트는 전체 파일 단위로 실행한다. 파라미터 일부만 실행해 같은 선언 전체를 통과로 기록하지 않도록 수집 목록과 결과를 대조한다. Playwright는 전체 수집 목록을 먼저 읽고, 재시도·반복·부분 shard·only 선택을 허용하지 않는다. 대상의 누락·중복·SKIP·실패 후 재시도 성공은 통과로 인정하지 않는다.

결과는 `_attic/runtime/mes-expectations/<run-id>/`에 남는다. 실행기는 실제 자식 검사가 모두 끝난 뒤 선택 조건·실행 그룹·보고서 해시를 담은 완료 영수증 `run.json`을 만든다. 영수증 없이 보고서나 화면만 모은 결과는 승격하지 않는다. 개별 실행이 성공하더라도 전체 원장의 완료를 뜻하지 않는다. 제품·테스트·설정 파일 목록과 내용이 실행 중 또는 실행 후 바뀌면 그 근거를 사용할 수 없다.

실행 manifest의 HEAD는 추적을 위한 정보다. 문서 커밋만으로 결과를 무효화하지 않으며, 재사용 가능 여부는 기록된 제품·테스트·설정 입력과 현재 조건의 일치로 판단한다.

## 브라우저와 근거 보존

브라우저 실행은 전용 백엔드 8021·프론트 3100·`backend/mes_e2e.db`를 사용한다. 점유된 포트는 사용하지 않는다. 준비 단계는 전용 합성 DB를 만들며 원본 `mes.db`는 바꾸지 않는다. 작업 종료 시 전용 환경 정리와 원본 DB 불변을 확인한다. 실제 개발·직원 서비스에 이 명령을 대신 연결하지 않는다.

마지막 AS·연구 승인자 회수는 다른 미결 요청도 재분류하므로 해당 두 시나리오 파일은 각각 새 DB에서 실행한다. 원장 실행기는 이를 별도 그룹으로 나누며 CI도 일반 전체·역할 회수·AS·연구 UI를 별도 실행 환경으로 분리한다. 일반 실행에서 제외한 두 파일은 각 전용 실행에서 모두 검사한다.

브라우저 근거에는 실제 DB revision·fixture 해시·논리 DB 해시·서버 boot ID·URL·런타임 버전과 성공 화면을 기록한다. 같은 직원/다른 직원 탭 격리는 같은 브라우저 컨텍스트에서 검증한다. 네트워크 응답 주입은 화면 오류 대응 검사로 명시하며 실제 서버 권한 검사를 대신하지 않는다.

사유·메모 분리 조건(`8.6-09`, `8.10-04`, `8.13-07`의 `reason-and-memo-independent-labels`)은 두 종류의 증거를 구분한다. `defect-reason-fields-expectations.spec.ts`의 `DEFECT-REASON-FIELDS`는 실제 API로 카테고리만 입력한 격리·복귀·폐기·반품을 생성하고 없는 메모를 만들어 표시하지 않는지 확인한다. `DEFECT-REASON-LEGACY`는 사유 카테고리가 없는 과거 자료의 표시만 확인하기 위해 해당 QA 품목의 GET 응답을 투영하며, 서버 원본이 변하지 않았는지도 대조한다. 이 두 번째 검사는 사유 없이 새 작업을 저장할 수 있다는 증거가 아니다. 현재 제출의 사유 필수 계약은 별도 서버·화면 검사로 유지한다.

`requiredEvidence: ["test", "browser"]`는 자동 assertion과 실제 브라우저 실행을 모두 요구한다. 실제 UI를 조작하고 결과를 검증한 Playwright 실행은 두 요건을 함께 충족할 수 있다. API만 호출한 Playwright 테스트나 DOM 모의 테스트를 화면 검증으로 연결하지 않는다.

```powershell
& $node scripts/dev/run-mes-expectations.mjs --promote _attic/runtime/mes-expectations/review-tools-01
& $node scripts/dev/normalize-mes-expectations.mjs
& $node scripts/dev/normalize-mes-expectations.mjs --check
```

승격 명령은 현재 입력과 조건을 다시 검증한 뒤 원본 보고서·수집 목록·실행 manifest·성공 화면을 원장 옆 `sources/verification/<run-id>/`에 복사한다. 일부 조건을 실행했다면 그 조건만 갱신한다. 진단 로그와 실패 화면은 실행 폴더에 남겨 조사에 사용한다.

## 확정된 직원·출하·주간 정책

새 직원은 관리자 메뉴가 기본으로 숨겨진다. 생성 요청에서 메뉴 표시 설정을 명시하면 그 설정을 적용하며, 기존 직원을 수정할 때 메뉴 설정을 생략하면 저장된 값을 유지한다. 필요한 직원의 관리자 메뉴는 직원 설정에서 켤 수 있다. 창고·부서 정/부와 AS·연구 승인 역할, 기존 PIN은 각각 기존 기준을 따른다.

출하 준비는 실제 출하할 최종 PF와 동반 출하품의 가용재고를 검사하고 예약한다. 이미 생산된 PF는 BOM 구성품의 현재 부족만으로 출하를 막지 않는다. 품목 삭제, BOM 변경 뒤 재확인, 예약 부족과 중복 제출 검사는 유지한다.

주간보고의 모델별 표는 생산량이 없어도 PF 픽업 완료가 있으면 표시한다. 생산과 PF 출하 수량은 별도로 읽는다. 조회 주차는 KST 월요일 00시부터 다음 월요일 00시 직전까지이며, 전체 정상재고 합계는 서버가 정한 보고 대상 품목의 합계다. **집계·검산 기준**을 펼쳐 대상과 과거 집계 기준을 확인한다. 재작업 불량·폐기 자식의 입고와 불량 두 열은 정상재고 순변화 0을 보존하기 위한 기록으로 유지한다.

## BOM 변경 확인

관리자 **BOM 관리**에서는 구성품을 추가하거나 수량·삭제를 바꾼 뒤 **구성 저장**을 누른다. 저장 전까지 서버 구성은 유지된다. 수량 오류는 행별 이름과 함께 표시되며, 저장 실패나 다른 탭의 수정 충돌이 발생하면 작성한 초안이 남는다. **변경 취소**는 서버의 최신 구성을 다시 읽는다.

검토 완료한 BOM은 수정할 수 없다. 완료 해제 뒤 저장·재완료할 수 있으며 각 변경 이력이 남는다. 다른 탭에서 완료한 경우 열려 있던 편집창도 닫고 서버의 완료 구성을 표시한다. 화면 오류 안내·실패 시 무변경·두 탭 경합은 `frontend/tests/e2e/bom-expectations.spec.ts`의 실제 흐름으로 검사한다.

## 완료 판정

```powershell
& $node scripts/dev/normalize-mes-expectations.mjs --check --require-complete
```

이 명령은 모든 대상의 원자 조건 검토·연결·현재 실행 통과를 요구한다. 작업 중에는 남은 조건 때문에 실패할 수 있다. 정책·코드·검사 변경 후 과거 해시를 일괄 갱신해 완료로 만드는 대신, 바뀐 검증 조건을 읽고 필요한 실행을 다시 수행한다. 최종 배포 준비 판정은 통합 검사와 별도 공동복구 리허설까지 확인한 뒤 기록한다.
