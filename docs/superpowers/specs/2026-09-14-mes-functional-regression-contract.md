# DEXCOWIN MES 전 기능 업무계약 조사 기록

> 상태: 사용자와 대화하며 계속 갱신하는 초안
> 최종 테스트 기준 아님: `기대 반응`을 사용자에게 확인받기 전에는 기존 코드나 기존 테스트를 정답으로 간주하지 않는다.

## 1. 이 문서의 목적

DEXCOWIN MES에서 사용자가 수행할 수 있는 입출고·출하·불량 처리의 모든 업무상 경우의 수를 먼저 식별한다. 각 경우마다 기대 반응과 실제 반응을 UI, API, DB 재고·예약·원장, 입출고 내역까지 연결해 기록한다. 사용자가 기대 반응을 확인한 행만 자동 테스트의 기준으로 확정한다.

진행 순서는 다음과 같다.

1. 화면, API, 서버 규칙, 기존 데이터와 레거시 내역을 조사해 업무상 서로 다른 경우를 빠짐없이 나열한다.
2. 현재 구현을 보지 않고도 설명할 수 있는 사용자 기대 반응을 먼저 작성한다.
3. 격리된 테스트 DB에서 실제 화면 흐름을 실행한다.
4. API 응답, 위치별 재고·예약, 요청 상태, 거래 원장, 입출고 내역 표시를 실제 반응으로 기록한다.
5. 기대와 실제의 차이를 표시하고 사용자가 각 기대값을 확인한다.
6. 확인된 행에 계약 ID를 부여하고 서비스·API/DB·Playwright 테스트로 자동화한다.

## 2. 기록 상태

| 상태 | 의미 |
|---|---|
| `합의` | 사용자가 기대 반응을 명시적으로 확인함 |
| `검토 필요` | 경우는 식별했지만 세부 기대 반응을 더 논의해야 함 |
| `미실행` | 실제 UI/API/DB 검증을 아직 하지 않음 |
| `일치` | 실제 반응이 합의된 기대 반응과 같음 |
| `불일치` | 실제 반응이 합의된 기대 반응과 다름 |
| `자동화 완료` | 합의된 계약을 자동 테스트가 검증함 |

기존 테스트 통과 여부는 위 상태를 대신하지 않는다. 기존 테스트가 잘못된 결과를 기대하도록 작성됐을 가능성도 별도로 검토한다.

## 3. 현재까지 합의한 원칙

### 3.1 부서 입출고의 부서 결정

- 사용자가 부서를 선택해서 진행하지 않는다.
- 품목의 공정 코드와 업무 규칙을 기준으로 서버가 대상 부서를 자동 결정해야 한다.
- 사용자가 URL이나 API payload로 다른 부서를 주입해도 다른 부서 재고가 변경되면 안 된다.
- 실제 검증에서는 대상 부서뿐 아니라 다른 모든 부서와 창고 재고가 그대로인지 함께 비교한다.

### 3.2 커스텀 BOM 입출고

- 커스텀 BOM으로 입출고할 때 **상위 자재 재고는 그대로 유지한다.**
- 상위 자재에는 재고 증감과 재고 원장 효과가 생기면 안 된다.
- 사용자가 커스텀 구성에 포함한 **하위 자재만** 해당 작업 방향에 맞게 입고 또는 출고된다.
- 제외한 하위 자재와 관련 없는 품목·부서·창고는 변하지 않아야 한다.
- 입출고 내역에서도 상위 자재가 실제 재고 이동 품목처럼 오인되게 표시되면 안 되며, 하위 자재별 실제 증감이 정확히 보여야 한다.

### 3.3 테스트 기준을 확정하는 순서

- 테스트부터 작성하지 않는다.
- 입출고의 모든 경우와 출하·불량 처리까지 목록화한다.
- 각 경우의 기대 반응과 실제 반응을 같은 표에 기록한다.
- 입출고 내역의 표시 결과까지 확인한다.
- 사용자가 기대값을 확인한 뒤 그 표를 테스트 오라클로 고정한다.

### 3.4 현재 작업 기준선

- 현재 별도 작업에서 수정 중인 입출고 안전성 변경이 검증되어 `main`에 병합된 뒤 실제 반응 조사를 시작한다.
- 운영 DB는 사용하지 않는다. 새 격리 DB와 전용 테스트 계정·재고를 사용한다.
- 조사 전후 실제 운영용 `backend/mes.db`가 변경되지 않았는지 확인한다.
- 이번 회귀 테스트 구축에는 요청 작성, 작성 중, 내 요청, 창고 승인함, 부서 승인함, 품목 전환을 포함한다.
- 숨겨진 모바일 스캐너와 인수인계는 이번 회귀 테스트 구축에서 제외한다.
- 인수인계 제거는 별도 후속 작업으로 관리하며, 이번 작업에서는 현행 인수인계 코드와 데이터에 손대지 않는다.

## 4. 경우의 수 기록 표준

각 업무 행은 최소한 다음 열을 가진다.

| 열 | 기록 내용 |
|---|---|
| 계약 후보 ID | 논의와 테스트를 연결할 고유 ID |
| 업무 영역·작업 유형 | 원자재 입고, 창고 반출, 사용출고, 출하, 불량 등 |
| 변형 | 낱개/기본 BOM/커스텀 BOM, 단건/복수, 정상/실패 등 |
| 요청자·권한 | 부서, 창고 정·부담당자, 부서 결재권자, 일반 직원 등 |
| 초기 상태 | 위치별 재고, 예약, 요청 상태, BOM과 기준정보 |
| 사용자 행동 | 실제 화면에서 수행하는 절차와 입력값 |
| 기대 결재 흐름 | 무결재/자가결재/대기, 필요한 단계와 순서 |
| 기대 재고·예약 | 창고와 모든 부서의 위치별 전후 수량 |
| 기대 요청·원장 | 요청/라인 상태, 거래·operation/effect, 감사 정보 |
| 기대 화면·내역 | 성공·오류 안내, 대기함, 입출고 내역의 표시 내용 |
| 실제 반응 | HTTP/UI 반응과 실제 상태 전이 |
| 실제 DB·내역 | 위치별 재고·예약·원장과 화면 표시 |
| 차이·판정 | 일치/불일치와 재현 증거 |
| 사용자 확인 | 기대값 승인 여부와 확인일 |
| 연결 테스트 | 서비스/API·DB/Playwright 테스트 ID와 결과 |

실패가 기대되는 행도 성공 행과 같은 수준으로 기록한다. 실패 응답뿐 아니라 재고, 예약, 요청, 원장, 내역이 모두 무변경인지 확인한다.

## 5. 입출고 경우의 수 1차 목록

이 목록은 현재 화면과 코드에서 확인한 1차 조사본이다. 사용자 업무 관점에서 빠진 경우를 계속 추가한다.

| 영역 | 현재 식별한 작업 | 반드시 교차할 변형 |
|---|---|---|
| 원자재 입고 | 공급처 원자재 입고 | 창고 정/부담당자/무권한자, 단건/복수, 신규/기존 품목, 정상/잘못된 수량/중복 제출 |
| 창고 입출고 | 창고→부서 반출, 부서→창고 반입 | 자동 부서 라우팅, 단건/복수, 충분/부족 재고, 결재권한 조합, 반려·취소·재시도 |
| 공정·부서 입출고 | 생산, 분해, 부서 낱개 입고, 부서 낱개 출고 | 기본 BOM/커스텀 BOM/낱개, 자동 부서 라우팅, 재고 미반영 품목, 혼합 묶음 |
| 사용출고 | AS·연구 사용, 창고 담당자 사용출고 | 출고 원천 창고/부서, 낱개/BOM, 상·하위 차감/하위만 차감, 권한과 결재 |
| 창고 수량보정 | 창고 보정 입고, 창고 보정 출고 | 정/부담당자/무권한자, 단건/복수, 부족 재고, 중복 실행 |
| 품목 전환 | SPEC 전환, BOM 전환 | 조립/출하/무권한자, 원본·대상 품목, 수량, 부분 실패, 전환 내역 표시 |
| 요청 수명주기 | 초안, 제출, 예약, 승인, 반려, 취소, 재시도 | 새로고침, URL 진입, PC↔모바일, 중복 클릭, 응답 유실, 동시 처리 |
| 과거 내역 | 레거시 입출고·취소·역전 데이터 | 현재 라벨·그룹화·필터·재고 전후 수량, 계산 불가능한 값의 표시 |

### 5.1 현재 화면에서 확인한 입출고 작업 유형

- 최상위 입출고 유형은 원자재 입고, 창고 입출고, 공정 입출고, 사용출고, 창고 수량보정이다.
- 세부 유형은 공급처 입고, 창고 반출·반입, 생산·분해·부서 낱개 입고·출고, 사용출고, 창고 보정 입고·출고다.
- 불량은 입출고 메뉴가 아니라 별도 최상위 불량 탭에서 다루지만 재고 원장과 입출고 내역 검증에는 포함한다.
- 품목 전환은 조립 또는 출하 직원에게 별도 카드로 노출된다.

근거: `frontend/app/mes/_components/_warehouse_v2/ioWorkType.ts:34`, `frontend/app/mes/_components/_warehouse_v2/ioWorkType.ts:72`, `frontend/app/mes/_components/_warehouse_v2/IoWorkTypeStep.tsx:22`.

### 5.2 자동 부서 라우팅

현재 코드상 창고 반출·반입, 생산, 분해, 부서 낱개 입고·출고는 자동 부서 라우팅 대상이다. 실제 계약 검증에서는 품목 공정 코드별 예상 부서를 먼저 표에 적고, 요청 결과가 그 부서에만 반영됐는지 확인한다.

근거: `frontend/app/mes/_components/_warehouse_v2/ioWorkType.ts:20`.

### 5.3 사용출고

사용출고는 다음 축을 각각 분리한다.

- 요청자: AS 직원, 연구 직원, 창고 정담당자, 창고 부담당자, 무권한 직원
- 출고 원천: 창고, 부서
- 구성: 낱개, BOM
- BOM 차감 방식: 상·하위 차감, 하위만 차감
- 결과: 즉시/결재 대기/거절, 원천 위치 차감, 요청·원장·내역 표시

현재 UI의 사용출고 노출 대상과 BOM 차감 방식 근거는 `frontend/app/mes/_components/_warehouse_v2/ioWorkType.ts:49`, `frontend/app/mes/_components/_warehouse_v2/internalUseBom.ts:8`이다.

### 5.4 품목 전환

- SPEC 전환과 BOM 전환을 별도 계약으로 기록한다.
- 원본 품목 감소와 대상 품목 증가, 총량/단위 규칙, 부분 실패 시 원자성, 권한, 재시도, 취소 가능 여부를 확인한다.
- 전환 결과가 일반 입출고 내역에서 어떤 라벨과 전후 수량으로 표시돼야 하는지 사용자 확인을 받는다.
- 현재 UI에서는 조립 또는 출하 직원에게만 품목 전환 카드를 노출한다. 서버 권한도 별도로 검증한다.

근거: `frontend/app/mes/_components/_warehouse_v2/IoWorkTypeStep.tsx:24`, `backend/app/routers/io.py:97`.

## 6. 결재는 모든 결재 필요 업무에 교차 적용한다

“결재권자가 요청하면 자동 결재”는 단순한 사용자 속성이 아니라 **그 요청에 필요한 각 결재 단계의 권한을 요청자가 충족하는지**로 판정한다.

| 필요한 결재 | 요청자 권한 | 기대 흐름 | 기대 재고·기록 | 확인 상태 |
|---|---|---|---|---|
| 없음 | 관계없음 | 즉시 실행 | 즉시 재고·원장 반영, 승인자 필드는 불필요 결재로 기록하지 않음 | 검토 필요 |
| 창고만 | 창고 정·부담당자 | 창고 자가결재 후 즉시 완료 | 실제 재고 반영, 창고 승인자에 요청자 기록 | 합의 |
| 창고만 | 창고 결재권 없음 | 창고 결재 대기 | 승인 전 실제 재고·원장 미반영, 필요한 원본 위치에만 예약 | 합의 |
| 부서만 | 해당 부서 결재권자 | 부서 자가결재 후 즉시 완료 | 실제 재고 반영, 부서 승인자에 요청자 기록 | 합의 |
| 부서만 | 무권한자 또는 타 부서 결재권자 | 해당 부서 결재 대기 | 승인 전 실제 재고·원장 미반영 | 합의 |
| 창고→부서 | 양쪽 권한 모두 보유 | 두 단계 자가결재 후 즉시 완료 | 두 승인자 필드와 실제 재고·원장 반영 | 검토 필요 |
| 창고→부서 | 창고 권한만 보유 | 창고 단계만 자가결재, 부서 결재 대기 | 창고 승인자만 기록, 최종 승인 전 예약 유지 | 검토 필요 |
| 창고→부서 | 부서 권한만 보유 | 창고 결재부터 대기하며 부서 단계 선처리 금지 | 부서 자가결재는 창고 승인 후에만 가능 | 검토 필요 |
| 창고→부서 | 두 권한 모두 없음 | 창고 결재 후 부서 결재 순서로 진행 | 각 단계·예약·대기열·원장을 순서대로 확인 | 합의 |

각 결재 행은 다음 요청자·승인자 조합을 최소한 포함한다.

- 창고 정담당자와 부담당자
- 정확한 대상 부서의 결재권자
- 창고·부서 권한을 동시에 가진 사람
- 일반 작업자
- 다른 부서의 결재권자
- 비활성 직원, 잘못된 PIN, 만료된 세션
- body/header/URL로 작업자나 부서를 위조한 요청

각 조합에서 요청 직후 상태, 결재 대기함과 카운트, 예약 위치·수량, 실제 재고 반영 시점, `approved_by`와 `department_approved_by`, 요청자·결재자 내역 표시, 반려·취소·중복/동시 승인을 확인한다.

## 12. 입출고 영역 종료 판정

### 2026-09-14 판정

입출고 화면과 코드에서 큰 기능 종류를 찾는 1차 조사는 완료했다. 그러나 업무상 모든 경우의 수와 테스트 기대값 확정은 아직 완료하지 않았다. 다음 영역으로 넘어가기 전에 아래 조건을 충족해야 한다.

1. 각 작업을 권한, 낱개/기본 BOM/커스텀 BOM, 단건/복수, 충분/부족 재고, 결재, 반려·취소·재시도 기준으로 행별 분리한다.
2. 각 행의 위치별 재고·예약·요청 상태·원장·입출고 내역 기대값을 사용자에게 확인받는다.
3. 숨겨진 모바일 스캐너와 인수인계가 제외됐는지 최종 목록에서 확인한다.

### 업무 질문 3 — 원자재 입고 결재: 결정됨

원자재 입고는 창고 정·부담당자 모두 별도 결재 없이 즉시 처리한다. 완료 시 창고 재고만 증가하고 부서 재고, 예약, 무관한 품목은 변하지 않아야 한다. 결재가 필요 없는 작업이므로 승인 대기 요청이나 승인자 기록을 만들지 않는다.

### 업무 질문 4 — 여러 원자재를 한 번에 입고할 때 일부 오류

여러 품목을 한 번에 입고하다가 한 품목의 수량이나 정보가 잘못된 경우의 기대 반응을 확인한다.

1. 전체 입고를 취소하고 어느 품목도 반영하지 않음
2. 정상 품목만 입고하고 잘못된 품목만 제외함
3. 오류 품목을 알려 준 뒤 사용자가 전체 취소 또는 정상 품목만 진행 중 선택함

추천은 1번이다. 일부 품목만 반영되면 사용자가 화면에서 제출한 묶음과 실제 재고·입출고 내역이 달라지고, 다시 처리할 때 중복 입고가 생기기 쉽기 때문이다.
