> 상태: 롤백 뒤 보존한 조사 초안. 운영 승인본·자동화 오라클·현 `main`의 완전한 기능 명세가 아니다.
> 코드 기준: `main` @ `b0f7564f`; 비교 기준: `codex/quality-preserved-20260914` @ `60e045b3`. 두 기준은 서로 조상이 아닌 별도 계보이며 어느 한쪽도 자동 채택하지 않는다.
> 테스트 기준 확정 전 단계: 기대 반응과 실제 반응을 분리하며, 기존 코드·기존 테스트·보존 브랜치를 곧바로 정답으로 간주하지 않는다.

## 0. 롤백 이후 보존·재개 원칙

- 이 문서의 실화면·API·DB 수치와 판정은 각 항목에 적힌 실행 시각과 당시 환경에만 유효한 시점 증거다. 현재 변동값은 문서의 숫자를 재사용하지 않고 `python _attic/backend-scripts/facts.py`로 다시 확인한다.
- `기대값 제안`은 정책 미확정, `합의`는 사용자와 확인한 기대, `코드 조사`는 실행 검증이 아닌 코드 독해, `일치`는 해당 행에 명시된 UI·API·DB 증거 범위에서만 성립한다. 자동 테스트 기준으로 고정하기 전에는 기대와 현행을 다시 대조한다.
- 품질 보존 브랜치의 커밋·파일·테스트를 통째로 merge 또는 cherry-pick하지 않는다. 보존 브랜치는 미검증 변경을 포함한 비교·복구용 스냅샷이지 운영 승인본이 아니다.
- 기능 후보마다 관련 계약 ID, 보존 브랜치의 원본 commit 또는 hunk, 현 `main`과의 의미 차이, 데이터·권한·동결 화면 영향, 되돌리기 방법을 기록한다.
- 최신 `main`에서 먼저 실패를 재현하고 회귀 테스트를 RED로 만든 뒤, 최소 변경으로 재구현하거나 필요한 hunk만 좁게 이식한다. 직접 관련 테스트와 서비스·API/DB·UI 경계를 검증한 기능만 하나씩 반영한다.
- 주간보고 화면과 backend 보고 API는 동결 영역이다. 아래 주간보고 항목은 관찰·테스트 후보로만 보존하며, 사용자의 명시적 요청 전에는 코드 변경 후보로 실행하지 않는다.

## 1. 목적과 진행 순서

입출고·출하·불량·재작업·입출고 내역·관리자 설정의 모든 사용자 경우를 목록화하고, 각 경우의 기대 반응과 실제 UI/API/DB 반응을 같은 표에 기록한다. 사용자가 기대값을 확인한 뒤에만 자동 테스트의 오라클로 고정한다.

1. 화면·API·서버·기존 테스트에서 가능한 경우를 조사한다.
2. 코드로 확인 가능한 현재 동작은 질문하지 않고 조사 결과로 기록한다.
3. 실제 화면에서 가능한 흐름·입력·제약을 먼저 확인하고, 현재 동작과 제안 테스트를 한 묶음으로 사용자에게 확인한다.
4. 개발 서버에서는 식별 가능한 소량의 테스트 건을 실제 제출해 UI·API·위치별 재고·예약·원장·내역을 확인한다.
5. 현재 `main`의 격리 DB에서 기능 후보 하나씩 같은 시나리오를 재현해 기대와 실제의 일치 여부를 기록한다.
6. 사용자가 확인한 기대값을 서비스/API·DB/Playwright 테스트로 자동화한 뒤 해당 기능의 최소 변경만 선별 반영한다.

실제 실행 전 상태는 `미실행`으로 유지한다. 코드 독해 결과는 `코드 조사`이며 실제 브라우저·DB 검증을 대신하지 않는다.

## 5. 업무 질문 13~22 결정과 코드 조사

### 13. 결재 대기 중 출고 재고: 결정됨

요청 제출 즉시 원본 위치에 예약하고, 승인 시 예약을 해제하면서 실제 이동한다. 반려·취소 시 실제 이동 없이 예약만 해제한다. 입고 전용 요청은 예약하지 않는다.

- 코드 조사: 현행과 일치. `backend/app/services/stock_requests.py:206`, `backend/app/services/sr_validation.py:88`, `backend/app/services/sr_approval.py:262`

### 14. 결재 대기 요청 취소 권한: 현행 유지로 결정됨

현행 기준을 그대로 사용한다. 요청자 본인 또는 창고·부서 결재 역할 보유자가 PIN 확인 후 취소할 수 있다. 취소 사유는 현재 받지 않는다. 단, 아무 부서의 결재 역할만 있어도 다른 부서 요청을 취소할 수 있는 현재 범위까지 유지한다는 의미인지 최종 테스트 표 작성 전에 다시 위험 항목으로 표시한다.

- 코드 조사: `backend/app/services/sr_approval.py:324`

### 15. 결재 반려 사유: 결정됨

반려 사유를 필수 입력하고 요청자 화면, 결재 내역, 관련 이력에 표시한다.

- 코드 조사: 서버는 사유를 필수 검증하고 저장한다. 모든 관련 화면 표시 여부는 실제 검증 필요. `backend/app/services/sr_approval.py:254`, `backend/app/services/sr_approval.py:269`

### 16. 승인 전에 재고·품목·공정·BOM이 변경됨: 결정됨

전체 승인을 막고 달라진 모든 품목과 이유를 한 번에 표시한다. 요청자가 내용을 다시 확인해 새로 제출하기 전에는 실행하지 않으며 모든 상태 변경은 원자적으로 원복한다.

- 코드 조사: 현행은 승인 시 재검증과 트랜잭션 원복은 하지만 검증 루프가 첫 오류에서 예외를 발생시켜 모든 오류를 한 번에 모으지 않는다. 기대와 일부 불일치. `backend/app/services/sr_approval.py:87`, `backend/app/services/io_dispatch.py:109`

### 17. 임시저장 후 품목·BOM·부서 기준이 변경됨: 결정됨

변경 사실과 영향을 받은 모든 품목을 표시하고, 최신 기준으로 다시 미리보기하기 전까지 제출을 막는다.

- 코드 조사: 현행은 기존 BOM 선택 의도를 보존하면서 실시간 부서 경로를 정규화해 제출할 수 있어, 필수 경고·재미리보기 계약과 다르다. `backend/app/services/io_dispatch.py:90`, `backend/app/services/io_dispatch.py:1406`, `backend/tests/test_io_v2.py:4770`

### 18. BOM 하위 품목이 모두 재고 미반영임: 결정됨

재고 변동이 없음을 명확히 안내한 뒤 완료하고, 무변동 작업임을 입출고 내역에 남긴다.

- 코드 조사: 완료 메시지와 무재고 실행은 현행에 존재한다. 거래 원장이 없는 무변동 배치가 입출고 내역에 확실히 노출되는지는 실제 검증이 필요하다. `backend/app/services/io_dispatch.py:1350`, `backend/app/services/io_dispatch.py:1364`

### 19. 완료된 입출고의 취소·정정: 결정됨

원본은 삭제하지 않는다. 권한자가 사유를 입력하면 반대 효과의 별도 역전 작업·원장을 만들고 원본과 연결한다.

- 코드 조사: 말씀하신 대로 현행의 operation 연결 거래는 이미 이 방식이다. 요청자 또는 결재 역할 보유자, PIN, 사유를 확인한 뒤 묶음 전체를 역전한다. `backend/app/routers/inventory/transactions.py:1120`, `backend/app/routers/inventory/transactions.py:1178`, `backend/app/services/inventory_operation_cancellation.py:956`

### 20. BOM 입출고 내역 표시: 결정됨

상위 품목을 작업 제목·참조로 표시하고, 실제 증감한 하위 품목의 위치·수량·역할을 펼쳐서 표시한다. 커스텀 BOM 상위가 미반영이면 상위 수량이 실제 변동처럼 보이지 않아야 한다.

- 코드 조사: 현행 표시 구조와 관련 UI 테스트는 이 방향이다. 실제 데이터 종단 검증은 필요하다. `frontend/app/mes/_components/_history_sections/HistoryBatchDetailPanel.tsx:552`, `frontend/app/mes/_components/_history_sections/__tests__/BomBatchDetail.test.tsx:205`

### 21. 실패·반려·취소 요청의 이력 보존: 결정됨

모두 영구 보존하고 상태·사유·요청자·결재자·재고 무변경 여부를 표시한다. 화면 제출 전 검증 실패도 감사 로그 범위를 별도 계약으로 세분화한다.

- 코드 조사: 반려·취소 요청 상태는 보존하지만 거래 기반 입출고 내역은 실제 거래 로그가 없는 실패 요청을 모두 표시하지 못한다. 기대와 일부 불일치. `backend/app/services/sr_approval.py:265`, `backend/app/routers/inventory/transactions.py:289`

### 22. 입출고 내역 필터: 결정됨

날짜·상태·유형·부서·품목·요청자 필터를 서버 전체 이력에 적용한다. 페이지 이동, 총 건수, 요약, 합계도 동일한 조건과 모집단을 사용한다.

- 코드 조사: 날짜·유형·부서·품목·검색 등은 서버 필터와 그룹 페이지에 적용된다. 거래 조회에는 요청 상태 전용 필터가 없고, 별도 요약과 모든 조건이 완전히 같은지는 종단 검증이 필요하다. `backend/app/routers/inventory/transactions.py:289`, `backend/app/routers/inventory/transactions.py:405`

## 6. 다음 조사 방식

추상적인 업무 정책 질문을 먼저 나열하지 않는다. 실제 화면을 작업 유형별로 열어 다음 순서로 검토한다.

1. 화면에서 확인한 현재 단계·입력·권한·메시지를 기록한다.
2. 개발 서버에서 안전하게 구분 가능한 소량의 요청을 실제 제출한다.
3. 결재 전후의 위치별 재고, 요청 상태, 입출고 내역을 함께 확인한다.
4. `현행 동작`과 `제안 테스트 기대값`을 같은 표로 제시하고 사용자에게 확인받는다.
5. 화면이나 코드로 알 수 없는 업무 기준만 마지막에 질문한다.

남은 큰 묶음은 사용출고 세부 정책, 품목 전환, 입출고 내역의 표시·집계 경계, 출하, 불량·재작업, 관리자 변경 영향이다.

역할 테스트는 화면 노출만으로 통과시키지 않는다. 같은 사용자·같은 payload로 직접 API를 호출해 허용 역할은 성공하고 비허용 역할은 `403`과 전체 무변경을 반환해야 한다. 창고 결재와 부서 결재가 모두 필요한 복합 요청은 각 단계의 승인 순서, 중복 승인, 거절, 취소, 역할 변경 중 승인까지 포함한다.

AS·연구 사용출고의 BOM 계약도 부서 BOM 입출고와 동일하게 고정한다. 커스텀 BOM으로 사용출고할 때 **상위 자재 재고는 전혀 변경하지 않고**, 사용자가 최종 포함한 **하위 자재만** 선택 위치에서 차감한다. 제외한 하위 자재, 다른 부서, 창고, 격리·B급·구형 재고는 모두 그대로여야 한다.

관리자 연쇄 테스트의 핵심 판정은 다음과 같다.

- 기준 정보 저장 직후 해당 정보를 소비하는 모든 신규 화면·후보·필터·권한이 같은 값으로 갱신되어야 한다.
- 기준 정보 변경은 과거 거래의 품목·위치·구성·처리자 스냅샷을 소급 변경하거나 연결을 끊어서는 안 된다.
- 삭제·비활성화·역할 회수는 현재 재고, 예약, 대기 결재, 진행 중 출하, 불량 원건을 우회하거나 고아 상태로 만들 수 없다.
- 관리자 화면에서 차단한 작업은 직접 API에서도 동일하게 거부되고, 실패 시 기준 정보와 모든 업무 데이터가 전부 무변경이어야 한다.
- 내보내기와 정합성 검사는 같은 원천 거래·분류·KST 기간 계약을 사용해야 하며 화면 집계와 파일·검사 결과가 서로 달라서는 안 된다.

주간보고 자동 테스트는 단순히 API의 `validation.status == verified`만 검사하지 않는다. 품목별 원장 합, 공정별 카드, 전체 요약, 모델별 생산 매트릭스, F705-02 파일을 독립적으로 계산한 기대값과 각각 대조한다. 어느 영역이 다른 업무 정의를 사용한다면 명칭·제외 사유·검산 범위를 화면과 응답에 명시해야 한다.
