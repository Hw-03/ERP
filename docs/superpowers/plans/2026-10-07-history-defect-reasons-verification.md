- 전체 마이그레이션 검사와 새 검증 DB의 bootstrap `--all → --check`가 통과했다. PostgreSQL 환경 미구성과 과거 출하 전용 DB 조건으로 3개 검사가 skip됐다. 새 DB `integrated-qa.db`는 0040이며 이전 기능 검증 DB는 이관에 재사용하지 않았다.
- 통합 소스 compileall과 OpenAPI 재생성이 통과했다. 기본 Turbopack production build와 TypeScript 검사가 통과했고 번들 크기는 2.939MB로 2.950MB 제한을 지켰다. 격리 워크트리의 node_modules junction을 인식하도록 빌드 중에만 root를 지정하고 원래 설정 바이트를 복원했다.
- staged smart 계획은 이미 main에 있는 인프라·검증 기록을 포함하여 전체 게이트로 승격했다. 이번 변경은 검증 실행 구조나 공통 설정을 변경하지 않으므로 기존 main 검사와 기능 검사를 재사용하고, 실제 충돌·사유 계약·소비자 회귀·전체 이관·타입·빌드·번들을 직접 검증했다. 최종 문구와 비동기 테스트 수정의 14개 검사 및 대상 ESLint, 통계 회귀 43개, staged whitespace 검사를 다시 통과했다.
- 자동 승인 검토가 백그라운드 서버 실행과 전용 프론트 재실행을 ‘blocked by policy’로 거절했고 구체적인 이유는 없었다. 도구가 관리하는 백엔드 실행은 허용되어 8020 readiness와 0040을 확인했다. 통합 후 프론트 브라우저 재검증은 수행하지 못했다. 위 PC·모바일 사유 화면 증거는 main 통합 전 검증이다.

원본 main의 별도 미커밋 파일 3개는 stage하지 않는다. 검증 DB·화면·로그는 원본 체크아웃의 ignored `_attic/runtime/history-defect-reasons/`에 보존한 후 사용자가 요청한 격리 워크트리만 정리한다. 운영 DB의 0040 적용은 별도 요청 대상이다.

## 2026-10-07 개발 서버 사유 목록 조회 복구

사용자가 실제 개발 서버 3001의 조회 오류를 보고하여 개발 환경을 복구했다. 8011 readiness는 DB revision 0038로 503이었고, 기존 백엔드의 새 사유 API는 404를 반환했다. 검증용 3020 서버 종료와는 별개로 개발 DB 이관과 백엔드 재시작도 필요했다.

개발 백엔드를 정식 stop 스크립트로 중지하고 SQLite backup API로 `development-before-0040.db`와 이관 검증 복사본을 생성했다. 복사본에서 bootstrap `--all`과 기존 행 비교·FK·무결성 검사를 통과한 뒤 개발 DB에 동일하게 적용했다. 이관에서 의도적으로 제거한 employees.level과 갱신한 Alembic 메타데이터를 제외하고 기존 모든 컬럼의 업무 행을 해시로 비교하여 보존을 확인했다. `--check`도 통과했고 정식 start 스크립트로 8011을 재시작했다. 시작 시 자동 이관을 추가하지 않았다.

0040 readiness의 database/schema/inventory/ledger는 모두 true이며 3001을 통한 직원 사유 목록 조회가 HTTP 200을 반환했다. 사용자가 열어 둔 실제 불량 작업의 선택창에서 ‘다시 시도’ 후 목록과 검색·선택 가능 상태를 확인했다. 가상 목록을 주입하거나 재고 처리·사유 변경을 제출하지 않았다. 직원 환경 `C:\ERP-dev` 및 3000·8010은 변경하지 않았다. 백업과 bootstrap·schema check 로그, 화면은 ignored `_attic/runtime/history-defect-reasons/`에 남겼다.
