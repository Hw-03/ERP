# 작업 중 재고 예약·대시보드·관리자 작업 예약 관리

**GOAL:** 격리 워크트리에서 작업 저장 시 자재를 예약하고, 대시보드에 담당자·목적·예약 자재·증가 예정 재고를 표시하며, 관리자 탭의 작업 예약 관리에서 전체 작업 조회와 사유를 남기는 취소를 제공한다.

**계획 수정일:** 2026-10-20. CP0 환경 준비, CP1 계약 고정, CP2 시안 승인, CP3 저장 예약의 핵심, CP4 상태 전이·관리자 API, CP5 작업 중·대시보드 화면, CP6 관리자 작업 예약 관리 메뉴, CP7 통합 검증을 완료했다. CP8은 미착수다. `subagent-driven-development`와 `efficient-verification`을 적용한다.

**2026-10-22 후속 화면 기준:** 직원의 `내 작업 / 전체 작업` 전환과 관리자 `작업 관리` 표시는 [직원 작업 현황 공유 계획](2026-10-22-shared-work-drafts.md)을 따른다. 아래 CP별 완료 기록은 당시 화면과 검증의 역사 기록으로 보존한다.

**CP별 진행 방식:** 위 GOAL은 전체 목적이며, 실제 도구 GOAL은 한 번에 해당 CP 하나만 생성한다. CP 완료 후 GOAL을 완료 처리하고 다음 CP를 자동 시작하지 않는다. 표의 추천 모델·추론 수준은 부모 채팅에도 적용하며 사용자가 CP 경계에서 직접 변경한다. 하위 에이전트는 부모가 역할별 지정 모델·추론 수준으로 생성한다. 현재 채팅 설정을 도구로 자동 변경했다고 보고하지 않는다.

**최신 DB 지시:** 개발용 `C:/ERP/backend/mes.db`를 SQLite 읽기 전용 백업으로 워크트리에 독립 복사하여 사용한다. 자동 테스트는 기존 메모리 DB/합성 fixture로 격리한다. CP7에서 사용자가 “하나 새로 만들면 되지. 알아서 만들어서 진행해”라고 명시하여 개발 복사본에 한정한 창고 승인 검증 계정 `CP7-QA-20261020`을 생성했다. 실제 승인 확인 후 비활성화하고 창고 승인 권한을 회수했다. 기존 직원 PIN·권한과 원본 DB는 변경하지 않는다.

## 1. 화면별 역할과 확정 동작

| 화면 | 제공할 기능 |
|---|---|
| 입출고 → 작업 중 | 내 작업에서 본인 작업 저장·재개·수정·삭제. 전체 작업에서 모든 부서의 저장 작업을 조회 |
| 대시보드 | 전체 직원의 관련 작업을 조회. 누가, 어떤 작업을 위해, 어느 위치의 자재를 예약했고, 무엇이 얼마나 늘어날지 확인 |
| 관리자 → 작업 관리 | 저장 작업 검색·담당자/부서 필터·상세·처리 기록. 관리자 인증과 사유 입력 후 다른 직원의 작업 삭제와 예약 해제 |

- 품목을 고르는 동안에는 예약하지 않는다. **‘작업 중’에 명시적으로 저장할 때 필요한 자재 전량을 확보**한다. 부족하면 품목·위치·부족 수량을 안내한다. 수정 실패 시 기존 저장 내용과 예약, 화면의 수정 입력을 보존한다.
- 가용 재고는 **창고·정상 부서 실재고에서 그 위치의 작업·승인·출하 예약을 차감**한다. 각 예약은 한 번만 차감한다. 생산·입고 예정은 완료 전까지 가산하지 않는다.
- 예약은 자동 만료시키지 않는다. 제출 시 승인 예약으로 이관하고, 즉시 실행은 실제 소진으로 연결한다. 완료·삭제·최종 반려·취소 시 해당 예약을 정리한다. 일반 오류는 전체 롤백하며, 기존 일반 승인/사용출고의 실패 이력 확정 경로는 보존한다. 확정된 실패는 예약 정리와 버전 증가, `state_committed` 응답으로 구분한다. 계획/버전 충돌은 실패 확정으로 바꾸지 않는다.
- 기존 반려 흐름에 따라 작업 중으로 돌아온 건은 **반려 사유와 작업 중 상태**로 구분한다. 다시 저장하여 전량 확보하기 전까지 예약·확정 예정량 집계에서 제외한다. 투입 없이 입고만 있는 유효 작업은 **‘예약 대상 없음’**이며 예정량은 표시한다.
- 관리자는 직원 직급이나 창고 정·부 담당자가 아니라 **기존 시스템 관리자 PIN으로 인증한 사용자**다. 관리자 화면의 인증 상태를 재사용하되 API는 요청마다 인증을 검증한다.
- **다른 사람의 작업 취소는 관리자 메뉴에 둔다.** 대시보드에는 관리자 취소 버튼을 넣지 않는다. 작업 중 배치만 취소할 수 있으며, 제출된 승인 요청은 기존 승인·취소 절차를 따른다.
- 관리자 취소는 작업 취소와 예약 해제를 함께 수행하고, 처리 주체·시각·사유를 보존한다. 직원 식별은 기존 검증된 감사 세션을 사용하며, 공유 관리자 인증만 확인된 경우 특정 직원 이름을 추정하지 않고 ‘공유 관리자’로 기록한다.

## 2. 관리자 메뉴와 디자인 사양

### 메뉴와 정보 구조

- 관리자 상단 **‘시스템’ 그룹에 ‘작업 관리’**를 둔다. `AdminSection` 값은 `workReservations`를 유지하고 기존 `Tabs → Transition → Content` 경로에 연결한다. 메뉴 데이터는 해당 메뉴 진입 시 조회한다.
- 선택된 관리자 메뉴 바로 아래에 **좌측 작업 목록 → 우측 선택 상세**를 배치한다. 별도 상단 제목·요약 줄은 생략하고 작업 건수는 목록 헤더에서만 표시한다. 서로 다른 품목 수량을 합산하지 않으며 취소 기록 보기·비활성 담당자 전용 필터·정렬 선택은 제공하지 않는다.
- 목록 검색: 담당자·작업 종류·목적 품목명/코드·작업번호. 검색창은 ‘작업 목록’ 제목과 맨 오른쪽 건수 사이에 둔다. 필터는 **담당자 부서 / 담당자**이며 담당자 부서와 재고 위치를 구분한다.
- 기본 목록은 취소되지 않은 작업 중 배치다. 마지막 저장 시각이 오래된 순으로 정렬하고, 실제 경과 시간과 비활성 직원 표시를 제공한다. 임의의 ‘장기’ 기준이나 만료일을 만들지 않는다.
- 행에는 담당자·부서, 목적 품목·수량, 작업 종류, 작업 진행 상태, 마지막 저장 시각을 표시한다. 자재 확보 여부로 작업을 분류하지 않으며 반려 등 조치가 필요한 경우는 별도로 안내한다. 긴 품목명은 공간에 맞게 줄바꿈하고 상세에서 전체 내용을 확인할 수 있게 한다.
- 상세 순서: **작업 목적·담당자 → 예약 자재(위치·수량) → 완료 시 증감(품목·위치·수량) → 처리 기록**. 중첩 카드를 늘리지 않고 소제목과 구분선으로 나눈다. 취소된 작업은 기본 목록에서 제외하고 내부 이력·사유를 보존한다. 미선택 빈 화면은 가용 공간에 맞는 공용 큰 안내를 사용한다.
- 상세의 ‘작업 삭제’ 버튼은 확인창을 연다. 담당자·대상 작업·해제할 예약을 보여주고 **삭제 사유**를 필수로 받는다. ‘돌아가기 / 작업 삭제’로 명확히 표시한다. 내부 취소 서비스와 이력은 유지하며 공백 사유와 중복 클릭을 막고 실패하면 사유를 유지한다. 이미 제출·수정·취소된 경우 최신 상태를 다시 조회한다.
- 모바일은 기존 대시보드·입출고에 예약 정보를 반영한다. 현행 모바일은 관리자 화면을 제외하므로 이번 변경에서 모바일 관리자 진입을 새로 만들지는 않는다.

### 기존 화면과 어울리는 기준

- 현재 화면의 밝은 청색·슬레이트 배경, Pretendard, 부드러운 20px 카드, 얇은 경계선과 청색 선택 강조를 유지한다. `AdminPageHeader`, `AdminKpiBar`, `AdminListPanel`, `AdminDetailCard`, `ConfirmModal`을 재사용한다.
- 실제 구현 색상은 `LEGACY_COLORS`/`var(--c-*)`만 사용한다. 상태는 색상과 문구를 함께 제공한다. 본문 14px 이상, 부가 정보 12px 이상, 조작 영역 44px 이상을 기준으로 주변 화면과 맞춘다.
- 새 메뉴의 긴 이름 때문에 기존 메뉴 글자를 줄이지 않는다. 1914×883 및 1366×768에서 메뉴 겹침·잘림을 확인하고 필요한 최소 폭과 가로 스크롤만 조정한다.
- 관리자 목록과 상세는 각각 내부 스크롤을 사용한다. 긴 BOM, 긴 품목명, 많은 작업에서도 제목·선택 상태·주요 동작을 잃지 않도록 한다. 대시보드는 기존 행 밀도와 부서 색상을 유지한다.
- 대시보드 **분포 바**는 물리 재고 길이를 유지하며 예약 부분만 패턴으로 구분한다. **부서 배지**는 현재 수량과 예약량을 함께 표시한다. **우측 상세**는 가용·작업 예약·승인 예약·증가 예정을 구분하고 관련 작업으로 연결한다.
- 생산·입고 예정은 별도 표시한다. 부서 이동은 위치별 ‘이동 예정’이며 같은 품목의 전체 증가로 계산하지 않는다. 현재 재고가 0인 결과품과 도착 위치도 예정 정보에서 보인다.

### 구현 전후 디자인 체크포인트

1. **CP2:** 관리자 기본 목록·선택 상세·취소 확인창을 한 정적 HTML 시안에 만든다. 사용자 스크린샷의 대시보드 세 지점도 같은 시안에서 변경 모습을 확인한다. 가상 예시임을 표시하고 실데이터와 분리한다.
2. 실제 API 화면을 만들기 전에 시안을 사용자에게 보여주고 피드백을 반영한다. 취향이 맞지 않으면 시안에서 계속 수정한다. 이 대기 중 독립적인 백엔드 작업은 진행할 수 있다.
3. **CP8:** 승인된 시안과 실제 브라우저를 나란히 비교하여 여백·글자 크기·행 높이·색상·스크롤·빈 상태를 보정한다. 처음부터 사용자가 전체 완성본의 디자인 문제를 찾아야 하는 방식으로 넘기지 않는다.

신규 화면의 시안 확인은 [design 스킬](../../../.agents/skills/design/SKILL.md)의 Step 2-B, **“Only after the user approves the look, implement it for real”**에 따른다. 별도 승인 질문을 단계마다 반복하지 않고, 실제 시안을 준비한 다음 이 단계에서만 화면 방향을 확인한다.

## 3. 재고 처리와 API 계약

**CP1 확정 계약:** [수량·모델·상태·잠금·HTTP·검증 사례](2026-10-20-work-reservations-contract.md). 아래 요약보다 구체적인 필드/예외/호환 범위는 이 문서를 따른다.

- 실제 실행의 유효 증감계획 계산을 작은 공통 함수로 분리한다. 저장 예약·예정량·실제 실행에서 BOM 수정·제외·면제·경로·수량을 동일하게 해석한다. 미래 입고량으로 현재 필요한 자재를 상계하지 않는다.
- `IoDraftReservation`에 배치·품목·물리 위치·예약량을 기록하고, 서버가 확정한 유효 증감계획 스냅샷을 보관한다. 작업 예약은 기존 위치 및 품목의 `pending_quantity`에 포함한다. 무결성 검사와 타 요청의 예약 해제 보호 합계에도 이 원장을 포함한다.
- 배치 예약 상태는 `reserved / not_required / inactive`, 정수 `revision`을 사용한다(2026-10-21 사용자 변경). ‘예약 필요’ 별도 상태는 제거하며 반려 복귀는 draft/inactive와 반려 사유로 구분한다. 신규 부족 작업은 계속 원자적으로 저장을 거절한다. 전환 불가 기존 임시저장 작업은 실제 배포 시 백업·대상 목록 확보 뒤 승인된 범위로 정리하며, 지금 직원 DB는 변경하지 않는다.
- 생성은 안정된 `client_request_id`로 중복을 방지한다. 같은 생성 키에 다른 내용은 충돌이다. 수정·삭제·제출·관리자 취소는 `expected_revision`으로 오래된 요청을 거절한다. 수정 응답이 유실되면 같은 버전을 무조건 재적용하지 않고 충돌 후 최신 조회로 복구하며 입력을 보존한다.
- `revision`은 인증 후 배치 잠금·소유권 확인을 거쳐 비교한다. 저장·제출·요청 수정·반려 복귀·관리자 취소·기존 전환 등 **내용·상태·예약 원장을 바꾸는 성공 트랜잭션마다 증가**시킨다. 기존 실패 이력 확정도 증가하고, 실패 롤백과 변경 없는 중복 요청은 이전 버전을 보존한다. 일반 승인·반려는 기존 요청 상태/권한 guard를 유지하며 연결 배치 버전을 증가시킨다.
- 한 트랜잭션 안에서 **필요한 사용출고 roster 잠금 → 배치 → request_id 순 연결 승인 요청 → 기존·신규 품목 합집합의 정렬된 잠금 → 위치 예약 갱신** 순서를 지킨다. 기존 요청 수정 경로도 참여 범위에서 같은 순서로 맞춘다. 제출은 작업 예약에서 승인 예약으로, ‘요청 수정’은 승인 예약에서 작업 예약으로 원자적으로 이관한다. 계약 오류는 이전 상태 전체를 복원한다.
- 미리보기 `owner_batch_id`는 소유권과 편집 가능한 상태를 확인하여 자기 작업 예약만 재사용한다. 대시보드에는 소유자 가산을 적용하지 않는다. GET 조회는 저장된 예약 스냅샷을 보여주며 예약·경로를 변경하지 않는다.
- 품목 목록 응답의 `work_reservations`에 `work_reserved_quantity`, `approval_reserved_quantity`, 출하 예약과 위치별 예정 요약을 일괄 계산해 추가한다. 기존 `pending_quantity`는 **창고의 작업+승인 예약** 의미를 유지하고 부서/출하 예약을 합쳐 넣지 않는다. 신규 전체 합계는 정상 재고 범위다. 기존 ‘승인 대기’ 라벨은 승인 전용 수치를 사용한다. 행마다 별도 API나 DB 쿼리를 반복하지 않는다.
- `GET /api/inventory/work-status?item_id=…`: 해당 품목의 예약/결과 예정과 연결된 작업, 담당자, 작업 단계, 투입·결과 품목을 반환한다. 상세 정보는 선택한 품목을 중심으로 조회한다.
- `GET /api/admin/work-reservations`: 검색·담당자 부서·담당자·페이지를 지원한다. draft만 오래된 저장순으로 조회하며 응답은 `items,total,skip,limit`이다. 예약 상태·비활성·취소 기록 필터와 정렬 선택·분류 집계는 제공하지 않는다. `GET /api/admin/work-reservations/{batch_id}`는 상세·예약 내역·처리 이력을 반환한다.
- `POST /api/admin/work-reservations/{batch_id}/cancel`: `{ expected_revision, reason }`을 받고 관리자 PIN을 검증한다. 작업 취소·원장 해제·처리 주체/시각/사유 기록을 같은 트랜잭션에 저장한다. 재시도나 중복 취소로 다시 해제하지 않는다. 조회 API도 PIN을 검증하고 조회 중 DB를 초기화하지 않는다.
- 예정량은 작업 중과 승인 대기를 연결해 집계한다. 부분 완료된 요청은 열려 있는 요청/라인만 포함하며 완료·최종 반려·취소·실패 라인은 제외한다. 경로가 바뀌면 저장·제출·승인 때 재검증한다. 저장된 계획과 재계산한 실제 투입이 달라지면 기존 예약으로 조용히 실행하지 않고 충돌을 알린다. 재저장 또는 기존 요청 수정 절차로 필요한 자재를 다시 확보해야 한다.
- 실시간 revision과 쿼리 무효화에 작업 현황·관리자 목록/상세 키를 연결한다. 저장·취소·승인 후 해당 화면과 다른 사용자 세션에서 모두 갱신된다.

## 4. 놓치면 안 되는 기존 흐름

- **부족품 창고에서 가져오기:** 부족한 원작업의 서버 저장을 요구하지 않는다. 원작업 ID·수정 내용·단계·부서·메모를 현재 작성 세션에 보관하고 복귀 버튼과 이탈 경고를 제공한다. 기존에 확보한 예약은 보존하며 미등록 변경은 아직 예약되지 않았음을 표시한다. 창고 이동의 실제 완료 전에는 도착 재고로 계산하지 않는다.
- **실사 공유 컴포넌트:** 분포 바와 배지는 대시보드에서만 예약·예정 표시를 켜고, 실사에서는 기존 실재고 의미를 유지한다. 예정 위치를 표시하기 위해 가짜 물리 재고 행을 만들지 않는다.
- **비활성 담당자:** 기존에 예약된 작업은 담당자 비활성화만으로 해제하지 않는다. 관리자가 목록에서 찾아 사유를 남겨 취소한다. 과거 작업 최초 전환에서 비활성 담당자는 전환 차단 결과로 보고한다.
- **과거 불량 출발 작업:** 현행 입출고 범위를 대상으로 한다. `from_bucket=defective`는 별도 불량 화면으로 안내하고 예약하지 않는다. 과거 해당 작업은 조회·삭제를 유지하며 전환 보고서에 사유를 남긴다. 불량 pool 선택을 추정하는 구현은 포함하지 않는다.
- 주간보고, 모바일 하단 탭 디자인, 출하 5단계 최종 카드 동결 영역은 변경하지 않는다. ‘작성 중’ 문구 변경은 입출고 작업 문맥에 한정하고 다른 초안 기능까지 바꾸지 않는다.

## 8. 검증 선택과 코드 근거

검증은 실제 diff를 읽고 필요한 범위만 선택한다. 새 예약/관리자 동작은 실패하는 행위 테스트로 시작하고, 단순 문구·간격 변경에는 구현을 그대로 복제하는 테스트를 만들지 않는다. 격리 워크트리의 변경은 `powershell -ExecutionPolicy Bypass -File .\scripts\dev\verify_local.ps1 -Mode smart -ChangeSet working -PlanOnly`로 검사 계획을 확인한다. 경로 분류만으로 전체 검사로 승격되면 실제 소비자와 미해결 위험을 읽어 필요한 검사를 선택하고 근거를 남긴다.

- 백엔드 직접 관련 기준 파일: `backend/tests/test_io_v2.py`, `backend/tests/services/test_io_dispatch.py`, `backend/tests/services/test_io_workflow_integrity.py`, `backend/tests/services/test_sr_reservation.py`, `backend/tests/services/test_stock_request_actions.py`, `backend/tests/concurrency/test_io_draft_submit_concurrent.py`. 새 테스트는 `backend/tests/services/test_io_draft_reservations.py`, `backend/tests/routers/test_admin_work_reservations.py`에 둔다.
- 대표 실행: backend에서 `python -m pytest tests/services/test_io_draft_reservations.py tests/routers/test_admin_work_reservations.py tests/services/test_sr_reservation.py tests/services/test_stock_request_actions.py tests/concurrency/test_io_draft_submit_concurrent.py -q`. 상태 전이/순서/가용량 기대값이 모두 일치해야 한다. 사용 가능한 DB별 동시성 결과를 구분하고 SQLite 결과만으로 PostgreSQL 행 잠금을 입증했다고 보고하지 않는다.
