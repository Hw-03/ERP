- 성공한 데이터 동기화에서 생성한 **직원 DB 원형 스냅샷**과 백업 manifest를 우선 재사용한다. 개발 코드로 추가 변환한 후보 DB와 혼동하지 않는다.

- 기준판을 격리 환경에서 기동해 로그인·품목·내역·재고 조회를 확인한다. 기준판부터 문제가 있으면 기존 문제로 기록하고 통합 회귀와 구분한다.

### CP2 — 전체 작업 통합

- 기준판에 기존 작업 브랜치를 통합한다. 기능을 임의로 몇 개씩 골라 적용하지 않는다.

- 한쪽 파일 전체를 선택해 충돌을 없애거나, 기존 마이그레이션을 삭제·수정해 이력을 맞추지 않는다.
- 새 정책 결정이 필요한 충돌은 해당 지점과 재현 내용을 남기고 중단한다. 단순 import·타입·연결 충돌은 국소 수정한다.
- 기준 DB의 별도 사본에 통합판 마이그레이션을 명시적으로 적용한다. 기존 업무 행·컬럼은 승인된 변경 외에 보존되는지 비교한다.
- 서버 기동 자체로 마이그레이션·초기화·시드를 실행하지 않는다.

**통과 조건:** 기준판과 통합판의 코드·DB 조합이 각각 재현되며, 통합 변경과 충돌 해결 내역을 설명할 수 있다.

## 3. 실제 직원 DB 복제본의 브라우저 업무 검증 — CP3

- 원형 스냅샷은 보관하고, 업무별로 초기화 가능한 검증 사본에서 처리한다.
- **기존 E2E의 DB 삭제·합성 시드 초기화는 사용하지 않는다.** 복제 DB를 유지하는 전용 실행 설정을 사용한다.
- 전용 로컬 주소·DB 절대경로·프로세스 소유권을 확인한다. 운영 포트와 외부 연동 주소를 사용하지 않는다.
- 실제 품목·BOM·부서·공급업체·재고 분포를 이용한다. 기존 운영 요청을 임의로 완료하지 않고, 검증용으로 새 요청을 생성해 추적한다.
- 로그인/PIN 준비가 필요하면 복제본에만 적용하고 변경 내용을 기록한다. 품목·BOM·재고를 임의로 바꿔 성공 조건을 만들지 않는다.
- 사전 데이터 대조는 API·DB 조회를 사용할 수 있지만, 핵심 업무의 선택·입력·제출·승인·취소는 브라우저로 수행한다.

| 검증 묶음 | 브라우저에서 수행할 작업 | 확인할 결과 |
|---|---|---|
| 원자재·튜브 입고 | 공급업체 선택, 수량 입력, 미리보기, 제출 | 허용 품목·공급업체, 정확한 입고 위치, 완료 상태와 거래 이력 |
| 창고·부서 이동 | 창고→부서, 부서→창고, 허용된 부서 간 이동 | 출발 위치 감소·도착 위치 증가, 다른 위치 불변 |
| 생산·분해 | 실제 BOM을 가진 품목으로 생산·분해 | 부모·자식의 실제 부서와 수량, 부족 재고 차단 |
| 사용출고·결재 | 일반 부서 및 AS·연구 경로로 요청·승인 | 승인 전후 재고 반영 시점, 예약, 담당자 역할 |
| 수량 보정·품목 전환 | 실제 화면에서 허용된 증가·감소·전환 | 미리보기와 결과 일치, 위치별 증감·작업 이력 |
| 불량·B급·구형 | 창고/부서 격리, 부분·전량 정상 복귀, 일괄 처리 | 원건 잔량, 정상 복귀 위치, 다른 분류·위치 불변 |
| 폐기·재작업·반품 | 허용된 분류·위치·업체로 처리 | 상위·하위 수량, 격리·정상·폐기 구분, 이력 |
| 출하 | 요청→준비→예약→픽업, 준비 취소·픽업 취소 | PF·동반 출하품 가용량, 예약 해제, 실제 출하 위치 복원 |
| 취소·실패 | 단건/묶음 취소, 중복 제출, 부족 수량, 변경된 초안 | 중복·부분 반영 없음, 허용된 취소의 원래 위치·예약 복원 |
| 조회·보고 | 처리 후 내역·상세·일보·주간 조회 | 같은 작업의 수량·담당자·시각·분류가 일치 |

- 각 작업의 **전 수량 → 예상 변화 → 실제 후 수량 → 취소 후 수량**을 위치별로 기록한다. 무관한 품목·부서가 바뀌지 않았는지도 대조한다.
- 입고·이동·정상 복귀 후에는 그 위치의 재고를 실제 다음 생산·사용출고·출하에서 사용한다.
- PC에서는 전체 업무 유형을 확인한다. 모바일에서는 별도 화면 경로가 있는 입출고·불량 복귀·출하·취소를 실제 완료한다.
- 실제 자료에 적합한 품목이나 BOM이 없으면 해당 조건을 미실행 사유와 함께 기록한다. 필요하면 별도 합성 검증을 연결하되 운영 자료 검증의 성공으로 표시하지 않는다.
- 실패하면 해당 업무 사본과 로그를 보존하고 최소 수정 후 영향받는 묶음만 다시 실행한다.

**통과 조건:** 화면 완료 표시뿐 아니라 실제 위치 수량·예약·원건 잔량·후속 사용·취소가 예상과 일치한다.

## 4. 성능·회귀·전환 검증 — CP4·CP5

### CP4 — 통합으로 새로 느려지거나 깨진 부분 확인

- 같은 원형 자료에서 만든 기준판·통합판 DB와 같은 실행 조건으로 일반 품목 목록·검색·상세·내역을 비교한다.
- 준비 호출 후 각 조회 30회씩 측정하고, 기준판/통합판 순서를 바꿔 한 번 대조한다. 결과가 경계에 걸릴 때만 해당 조회를 추가 측정한다.
- 일반 조회의 p95가 기준판보다 **20%와 100ms를 모두 초과해 증가**하면 회귀 후보로 조사한다. 응답 내용·조회 범위가 같은지도 확인한다.
- 무거운 조회의 기존 2초·10초 목표와 동시 30명 전체 행렬은 다시 시작하지 않는다. 새 오류·시간초과·뚜렷한 악화가 발견된 경로만 확인한다.
- 충돌 해결 파일과 직접 소비자의 테스트, 프론트 타입·정적 검사, 관련 마이그레이션·보존 검사를 수행한다.
- 통합판의 production 빌드와 승인된 3.00MiB 번들 검사를 수행한다. 기존 빌드는 입력이 정확히 일치할 때만 재사용한다.
- 이전 기대값 근거는 당시 완료로 보존한다. 새 통합 조합의 전체 기대값 PASS로 자동 승격하지 않는다.

### CP5 — 사용자가 두 버전을 바꿔 확인할 수 있도록 준비

- `배포 기준판`과 `통합판` 선택 도우미를 제공한다. 선택 시 전용 서버 종료 → 코드·DB·빌드 확인 → 검증용 DB 사본 연결 → 기동 순서로 처리한다.
- 코드만 옛 커밋으로 바꾸고 최신 DB를 그대로 사용하는 조합을 거부한다. 미커밋 변경이나 소유권이 다른 프로세스가 있으면 강제로 덮어쓰거나 종료하지 않는다.
- 확인 중 사용자가 만든 검증 데이터는 원형 DB와 분리한다. 다시 확인할 때 초기 검증 상태로 돌아갈 수 있게 한다.
- 실제로 **기준판 → 통합판 → 기준판** 전환을 한 번 수행해 로그인·조회·DB 조합·종료를 확인한다.
- 이는 격리 검토 환경의 전환 검증이다. 직원 서버 배포·운영 복구 성공으로 확대하지 않는다.

**통과 조건:** 통합으로 생긴 회귀를 확인했고, 사용자가 두 버전을 올바른 DB 조합으로 다시 열 수 있다.

## 5. 커밋·검토 자료·정리

| 지점 | 저장 내용 |
|---|---|
| 기준판 | 실제 배포 소스와 출처, DB 스냅샷 식별값 |
| 통합판 | 통합 코드와 충돌 해결 내용 |
| 업무 검증 | 기능별 결과·최소 수정·재고 전후 대조 |
| 성능·빌드 | 동일 조건 비교, 관련 검사와 빌드 결과 |
| 사용자 검토 준비 | 버전 선택 방법, 전환 검증, 최종 상태 |

- 각 업무 묶음이 끝날 때 수정 또는 검증 기록을 로컬 커밋한다. 통과하지 않은 지점은 `진행 중·실패·미실행` 상태를 명확히 기록한다.
- 커밋에는 코드·정제한 결과·재현 정보만 포함한다. 실제 DB, 직원 정보가 담긴 화면·로그, PIN·환경 파일, 빌드 산출물은 로컬 검증 자료로 보관한다.
- 커밋 제목은 실제 날짜의 한국어 형식(`YYYY-MM-DD area: summary`)을 따른다. 원격 푸시는 별도 요청 전까지 하지 않는다.
- 출근 후 볼 자료에는 **달라진 동작, 화면 여는 방법, 선택할 품목·시나리오, 예상 결과, 실제 결과, 알려진 한계**를 기능별로 적는다.
