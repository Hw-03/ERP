# BOM 입력·AS 조회 오류 원인 확정과 최소 수정

**GOAL:** 두 간헐 실패를 제품·자동화·실행 환경 문제로 구분할 근거를 확보하고, 확인된 원인의 최소 수정과 관련 회귀 검증을 완료한다.

2026-10-19 대화에서 승인한 CP0~CP4 계획의 실행 색인이다. 기존 후보 `codex/mes-main-candidate-comparison-20261016`, 시작 `782eb344`, 미커밋 AS 완료 문구와 기록을 보존한다. main·직원 서버·예약·실제 DB와 사용자 검토용 후보 화면/초안을 변경하지 않는다.

## CP0 환경 고정

- 새 합성 QA 자료, 소스·설정·lockfile·프로세스 소유권·포트를 기록한다. 기존 진단 원문은 보존한다.
- 테스트 실행기·Next·백엔드·브라우저를 같은 Linux 호스트에 둔다. 과거 Node20.20.2/Python3.11.17/Chromium1223 및 lockfile을 맞추고 OS 차이는 기록한다.
- 실제 앱 load·로그인 화면 준비가 원래 기한 안에 끝나야 업무 재현으로 인정한다.

## CP1 계측과 원인 구분

- BOM: `SHIP-VARIANT`, `SHIP-GENERATED-ROLES`. native 입력→React handler→모든 draft setter→commit→match body→저장값을 동일 품목/입력/시간축으로 연결한다. focus·선택·취소·DOM UID를 메모리 버퍼에 남긴다. 추가 대기·재입력으로 순서를 바꾸지 않는다.
- API: `IO-RESEARCH-RETURNS`. 제출201 뒤 상세·draft GET을 기존 Next 프록시로 보낸다. 직전 응답→idle→서버 종료/예외→FIN/RST→Next 재사용→500을 연결 ID와 주소/포트로 연결한다. loop 지연·PID·stderr·파일로그를 보존한다.
- PIN·쿠키·업무 본문을 계측하지 않는다. EOF 재현만으로 원 CI의 OS read reset 원인을 확정하지 않는다. 입력 미도달만으로 직원 영향 없음을 단정하지 않는다.

## CP2 국소 CI와 최소 수정

- 로컬에서 결정적 기록을 못 얻으면 후보 브랜치 진단 커밋·푸시 및 세 선택자만 실행하는 CI를 사용한다. 기존 전체 CI 정책은 유지하며 이번 진단 HEAD의 자동 일반 CI만 확인 후 취소한다.
- worker1·retry0·첫 실패 중단. 선택자별 최초 최대3회. 실패 없이 반복 통과하면 원 CI 선행 작업/요청 간격/누적 연결 중 필요한 조건만 복원한다. 가설·변수 하나씩 기록한다.
- 실패 회귀검사를 먼저 확보하고 원인 경계 한 곳만 수정한다. sleep·timeout 확대·재시도·단언 삭제·일괄 업데이트 금지. 공개 API·DB·재고 계산 변경 예정 없음.
- 수정 전 실패→수정 후 성공과 원인 변수 대조가 필요하다. 추측 패치로 완료 처리하지 않는다.

## CP3 국소 검증

- 새 회귀검사 수정 후10회, 원 세 선택자 각각3회, 마지막은 계측 없이 실행한다. 첫 실패 시 분석으로 복귀한다.
- BOM2/3 즉시 다음·match body·저장값·기본 BOM 불변, 원복/무효 수량/stale 응답을 확인한다.
- API 제출1회/201·두 조회·승인 전 재고·최종 승인에서만 차감/선택하위 반환·무선택/창고 불변을 확인한다. 전송 수정은 실제 Next 경유 검사를 포함한다.
- 영향 파일 테스트/ESLint/타입·필요 백엔드만 실행. 제품 수정 시 최종 production 빌드·3.25MiB 번들1회와 별도 IAB 탭 핵심 흐름을 확인한다. 기존 전체 검사는 재사용한다.

## CP4 기록과 종료

- 문제별 종료 즉시 상세·첫표·TODO·인계를 갱신한다. 원인/분류/직원 영향/신규와 재사용 근거/한계를 구분한다.
- 진단 도구·원인별 수정·최종 기록을 구분하고 필요한 경우 후보만 푸시한다. 국소 CI 성공을 전체 CI 성공으로 표현하지 않는다.
- 소유 진단 프로세스만 종료한다. 사용자 검토 환경과 고유 실패 자료는 보존한다. 원인 미확정이면 해결/병합 가능으로 승격하지 않는다.

## 10/19 국소 CI 진입 근거

- 동일 WSL Linux에서 원 BOM 두 선택자·AS 선택자는 각각3회 재시도 없이 통과. 원인 미확정이다.
- 원 CI의 직전 `SHIP-DISCARD`만 붙인 BOM 대조1회도 정상. 원 `DASHBOARD01`의101개 품목 준비만 복원한 AS 대조1회도 정상. 전체 shard는 다시 실행하지 않았다.
- 원 CI와 로컬의 OS/누적 자료 차이가 남아 있어 Ubuntu24.04·동일 Node/Python/Chromium의 전용 국소 workflow를 사용한다. 초기에는 원 세 선택자만 각최대3회, 첫 실패에서 중단한다.
- 진단 파일과 후보 전용 workflow만 커밋한다. 기존 공통 CI 설정·제품 소스는 그대로 유지한다. 별도 소스 export에서 계측하며, 사용자 후보3038/8038과 초안·연구 요청은 보존한다.
- 새 가드12건(Linux, skip0), Python/Node/TypeScript 구문과 workflow 파싱을 확인한다. 이후 국소 CI 성공을 제품 문제 해결이나 전체 CI 성공으로 표시하지 않는다.

## 10/19 첫 국소 CI 이후의 단일 변수 대조

- `4cfee12b`의 국소 CI39181286366은 원 세 선택자 각3회 성공, 기록 유실0이다. 제품 원인은 미확정이다. `--repeat-each=3 --workers=1`은 순차 실행하지만 worker0/1/2로 브라우저를 매번 새로 만든 사실을 보고서에 명시했다.
