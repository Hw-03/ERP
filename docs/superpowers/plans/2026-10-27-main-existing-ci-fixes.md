# 기존 main CI 실패 국소 수정

## 범위와 기준

- 작업 기준: main `706871c603c96543375570193ad38d44cf60ac9e`.
- 대상 실패: [관리자 로딩 표시 반영 CI](https://github.com/Hw-03/ERP/actions/runs/40453775805)의 Vitest 13건과 E2E 9건. [이전 main CI](https://github.com/Hw-03/ERP/actions/runs/40450492986)와 실패 제목이 같았고 새 실패 제목은 없었다.
- 다른 세션의 미커밋 제품·테스트 변경은 제외했다. 모바일 테스트는 아래 상태 설정 두 줄만 부분 스테이징한다.
- main의 커밋 사본을 Linux 로컬 진단 폴더로 내보냈다. 해당 사본에는 실제 DB와 환경 파일이 없으며 합성 `mes_e2e.db`만 생성·정리했다. 직원 환경·서비스·예약은 조작하지 않았다.
- Node 20.20.2, Python 3.11.17, Chromium revision 1223 및 lockfile과 일치하는 기존 의존성을 사용했다. 실제 DB·인증 세션·trace는 커밋하지 않는다.

## 검증 범위와 인계

- 대상 코드·lockfile이 같은 과거 성공 근거는 보존했다. 전체 백엔드·전체 E2E·커버리지·성능·복구·기대값 검사는 반복하지 않았다.
- 단위 검사 커밋의 staged smart 계획은 모바일 파일의 다른 세션 미스테이징 변경과 겹쳐 `Staged/working conflict`로 중단됐다. 가드를 완화하거나 다른 변경을 가져오지 않고, staged 내용과 일치하는 깨끗한 사본의 직접 검사 근거를 사용한다.
- 모바일 파일의 나머지 BOM 조회·실시간 갱신 수정과 다른 세션 변경은 그대로 남긴다.
- 인증 준비 순서와 헬퍼 diff의 독립 읽기 전용 리뷰에서 추가 수정 사항은 발견되지 않았다. 이는 위 실행 결과와 별도로 코드만 검토한 근거다.
- 인증 수정의 staged smart 계획은 다른 세션의 미스테이징 백엔드 변경 때문에 전체 백엔드로 승격됐다(`auth-smart-plan.log`). 실제 커밋에는 백엔드가 없으므로 해당 전체 검사를 반복하지 않고 깨끗한 사본의 직접 관련 검사·정적 검사·타입 검사를 사용했다.
- 신규 실행 합계는 단위 검사 78건, E2E 18건이며 모든 E2E 재시도는 0이었다. 기존 실패 기록은 보존했다.
- 단위 검사 입력 수정은 `335dbbd5`에 먼저 커밋했다. 인증 수정·헬퍼·이 기록은 별도 후속 커밋으로 구분한다.
- 새 main HEAD의 CI는 푸시 후 링크와 시작 상태만 보고하며 완료 대기는 하지 않는다.
- 후보 브랜치의 전체 병합과 직원 배포는 이번 작업에 포함하지 않는다.
