# 추가 조회 성능 개선

**GOAL:** 품목 저장의 불필요한 잠금과 BOM·출하·알림·내역 집계의 반복 조회 비용을 줄이고, 기존 업무 결과와 화면 동작을 유지한다.

**상태: 2026-10-27 구현·검증 완료.** 직원 환경 배포·커밋·푸시는 하지 않았다.

## 승인 범위와 순서

1. 현재 개발 코드(앞선 품목·이력·생산 가능 수량 개선 포함)를 고정하고 직원 DB의 읽기 전용 스냅샷으로 기준선을 측정한다.
2. P0: 품목 수정 커밋 후 응답 조립에서 쓰기 잠금이 다시 획득되는 상황을 재현하고, 응답은 별도 읽기 세션으로 조립한다. 커밋 헬퍼·일반 잠금·스냅샷 가드와 저장 자동 재시도 정책은 바꾸지 않는다.
3. P1: `GET /api/bom/parent-ids`로 기존 상세 BOM의 부모 집합과 동일한 UUID 배열을 반환한다. PC·모바일 입출고의 성공/실패·재시도·사전선택 대기를 유지하며 전체 상세 조회와 중복 revision refetch를 줄인다.
4. P2: 출하의 기존 API·응답·정렬·조회 범위와 캐시 구조를 유지하고 관련 객체·거래·역분개·부족 재고의 반복 조회를 요청 범위에서 일괄 처리한다.
5. P3: 닫힌 알림은 기존 개수 API, 열린 알림은 선택 목록을 조회한다. 직원별 캐시·로그인 팝업·30초/포커스/재연결 갱신·읽음/삭제 경합을 보존한다.
6. P4: 전수조사 집계는 검색이 없으면 SQL 집계, 검색이 있으면 최소 projection과 기존 검색 함수를 사용한다. 작업당 한 건·부서별 집계를 보존하고 집계·참조번호 요청에 취소 신호를 연결한다.
7. 공통 revision과 무효화 대상은 유지하고, 부모가 공용 키·통합 검증을 담당한다.

P0/P1을 먼저 완료한 뒤 P2/P3을 병렬 실행한다. P4와 최종 검증을 이어간다.

## 구현 근거와 회귀 경계

- 품목 수정은 `backend/app/routers/items.py`의 update_item만 커밋 후 별도 읽기 Session으로 응답을 조립한다. 테스트에서 외부 트랜잭션 bind를 보존하고 응답 조립을 멈춘 동안 다른 writer가 완료되는지 확인한다. `_tx` 헬퍼·DB engine 정책·스냅샷 가드는 수정하지 않았다.
- BOM 부모 API는 부모/자식 Item join으로 기존 상세 목록의 유효 관계 집합을 유지한다. `queryKeys.bom.parentIds()`는 기존 `["bom"]` 루트 아래에 있고, 편집 mutation 및 realtime의 해당 루트 무효화는 유지한다. 응답이 실패하면 빈 집합으로 오판하지 않는다.
- 출하 진행 중 조회 공유는 기존 `coalesced_read`만 사용한다. status/bind/revision 키 분리, 완료 후 결과 미보관, detached DTO를 검증했다. 타 직원의 예약도 기존 정책대로 차감하며 공용 재고 계산·예약 쓰기 정책은 바꾸지 않았다.
- 알림 개수의 `{count}`와 상세의 `{unread_count}`를 구분한다. 실패/미완료 조회는 로그인 1회 표시를 소비하지 않고, mutation 성공 시 진행 중 이전 응답을 취소한 후 서버 개수를 반영한다. 직원별 키와 기존 권한 헤더를 유지한다.
- 전수조사 집계는 동일한 작업 범위/품목 조건을 사용한다. 검색 없음은 SQL distinct 작업 집계, 검색 있음은 문자열 projection과 기존 별칭/동의어 함수를 사용하며 다중 일치 품목을 중복 작업으로 세지 않는다. 기존 전체 표시 묶음은 유지한다.
- API 계약 감사에서 `/api/bom/parent-ids` 추가를 제외한 OpenAPI 전체가 동일했다. 실제 스냅샷의 기존 BOM 전체·출하·알림·개수·집계·참조번호·품목·내역·생산 가능 수량 응답 해시가 같고, 새 부모 ID는 기존 BOM 부모 집합과 같았다.
- 동결 파일·DB 스키마·직원 환경·원본 서버는 본 작업에서 변경하지 않았다. 작업 트리에는 다른 세션의 변경이 있으므로 본 작업 생산 파일 목록은 runtime의 `qa-overlay.txt`로 구분한다. 관련 테스트·계획·측정 도구 파일은 별도로 포함한다.
