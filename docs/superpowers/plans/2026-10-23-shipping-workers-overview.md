# 출하 작업자 입력과 전체 작업 목록 통합

**GOAL:** 출하 작업자를 자유롭게 입력·변경하고, 준비 중인 출하를 전체 작업에서 작업자 이름과 출하 부서로 확인할 수 있게 한다.

## 승인한 동작

- 작업자는 선택 입력인 최대 200자 텍스트다. 여러 이름과 구분자를 보존하고 줄바꿈은 공백, 앞뒤 공백 제거 후 빈 값은 null로 저장한다. 직원 계정과 이름을 매칭하지 않는다.
- 데스크톱·모바일 요청 생성 첫 단계에 작업자를 추가하고, 상세에 독립 저장 입력란을 제공한다. 준비 중에만 수정하며 준비 완료 취소 시 다시 수정 가능하다. 요청자와 준비 완료 처리자는 별도다.
- 저장 실패·재조회·화면 이동 시 미저장 입력을 보호한다. 상태가 바뀌어 수정할 수 없게 된 경우에도 입력을 확인하고 이동할 수 있어야 한다.
- 전체 작업에만 준비 중 출하를 요청당 한 행으로 추가한다. 담당자·부서는 작업자 또는 `작업자 미입력`과 `출하`, 작업은 `출하 준비`, 대상은 최종 완제품(없으면 기본 완제품)·수량·코드, 예정 변동은 `픽업 시 출고`다. 기존 작업의 직원 부서는 유지한다.
- 작업자 이름은 줄바꿈하며 일반적인 이름 세 명은 기본 높이에 들어가는지 확인한다. 더 긴 경우 해당 행만 높이를 늘리고 생략하거나 글자를 줄이지 않는다.
- 펼침 상세에 요청자·인보이스·동반 출하품과 `출하에서 열기`를 제공한다. 준비 완료·픽업 완료·취소는 제외하고 준비 완료 취소로 준비 중이 되면 재표시한다.

## 계약과 구현 순서

1. 백엔드: nullable `worker_names` 컬럼·마이그레이션과 생성/수정/응답을 추가한다. 필드 생략은 기존 값을 보존한다. `PATCH /api/shipping/requests/{id}/workers`는 요청을 잠근 뒤 준비 중 상태를 검사하고 작업자만 변경한다. 실제 수정자·전후 값을 기존 변경 이력에 기록하며 준비 변경으로 취급하지 않는다.
2. 목록: `kind=shipping`을 기존 서버 union에 추가한 뒤 필터·건수·정렬·페이지를 처리한다. 작업자·품목명·코드 검색을 지원한다. 직원 ID 필터가 있으면 출하는 제외한다. 출하의 요청자 ID는 null, 실제 요청자 이름은 유지하고 표시 부서는 출하로 투영한다. 상세는 `shipping_summary={invoice_number,companion_lines}`를 제공한다.
3. 화면: 출하 입력·저장과 전체 작업 표시를 연결하고 기존 캐시 및 실시간 갱신을 재사용한다. 출하 5단계 카드 배치와 모바일 하단 탐색 디자인은 동결 규칙을 따른다.
4. 검증: 관련 백엔드·마이그레이션·프론트엔드 테스트와 타입·정적 검사 후 전용 서버 브라우저 흐름을 확인한다. 모든 변경은 연결된 shipping-work-overview 워크트리에서 수행한다. 전용 DB만 백업 후 명시적으로 마이그레이션한다. 포트는 3039·8039다.

## 합격 기준

- 선택 입력·여러 이름·개행·삭제·길이·기존 데이터와 구형 클라이언트의 필드 생략을 확인한다.
- 준비 중 저장 성공과 다른 상태 저장 거부, 상태 전환과 저장이 겹치는 경우를 확인한다. 작업자 수정으로 재고·BOM·SN·인보이스·상태가 변하지 않아야 한다.
- 기존 작업과 출하의 혼합 검색·부서 필터·정렬·페이지·건수 및 완료/취소/준비 복귀 표시를 확인한다.
- 데스크톱·모바일에서 요청 생성·상세 저장·실패 입력 보존·뒤로 가기·재조회와 작업자 이름 길이별 행 높이를 확인한다.
