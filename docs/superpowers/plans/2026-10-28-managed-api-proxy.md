# 프록시 연결 재사용 개선 실행 기록

**GOAL:** 브라우저와 백엔드 연결을 안전하게 재사용해 반복 연결 비용을 줄이고, 기존 유휴 연결 재사용 오류와 업무 기능 회귀를 방지한다.

사용자가 승인한 2026-10-28 계획을 실행한다. 커밋·푸시·직원 환경 배포는 포함하지 않는다. 원가분석 UI 요청은 사용자가 다른 채팅에 보낼 메시지였음을 확인하여 이 작업에 포함하지 않는다.

## 구현 계약

- `frontend/scripts/next-server.js`가 페이지·정적 파일·HMR을 Next에, `/api`와 `/api/*`를 고정된 `BACKEND_INTERNAL_URL`에 전달한다. 외부 입력으로 목적지를 고르지 않는다.
- 공개 `httpxy@0.5.6`과 전용 HTTP(S) Agent를 사용한다. Node 전역 Agent·Next 내부 모듈·의존성 소스는 패치하지 않는다.
- LIFO, 최대 연결 256개·유휴 64개, 유휴 만료 1초. 타이머와 요청 직전 단조 증가 시계 검사로 정리한다. 재사용 시 타이머를 취소하며 활성 저장·조회·SSE는 유휴 만료 대상이 아니다.
- 연결별 헤더는 각 구간에서 독립적으로 처리하고 인증·본문·쿠키·업무 응답을 유지한다. 요청·응답을 스트리밍하며 저장·조회 자동 재시도는 하지 않는다. 상류 비활성 타임아웃은 기존 30초다.
- Next 16이 자동 등록하는 HMR 리스너에는 별도의 미바인딩 HTTP 이벤트 서버를 제공한다. 실제 리슨 포트는 하나이며 API WebSocket과 Next 업그레이드가 동일 소켓을 중복 소비하지 않는다.
- 기존 감독 래퍼와 프로필·포트·산출물 분리·종료 진단을 유지한다. raw/start, Playwright, 격리 QA도 같은 진입점을 사용한다. 기존 전체 close 처리와 API rewrite는 최종 전환 시 제거한다.

## 성능·완료 기준

동일한 읽기 전용 DB 스냅샷과 백엔드 코드에서 기존 close, 이전 무관리 재사용, 새 관리 방식의 production HTTP를 비교한다. Next 프록시를 거치지 않는 과거 ASGI 결과로 대체하지 않는다.

- 품목·내역·출하·BOM·알림 개수·내역 집계: 조건별 100회, 동시성 1·5·10·20. SSE 열린 혼합 조회도 비교한다.
- 모든 응답의 해시 동등성, 오류·취소, p50·p95·처리량·양쪽 신규 TCP 수 기록.
- 짧은 간격의 순차 100회에서 양쪽 재사용률 90% 이상, 합성 전송 p95 감소.
- 대표 p95는 기존 close 대비 10% 또는 20ms 중 큰 값 이내, 일반 조회 2초·혼잡 조회 5초, 정상 부하 오류·취소 0.
- 직원 환경에 부하·쓰기를 실행하지 않는다. 저장 검증은 격리 QA DB만 사용한다.

## 근거 위치

- 자동 회귀: `frontend/scripts/api-agent.test.mjs`, `api-proxy.test.mjs`, `next-server.test.cjs`, `next-server.integration.test.mjs`.
- 실행 원자료: `_attic/runtime/proxy-pool-20261028/`.
- 측정 초기 TCP 계측은 Uvicorn의 전달 주소 해석으로 클라이언트 포트가 소거되는 문제가 발견되어 무효 기록으로 보존했다. 최종 측정은 표준 백엔드와 동일하게 proxy headers 해석을 끄고 수행한다.
- 최초 세 방식 비교는 시간대별 변동이 있어 동일 백엔드의 인접 블록 교차 비교로 보완했다. 교차 비교에서 상대 기준을 초과했던 집계 동시성 5는 사전에 정한 세 차례 측정을 모두 보존했고, 각 회차가 허용 범위를 통과했다. 과거 변동의 원인을 단정하지 않는다.
- 최종 검증 기록: `_attic/runtime/proxy-pool-20261028/results.md`. 새 관리 방식의 일반 p95 최댓값은 최초 867ms·교차 776ms, 혼잡은 최초 4,749ms·교차 2,028ms였다.
