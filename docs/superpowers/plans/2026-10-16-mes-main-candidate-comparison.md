# DEXCOWIN MES 개발서버와 병합 후보 비교

**GOAL:** 동일 직원 스냅샷에서 출발한 main과 병합 후보를 1920×1080 인앱 브라우저로 비교하고, 동작·수량·한계를 상세 기록해 병합 가능 여부를 판단한다.

2026-10-16 사용자 실행 승인. 후보 브랜치 검증·커밋·푸시·최종 CI까지 포함한다. 실제 main 병합과 직원 배포는 별도 결정이다. QA 직원 생성·PIN 초기화·권한 준비도 승인되었다. 직원 원본에는 적용하지 않는다.

부모만 인앱 브라우저를 순차 조작한다. 실제 CSS viewport 1920×1080 확인과 별도 탭·호스트로 쿠키 격리를 기록한다. A/B는 동일 개발 모드로 비교하고 마지막 B production에서 핵심 경로를 재확인한다. 모바일은 재사용 가능한 과거 근거와 관련 자동 검사로 구분한다. 에이전트는 브라우저 검사 중 DB를 변경하지 않는다.

## CP3 — 사용자 검토 기록

2026-10-16 추가 실행 지침: 새 업무 실행 전에 이미 확보한 화면·스냅샷·로그를 설명 문서로 복원한다. 기록을 채우기 위한 재실행은 하지 않는다. 이후에는 한 업무 묶음 종료마다 상세 기록·첫 페이지 비교표·활성 TODO·인계의 현재 단계를 함께 갱신한 후 다음 묶음으로 진행한다. 일부 조건 통과를 업무 전체 PASS로 승격하지 않는다.

상세 기록은 목적, 서버·역할·품목·조작 순서, 전/예상/후/후속/취소 수량, A/B 차이, 판정 이유, 직원 영향, 정확한 근거 경로, 미확인 조건의 여덟 항목을 갖춘다. 실제 직원 정보가 포함된 원문·화면과 짝지은 이미지 페이지는 ignored 로컬 runtime에 둔다. 커밋할 설명은 QA 역할과 품목코드 중심으로 정제한다.

첫 페이지에는 병합 판단(가능/수정 필요/판단 보류), 범위, 필수 미확인, 직원 영향과 우선순위를 적는다. 업무별 표는 main 결과/후보 결과/차이·영향/판정/상세 링크를 나란히 보여준다.

각 사례에는 목적, URL·역할·품목코드/품명·메뉴·클릭/입력 순서, 단계별 기대값, A/B 전후 수량·예약·원건 잔량·완료·취소, 차이의 이유, 짝지은 화면·원본·거래·자동검사 근거, 실패·미실행·한계를 적는다. 판정은 동일 정상/승인된 차이/회귀 발견/기존 문제/미확인. 일부 조건 검사로 전체 PASS를 만들지 않는다.

기술 부록에는 코드/DB 해시·버전·시각·로그를 모은다. 개인정보를 담은 화면·DB·원문은 ignored runtime에만 보관하며 저장소 문서는 정제한다.

## CP4 — 최종 판단

일반 품목 목록·검색·상세·내역을 준비 호출 후 각 30회, A/B 순서 교대로 측정한다. p95가 20%와 100ms 모두 증가한 경로만 조사한다. 무거운 조회의 수용된 목표와 동시30명 전체 행렬은 반복하지 않는다.

관련 자동 검사·migration 기존 행/컬럼 보존·타입·정적 검사·production 빌드·승인 번들 한도 및 최종 후보 HEAD CI를 확인한다. 유효한 근거는 소스·입력 연결로 재사용한다. main이 전진하면 후보로 결합하고 영향받은 조건만 갱신한다.

승인 밖 결재, 위치·수량·예약 불일치, 중복·부분 반영, 허용하지 않은 DB 변경, 필수 검증 누락이 없어야 병합 가능이다. 두 서버·재현 자료와 개발 DB 초기화/복원 방법을 남긴다. 운영의 새 거래를 오래된 백업으로 덮어쓰지 않는다.
