## 결과

### 새 브라우저 검증

정상 API로 준비한 자료와 직접 UI 조작을 구분해 `_attic/runtime/work-reservations/cp9-qa/ui-observations.json` 및 화면 증거에 기록했다. 선택 원자 조건과 원장 assertion의 연결은 `cp9-expectations-review.md`에 있다. 전체 원장 판정을 갱신하거나 전체 시나리오가 새로 통과했다고 간주하지 않는다.

- 기본 BOM 저장·수량 수정, 미저장 입력 유지, 두 사용자 재고 경합, 부족 저장 422와 이전 예약 보존, 창고 가져오기 왕복을 확인했다.
- 대시보드의 실재고·작업 예약·승인 예약·출하 예약·가용량·위치 이동·생산 예정을 대조했다. 입고·생산 예정은 가용량에 더하지 않는다.
- 기본 BOM의 즉시 생산과 본인 거래 취소, 창고 요청의 승인 전 물리 불변·예약 이관·승인 후 이동·원래 요청자의 취소를 확인했다. 별도 요청의 반려 사유와 승인 예약 해제를 확인했다.
- 관리자 취소 사유와 오래된 revision의 409, 다른 작업자 화면의 취소 반영, 일반 직원의 관리자 직접 진입 제한, 재시작 후 재인증을 확인했다.

- 같은 위치의 출하 예약 취소가 작업 예약을 해제하지 않는 것을 정상 API 취소 후 UI에서 확인했다. 출하 픽업은 실행하지 않았다.

### 발견해 수정한 동작

1. 예약 후 대시보드 행·상세와 KPI 상태가 달랐다. 모두 가용량으로 상태를 판단하도록 맞췄다. RED 3건 재현 후 관련 41건을 통과했고 PC·모바일에서 다시 확인했다.
2. 성공 처리 중 자기 예약 갱신 순간에 부족 경고가 나타났다. 제출·저장 대기 중 경고 표시만 억제하고 실제 검증과 버튼 차단은 유지했다. RED 4건 재현 후 관련 49건을 통과했다.
3. 창고 승인 거래의 원래 요청자가 본인 취소를 거절당했다. 연결 배치의 요청자를 우선 확인하고, 배치 없는 직접 작업만 실행자를 사용하도록 보완했다. 관련 93건 및 깨끗한 통합 후보 회귀 11건을 통과했다. 브라우저에서 기존 403을 재현한 같은 거래를 정상 취소해 복원했다. 동명이인·권한 회수·혼합 요청자·중복 역전 제한도 검토했다.

PA/PF 품목이 목록에는 있으나 KPI에 집계되지 않는 것은 기존 메인의 명시 정책임을 코드와 기존 테스트로 확인했으며 변경하지 않았다.

### 검증 재사용과 한계

CP7의 예약 lifecycle·소비자·SQLite·PostgreSQL 검사 중 소스와 입력 계약이 유지되는 결과를 재사용한다. 이번 실행에서는 실제 PostgreSQL 동시 경합, 전체 legacy/backfill 조합, 모든 관리자 폼, 동일 직원의 다중 탭 테마 동기화, 모든 실패 주입을 새로 브라우저 검수하지 않았다. 동결된 주간보고·모바일 하단 탭·출하 최종 카드 디자인은 수정하지 않았다. 서버 재시작 중 오류와 처리 중 상태는 관찰했지만 이를 통제된 네트워크 실패 주입 검사로 간주하지 않는다.

최종 후보는 새 메인 `1f56e0b5dceb9f9b258e96aebe5ae97d5b2a6594`를 기준으로 구성했다. 같은 시각에 커밋된 관리자 개선을 보존하고 관련 16파일 215개 검사와 기본 Turbopack 생산 빌드·TypeScript를 통과했다. 번들은 메인 3,442,280바이트에서 기능 포함 3,492,131바이트로 49,851바이트(+1.448%) 늘었다. 실측에 맞춰 기본 예산을 3.35MB로 조정하며 한도 초과 실패 검사와 강제 한도 옵션을 유지한다.

QA의 생산·승인 거래는 정상 취소해 역거래를 보존했다. 합성 draft·출하 예약은 정상 API로 해제했고, 모든 물리·pending 셀과 기존 승인 대기·출하 할당이 검증 전 기준과 동일했다. 임시 승인 계정만 비활성화하고 역할을 회수한다. 원본 DB 스키마 갱신 전 보호 백업은 `C:/ERP/_attic/runtime/work-reservations/cp9-original-schema-20261021-080611/mes-before-schema.db`다.
