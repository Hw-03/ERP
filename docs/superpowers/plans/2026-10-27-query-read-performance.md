# 품목·입출고 조회 지연 개선

**GOAL:** 품목·입출고 조회 지연의 원인을 측정으로 확인하고, 조회 결과의 정확성을 유지하면서 일반 조회 p95 2초·혼잡 조회 p95 5초 이내를 달성한다.

## 범위와 확인된 원인

- 직원 환경의 2026-10-26 10:22 로그에서 품목 23.891초, 입출고 내역 19.704초를 확인했다. 같은 시간 다른 조회도 느렸으므로 단독 조회와 동시 부하를 구분한다.
- 품목 작업 현황은 열린 작업의 증거뿐 아니라 종료된 과거 품목 요청까지 불러왔다. 열린 배치에 연결된 증거는 모든 상태를 유지하고, 별도 품목 요청은 요청·해당 라인이 열린 것만 가져오도록 제한했다(`backend/app/services/work_reservation_queries.py:269`).
- 이력은 페이지 선택 전에 전체 원장을 로딩·그룹화했다. 작업 ID가 있는 범위는 DB에서 제출/작업별 앵커를 먼저 선택하고 완결된 묶음을 로딩한다. 작업 ID가 없는 과거 불량 lifecycle, 달력, 작업만 있는 품목 이력은 기존 그룹 규칙을 유지한다(`backend/app/routers/inventory/transactions.py:473`).
- 화면의 수동 history fetch는 React Query의 active observer가 아니므로 provider의 invalidation 직렬화만으로 보호되지 않는다. 같은 조건의 조회 진행 중 revision은 하나로 합치고, 완료한 결과를 표시한 뒤 최신 revision으로 즉시 다시 읽는다(`frontend/app/mes/_components/_hooks/useHistoryGroups.ts:139`).
- 동시 동일 조회의 계산 중복은 TTL 없는 진행 중 요청 공유로 줄였다. DB 연결 대상·revision·조회 함수·전체 조건이 같은 경우만 공유하고 성공/실패 직후 제거한다. 완료 결과를 저장하는 캐시는 만들지 않는다. 혼합 부하의 경쟁 원인인 생산 가능 수량에도 같은 정책을 적용했다(`backend/app/services/read_singleflight.py:22`).

## 실행과 안전장치

- 활성 DB는 SQLite URI `mode=ro`로 열고 backup API로 별도 스냅샷을 만든다. 부하는 외부 URL 대신 ASGI 내부 호출과 읽기 전용 연결로 실행한다. 앱 lifespan과 직원 서버는 시작·중지하지 않는다.
- 기존 사용자 변경, 동결된 주간보고·모바일 탭·출하 카드 크기, 공개 API 응답 형태는 유지한다. 브랜치 생성·전환, 커밋·푸시, 직원 환경 배포는 하지 않는다.
- `QUERY_READ_DIAGNOSTICS=1`을 실행 환경에 지정하면 두 조회의 `evt=read_query_profile`을 남긴다. 기본은 꺼짐이다. request ID, 응답 시작까지의 시간, DB dependency 진입/첫 SQL 시각, cursor 실행 횟수·합계만 기록한다. 검색어·SQL·파라미터·응답 본문은 남기지 않는다.
- dependency 진입 시간은 스케줄링 등을 포함한 관측값이며 순수 queue wait가 아니다. SQL 합계는 cursor 실행만 포함하고 결과 fetch/ORM 변환·응답 직렬화는 포함하지 않는다. 응답 시작은 전송 완료·화면 표시 완료가 아니다. 기존 history DEBUG 단계 계측과 cProfile을 함께 사용한다.

## 검증 절차

1. 회귀 테스트가 기존 비용/재조회 취소를 재현하는지 먼저 확인하고 최소 수정한다.
2. 같은 스냅샷과 고정된 이전 앱 소스로 변경 전후를 측정한다. 도구는 `backend/scripts/benchmark_query_reads.py`이며 `--requests 100 --concurrency 1 5 10 20`으로 조건별 표본을 얻는다. 품목·이력·생산 가능 수량 단독 및 혼합 부하를 구분한다.
3. p50/p95/max, 오류·취소, 응답 의미 해시, 처리량과 프로세스 CPU를 보존한다. p95는 nearest-rank이며 warmup은 제외한다. 인프로세스 측정은 클라이언트 JSON 검증 비용도 포함하고 실제 네트워크·직원 PC 렌더링은 포함하지 않는다.
4. 이력의 같은 시각 커서, 검색한 구성품의 전체 묶음, 취소·실사·과거 이력, 페이지 중복/누락과 요청순 잔고를 검증한다. 품목 예약·불량·승인 회귀와 화면 revision burst/필터 변경/추가 페이지 깊이를 검증한다.
5. 실제 화면의 품목 검색·이력 첫 페이지/추가 페이지/최신 갱신을 확인하고 증거를 기록한다. 일반 p95 ≤ 2초·혼잡 p95 ≤ 5초와 오류·취소 0을 최종 판정한다.

실행 시점의 도메인 수량은 `python _attic/backend-scripts/facts.py`로 확인한다. 개인정보를 포함할 수 있는 스냅샷·프로파일·응답 비교 원자료는 Git에서 제외된 `_attic/runtime/query-performance/`에만 둔다.

### 최종 성능 결과

같은 직원 DB 스냅샷, 고정한 변경 전후 소스, 동시성 1·5·10·20, 조건별 100회로 측정했다. 단일 조회 세 종류와 혼합 부하를 합친 **16개 조건 모두 일반 p95 2초·혼잡 p95 5초 기준을 통과**했다. 전후 총 3,200회는 모두 HTTP 200이며 오류·취소가 없다. 전 조건의 응답 원본 SHA256·의미 SHA256·응답 크기가 동일하고 스냅샷도 변하지 않았다.

### 최종 회귀 검증

- 관련 백엔드 pytest **281개 통과**. 읽기 세션·감사 기록, 예약 집계, 품목 불량, 그룹 페이지·달력·실사·요청자 필터·요청순 잔고·요약·측정 도구를 포함한다.
- 관련 프런트 Vitest **50개 통과**, 수정한 hook·테스트의 ESLint 경고 0.
- 전체 공개 OpenAPI 문서 SHA256이 변경 전후 동일하다. 독립 스펙·품질 리뷰에서 중요 결함이 발견되지 않았다. `git diff --check` 통과.
- 합성 QA 환경에서 로그인·품목 검색·이력 첫/추가 페이지·검색 해제·실시간 갱신 후 로딩 깊이 보존을 실제 UI로 확인했다. QA 소스 overlay가 최종 소스와 일치하며 소유한 QA 프로세스만 종료했다. 기존 개발·직원 서버의 포트와 PID는 유지했다.
- 기존 과거 이력 fallback과 전체 원장을 검증하는 요청순 잔고 계산은 유지한다. PostgreSQL 실서버 부하와 직원 환경 배포 후 체감 속도는 이번 검증에 포함하지 않는다.
