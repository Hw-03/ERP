## 검사 범위와 한계

전체 기대값·전체 업무 테스트·부하 행렬을 다시 실행하지 않았다. 이전 결과는 해당 과거 소스에 대한 기록으로 유지하며 이번 통합판 전체 PASS로 승격하지 않는다. CP3~CP5 결과는 실제 실행 후 이어서 기록한다.

staged smart 계획은 전체 과거 브랜치의 도구·CI 유입 때문에 전체 게이트를 제시했다. 승인한 계획대로 새 충돌과 직접 소비자 검사·타입·정적 검사·사본 migration 보존 검사를 선택했다. smart 계획만 읽었으며 전체 게이트를 실행하지 않았다.

배포 기준판의 번들 검사 기본 한도는 2026-10-14 실사 통합에서 3.20MiB로 바뀌어 있다. 이번 승인 계획의 3.00MiB와 다르므로 CP4에서 명시한 3.00MiB 결과와 현재 기본 한도 결과를 각각 기록한다. 기준을 조용히 바꿔 통과로 처리하지 않는다.

충돌 해결 코드의 공백 검사는 두 번째 부모 대비 엄격 검사로 확인한다. 전체 유입 diff의 과거 원문 CRLF 로그와 이미 있던 도구 파일의 마지막 빈 줄은 해시 보존을 위해 고치지 않았다. CRLF를 인정하는 검사와 새 통합 변경 검사를 구분한다.

모든 단계에서 무관 품목·창고·다른 부서 수량/예약은 동일했다. 최종 수량/예약 전체는 최초와 같고, 기존 출하 allocation 행도 모두 불변이다. 요청 취소 뒤 준비 목록에서 QA 요청이 빠지는 것까지 확인했다. 관련 근거는 `pc-shipping-requested`~`mobile-shipping02-request-cancel` 스냅샷/diff와 해당 QA 요청 이력이다. 물리 수량과 별도의 `shipping_allocations` 상태를 따로 대조했다. 요청 중 버튼은 비활성화됐으며 강제 중복 요청/변경 초안 경합은 이번 브라우저 실행에서 아직 확인하지 않았다.

## CP3 부서 격리·폐기·재작업과 복귀 후 사용

실제 조립품 3개를 부서 불량으로 격리한 뒤 PC 부분 복귀 1, 폐기 1, 재작업 1을 순서대로 처리했다. 격리는 정상 167→164/격리 0→3, 부분 복귀는 정상 165/격리 2가 됐다. 폐기는 격리 2→1과 전체 수량 167→166만 바뀌었다. 재작업에서는 부모 격리 1→0/전체 166→165, 실제 BOM 부품의 조립 격리 0→1/전체 500→501이 됐다. 부품 창고 480과 다른 위치는 그대로였다.

재작업 묶음 취소는 부모와 자식의 위 변동을 함께 복원했고, 폐기 단건 취소는 부모 격리와 전체 수량을 각각 1 복원했다. 모바일로 남은 격리 2를 정상 복귀한 뒤 같은 조립 재고 2를 일반 부서 출고하고 취소했다. 기존 부서 담당 역할에 따른 자동 승인이 화면과 결과에서 일치했고, 출고 상세는 조립 167→165를 표시했다. 최종 전체 위치 수량/예약은 최초와 같다.

근거: `pc-dept-quarantine`, `pc-dept-restore-partial`, `pc-dept-scrap`, `pc-dept-rework`, 각각의 취소, `mobile-dept-restore-full`, `mobile-general-after-restore`, `mobile-general-cancel` 및 단계별 diff. 새 원건 외 기존 불량을 처리하지 않았다. 업체 반품과 보고서의 재작업 두 열 표시는 아직 별도 확인 대상이다.

## CP3 튜브 입고·반품·후속 생산·역순 취소

기존 튜브 담당자로 로그인해 전용 원자재 입고 화면에서 실제 공급업체와 전극 2개를 선택했다. 튜브 정상 166→168, 전체 166→168만 증가했고 창고는 그대로였다. 새 원건으로 2개를 격리한 뒤 허용된 같은 업체로 반품했다. 격리는 정상 168→166/격리 0→2, 반품은 격리 2→0/전체 168→166이었다. 반품 취소는 같은 튜브 격리 위치로 2개를 복원했고, 격리 취소는 정상 168/격리 0으로 돌아왔다.

이어 실제 튜브 BOM으로 완제품 1개를 생산했다. 부모 튜브 정상 1→2, 전극 168→166, 나머지 8종도 화면의 BOM 수량대로 튜브 정상 위치에서만 차감됐다. 기존 불량·구형 재고와 창고는 쓰지 않았다. 생산 10거래 묶음 취소 후 입고 취소를 수행해 전체 품목·위치 수량과 예약이 최초와 일치했다. 기존 운영 초안이나 불량 원건은 처리하지 않았다.

근거: `pc-tube-receipt`~`pc-tube-receipt-cancel` 및 단계별 diff. `initial--pc-tube-receipt-cancel.diff.json`에 최종 전체 수량/예약 복원을 기록했다. 업무 메모 검색에서 격리·복귀 항목이 누락되는 현상을 관찰했으며, 검색 결함의 범위/기준판 여부는 CP4에서 별도로 조사한다.

## CP4 사유 메모 검색 국소 수정

격리/복귀 메모가 상세에는 표시되는데 내역 검색에서 빠졌다. 실제 원건의 `reason_memo` 값과 검색 조건을 대조해 공용 `_history_search_filter`가 이 필드를 누락한 것을 확인했다. 배포 기준판에도 동일한 누락이 있었다. 검색 필드에 `TransactionLog.reason_memo` 하나만 추가했고 재고/API 쓰기/스키마는 변경하지 않았다.

`reason-search-red.log`에서 격리·복귀 두 조건의 빈 결과 실패를 확인했다. 수정 후 목록·묶음·집계와 기존 내보내기/달력 검사 54건을 통과했다(`reason-search-green.log`). QA 서버의 백엔드 해당 파일만 갱신해 실제 브라우저에서 `QA-20261015-DEPT-RESTORE-PARTIAL` 원건 1건을 찾았고, API로 격리/복귀 각 메모를 다시 대조했다(`search-patch-api.json`). 프론트 소스와 빌드는 그대로이며 전체 업무 검사를 반복하지 않았다.

## CP4 빌드 중간 결과

- 동일 Node 20.20.2, 동일 lockfile과 배포판의 Turbopack으로 두 판의 QA production 빌드 성공. API 주소는 격리 백엔드 8035다.
- 기준판: 3,297,988 bytes(3.145MiB), 통합판: 3,337,975 bytes(3.183MiB). 증가 39,987 bytes, 약 1.21%.
- 승인 계획의 3.00MiB 한도는 **미충족**이다. 통합판은 192,247 bytes 초과한다. 이미 배포판도 같은 한도를 초과하며 현행 배포 코드의 3.20MiB 검사는 두 판 모두 통과했다. 한도 파일은 변경하지 않았다.
- 실제 사용한 빌드: `baseline/build-qa.log`, `integrated/build-qa-final.log`. 초기에 중지한 webpack 시도와 외부 의존성 junction 때문에 실패한 Turbopack 시도는 실패 원문으로 보존하고 성공 근거로 사용하지 않는다. QA 폴더 안에 의존성을 복사해 최종 빌드했다.
- production 서버 시작 전후 업무 행이 같은지 확인했다. 서버 시작에 migration/seed는 실행하지 않았다. 이후 성능 비교 결과는 아래와 같으며 사용자 전환 도우미 검증은 진행 중이다.

## CP4 일반 조회 성능 비교

같은 직원 원형 자료의 기준판 사본과 명시적으로 migration한 통합판 사본을 사용했다. 업무 QA 사본은 따로 보존했다. Node/Python과 서버 설정을 같게 하고 기준판→통합판, 통합판→기준판 순서로 각 준비 호출 후 30회를 측정했다. 아래는 각 버전 60회의 합산 p95이며 원문은 `performance/measurements.json`, `history-populated.json`에 있다.

| 일반 조회 | 기준판 p95 | 통합판 p95 | 변화 |
|---|---:|---:|---:|
| 품목 목록 100개 | 51.46ms | 50.60ms | -0.86ms |
| 품목 코드 검색 | 38.43ms | 35.02ms | -3.42ms |
| 품목 상세 | 27.77ms | 19.48ms | -8.29ms |
| 품목 위치 재고 | 15.13ms | 16.57ms | +1.44ms |
| 실제 거래 8건의 품목 내역 | 50.15ms | 73.69ms | +23.54ms |
| 내역 목록 100묶음 | 2,135.48ms | 750.69ms | -1,384.79ms |

20%와 100ms를 동시에 초과해 느려진 경로는 없다. 품목 내역은 비율로 약 47% 늘었지만 절대 증가가 약 24ms이므로 지정한 회귀 기준에는 해당하지 않는다. 처음 선택한 원자재의 과거 내역이 빈 배열인 것을 확인해 그 측정은 실자료 내역 근거에서 제외하고 실제 거래 8건인 품목만 추가 측정했다. 다른 조회를 재실행하지 않았다. 최초 호출과 각 순서의 p95도 원문에 따로 남겼다.

품목 목록/검색/상세/위치의 기존 응답 필드는 동일하다. 내역의 거래 ID·순서·수량·위치·증감도 동일하며, 통합판은 위치별 전후 수량을 추가한다. 전체 목록에서 달라진 기존 필드 두 개는 한 AS 사용의 승인자/승인 시각이다. 실제 요청의 AS·연구 승인자와 시각에 통합판이 일치함을 확인했다(`approval-field-difference.json`). 조회 범위를 줄여 성능을 맞추지 않았다. 이는 단일 사용자 일반 조회 비교이며 무거운 정합성/동시 30명 전체 부하 결과로 확대하지 않는다.

## CP5 전환 도우미 준비

`scripts/dev/mes_integration_review.py`는 현재 워크트리 코드를 checkout하지 않고, 보존된 두 코드/production 빌드/DB 조합만 선택한다. manifest 해시와 코드·의존성·빌드·Node·설정·초기 DB 해시, 스키마, 미커밋 변경, 프로세스 소유권을 검사한다. 각 버전의 검토 DB를 따로 유지하며 초기화 전 사용자가 만든 검토 자료를 백업한다. 운영 포트나 원본 DB로 바꾸는 설정을 거부한다.

도우미의 경로 이탈·junction·코드/manifest/seed/config 변경·추가 소스·긴 Windows 경로·미커밋 변경·외부 프로세스 소유권 오류·정지 중 DB/WAL 변경·초기화 전 백업 보존 등 국소 14조건을 통과했다(`review-helper-final-v4.log`). 준비 중 Windows의 열린 SQLite 연결 때문에 원자적 교체가 거부되는 문제를 확인해 명시적 연결 종료로 보완했다. 긴 의존성 경로는 Windows extended path로 읽으며 가드를 제거하지 않았다. 실제 기준판→통합판→기준판 전환은 아직 별도 실행할 단계다.

## CP3 두 탭의 중복 제출·완료된 초안 거부

최종 통합판의 별도 `integrated/review.db`에서 창고 보정 출고 1을 새 QA 초안으로 저장하고 같은 초안을 두 브라우저 탭에 열었다. 초안 저장만으로 수량/예약은 바뀌지 않았다. 첫 탭 확정 버튼을 더블 클릭했을 때 완료 작업과 출고 거래는 각각 하나만 생겼다. 창고 90→89, 전체 362→361이고 고압 272 및 무관 재고/예약은 불변이었다.

두 번째 탭은 이전 최종 확인 내용을 그대로 갖고 있었다. 재제출하자 `임시저장 작업을 찾을 수 없습니다` 사유의 제출 실패가 표시됐고 DB는 첫 완료 직후와 같았다. 원작업을 브라우저 내역에서 취소해 창고 90/전체 362로 복원했다. 최종 전체 위치 수량/예약과 모든 기존 업무 행은 시작값과 같으며 QA 원작업 -1/연결 취소 +1 두 거래만 남았다. 이는 두 탭의 순차 재제출과 더블 클릭 결과이며 모든 동시 부하의 보장으로 확대하지 않는다.

근거는 `integrated/review-stock-audit/`의 `initial`, `draft-saved`, `double-click-completed`, `stale-draft-rejected`, `cancel-completed` 및 diff, `review-double-submit-result.json`, `stale-draft-rejected.jpg/.txt`, `cp5-business-backend.log`다. 동일 초안 실제 동시 제출과 완료 후 오래된 상태의 되돌리기, 출하 준비/픽업/취소 중복 실행은 별도 합성 SQLite 검사 6건도 통과했다(`duplicate-stale-local.log`). 이 합성 검사를 직원 자료 브라우저 실행으로 표시하지 않는다.
