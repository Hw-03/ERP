## 새 검증 근거

- 배포판 로그인·목록·상세·내역 브라우저 조회: `baseline/cp1-result.json`. 업무 제출 검증을 뜻하지 않는다.
- 관련 백엔드 8개 파일: `backend-merge-targeted.log`. 부서·불량·작업 상세·통합 목록/달력·실사 내역을 검사했다.
- migration·보존 도구·내역/정합성 조회 관련 검사: `migration-merge-targeted.log`. 기존 쿼리 수 단언 3건이 배포판의 실사 모드 조회 3회를 누락해서 실패했다. 추가 조회의 테이블/개수와 기존 조회 18회를 따로 확인하도록 조정하고 `integrity-width-recheck.log`에서 해당 3건을 통과했다. PostgreSQL 전용 2건은 환경 부재로 미실행이다.
- 화면 11개 파일의 최초 통합 검사: `frontend-merge-targeted.log`. 충돌로 중복된 선언, 최신 복귀 사유 폼과 작업 라벨에 맞지 않는 옛 fixture를 바로잡았다. 실패 파일과 추가 재고 풀 경로는 `frontend-merge-recheck.log`, 마지막 실시간 갱신의 응답 반영 대기는 `defect-refresh-recheck.log`에서 확인했다.
- 새 재고 풀 뒤로가기 실패: `pool-history-red.log`. 수정 후 원건/재고 풀 두 조건은 `frontend-merge-recheck.log`에서 통과했다.
- 로그인/탭 관련 5개 파일: `login-merge-targeted.log`. 최신 배포판의 숨김·inert 초안 유지와 이중 Provider fixture를 바로잡고 실패 2조건만 `login-merge-recheck.log`에서 확인했다. 선택하지 않은 조건은 새 실행의 PASS로 세지 않는다.
- 프론트 타입: `typecheck-merge-recheck.log`, 충돌 관련 ESLint: `conflict-eslint.log`.
- 실제 자료 migration: `integrated/migration-preservation.json`. 기존 83개 업무 테이블 값 전부 보존, 신규 nullable 3필드 과거 행 모두 NULL, SQLite/FK/스키마 검사 통과, 원형 SHA256 불변. 이는 모든 업무 정합성의 통과 선언이 아니다.

## 검사 범위와 한계

전체 기대값·전체 업무 테스트·부하 행렬을 다시 실행하지 않았다. 이전 결과는 해당 과거 소스에 대한 기록으로 유지하며 이번 통합판 전체 PASS로 승격하지 않는다. CP3~CP5 결과는 실제 실행 후 이어서 기록한다.

staged smart 계획은 전체 과거 브랜치의 도구·CI 유입 때문에 전체 게이트를 제시했다. 승인한 계획대로 새 충돌과 직접 소비자 검사·타입·정적 검사·사본 migration 보존 검사를 선택했다. smart 계획만 읽었으며 전체 게이트를 실행하지 않았다.

배포 기준판의 번들 검사 기본 한도는 2026-10-14 실사 통합에서 3.20MiB로 바뀌어 있다. 이번 승인 계획의 3.00MiB와 다르므로 CP4에서 명시한 3.00MiB 결과와 현재 기본 한도 결과를 각각 기록한다. 기준을 조용히 바꿔 통과로 처리하지 않는다.

충돌 해결 코드의 공백 검사는 두 번째 부모 대비 엄격 검사로 확인한다. 전체 유입 diff의 과거 원문 CRLF 로그와 이미 있던 도구 파일의 마지막 빈 줄은 해시 보존을 위해 고치지 않았다. CRLF를 인정하는 검사와 새 통합 변경 검사를 구분한다.

## CP3 생산·분해와 모바일 묶음 취소

실제 조립 BOM의 부모 재고 167, 부품 재고 20으로 시작했다. 부품 창고 재고는 별도로 480이었다. 생산 수량 21은 부족 안내와 제출 차단을 확인했고 전체 재고·예약과 작업 건수가 그대로였다. 수량 2의 생산은 조립 부모 167→169, 조립 부품 20→18만 바꿨다. 이어 분해 2는 조립 부모 169→167, 부품 18→20으로 반영됐다.

모바일 내역에서 분해→생산 순서로 취소했다. 각 화면은 부모·부품 2거래를 함께 취소한다고 안내했고 실제 DB도 두 거래를 모두 같은 조립 위치에서 되돌렸다. 창고 부품 480과 무관 품목·위치·예약은 동일했다. 취소 후 재취소 버튼이 사라지고 원작업/취소가 각각 내역에 표시됐다. 근거: `pc-production-blocked`, `pc-production-01`, `pc-disassemble-01`, `mobile-disassemble-cancel`, `mobile-production-cancel` 스냅샷과 단계별 diff.

## CP3 세 분류 격리·부분/전량/모바일 일괄 복귀·후속 사용

PC에서 같은 실제 원자재의 창고 재고를 새 사유 3건으로 격리했다. 불량 3, B급 2, 구형 2이며 창고 정상 90→83, 창고 격리 0→7, 총량 362는 유지됐다. 고압과 다른 품목은 동일했다.

- 불량 3 중 1을 정상 복귀: 창고 83→84, 격리 7→6, 해당 원건 잔량 2.
- 구형 2 전량 정상 복귀: 창고 84→86, 격리 6→4, 해당 원건 잔량 0.
- B급 원건을 불량으로 분류 변경: 수량·예약 변화 없음.
- 모바일에서 새 불량 두 원건을 선택해 남은 2+2를 일괄 복귀: 창고 86→90, 격리 4→0, 세 원건 잔량 모두 0.
- 모바일 연구 사용으로 복귀 재고 2를 실제 출고: 기존 담당 역할로 자동 승인, 창고 90→88, 총량 362→360, 고압 재고와 예약은 동일.
- 모바일 내역에서 연구 사용 취소: 창고 88→90, 총량 360→362로 복원.

근거: `pc-quarantine-01`부터 `mobile-research-cancel`까지의 스냅샷·diff. 마지막 `initial--mobile-production-cancel.diff.json`은 모든 품목·위치의 수량/예약이 최초와 일치함을 확인한다. 추가된 격리 위치의 0행과 업무 이력은 남아 있으며 DB 전체가 원형과 같다는 의미는 아니다. 부서 격리와 폐기·재작업·반품, 최초 분류 통계 대조는 아직 미실행이다.

## CP4 빌드 중간 결과

- 동일 Node 20.20.2, 동일 lockfile과 배포판의 Turbopack으로 두 판의 QA production 빌드 성공. API 주소는 격리 백엔드 8035다.
- 기준판: 3,297,988 bytes(3.145MiB), 통합판: 3,337,975 bytes(3.183MiB). 증가 39,987 bytes, 약 1.21%.
- 승인 계획의 3.00MiB 한도는 **미충족**이다. 통합판은 192,247 bytes 초과한다. 이미 배포판도 같은 한도를 초과하며 현행 배포 코드의 3.20MiB 검사는 두 판 모두 통과했다. 한도 파일은 변경하지 않았다.
- 실제 사용한 빌드: `baseline/build-qa.log`, `integrated/build-qa-final.log`. 초기에 중지한 webpack 시도와 외부 의존성 junction 때문에 실패한 Turbopack 시도는 실패 원문으로 보존하고 성공 근거로 사용하지 않는다. QA 폴더 안에 의존성을 복사해 최종 빌드했다.
- production 서버 시작 전후 업무 행이 같은지 확인했다. 서버 시작에 migration/seed는 실행하지 않았다. 성능 비교와 사용자 전환 도우미 검증은 남아 있다.
