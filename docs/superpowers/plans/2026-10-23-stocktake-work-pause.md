## 합의한 동작

- 실제 생산·이동 도중 보관한 작업이다. 재고조사와 작업 진행량의 정리는 작업자가 담당한다. 기존 작업 수량을 보존하고 필요하면 평소처럼 수정한다. 부분 진행량을 자동 추정하지 않는다.
- 기존 draft 상태와 내용을 보존한다. 일시중지 중 펼치기·상세 조회·삭제는 가능하지만 저장으로 재예약하거나 제출할 수 없다.
- 전체 회차 완료 대신 해당 작업의 모든 재고 영향 셀(투입 자재, 결과품, 이동 양끝)의 최신 계수 APPLIED를 확인한다. 계수 확정만으로는 재개하지 않는다.
- 관련 조사 반영 후 행의 ‘이어서 작업’을 누르면 기존 내용·수량으로 예약을 복구해 편집기를 연다. 별도 남은 수량 확인 체크와 재개 버튼은 없다. 재고 부족·버전 충돌 시 원본을 보존하고 진입을 차단한다.
- 조사 중 신규 저장은 관련 셀 미반영 시 예약 없이 일시중지로 저장한다. 즉시 제출은 같은 조건을 서버에서 검사한다.
- 재계수 시작 시 해당 셀과 관련된 draft를 다시 멈춘다. 부분 종료만으로 미반영 작업을 풀지 않는다. 다음 회차에서는 판단 회차를 갱신한다.
- 대상이 누락된 셀은 완료로 간주하지 않고 대상 확인 필요로 표시한다. 기존 조사 대상 정책을 자동 확대하지 않는다.
- 승인대기·이미 일부완료·출하 예약은 작업 중 draft와 다른 흐름이므로 기존 동작을 유지한다.

## 공통 계약

- 신규 `StocktakeWorkPause` 테이블: `(kind, work_id)` PK, `round_id`, `token`, `required_cells` JSON, `paused_at`. kind는 `io` 또는 `stock_request`. 테이블에는 현재 일시중지만 보관한다.
- 응답 `stocktake_pause`: null 또는 `{token, round_id, state: blocked|ready, paused_at, pending_target_count, missing_target_count}`. 상태는 현재 최신 계수와 gate에서 계산한다.
- IO 기존 draft 저장과 구형 StockRequest draft 저장에 선택적 `stocktake_resume_token`을 추가한다. UI의 이어서 작업·일반 저장/제출에서 재개 가능한 작업의 token을 자동 전달한다. 서버의 token·최신 반영 검사와 IO expected_revision 검사는 유지한다.
- 서버는 재개 시 원래 영향 셀과 변경 후 영향 셀을 모두 잠금·검증한 뒤 저장과 예약을 원자적으로 수행한다.
- 공통 서비스는 `pause_payload(db, kind, work_id)`, `ensure_work_save(db, kind, work_id, cells, resume_token=None)` 등 내부 함수로 상태 처리를 모은다. 구현 전에 백엔드 담당자가 구체 함수 계약을 부모에게 전달한다.

## 작업 및 검증

1. 모델·마이그레이션·DTO와 실패하는 상태 전이 테스트를 추가한다. 기존 실제 DB는 건드리지 않고 테스트 DB에서 검증한다.
2. 회차 시작/편입/재계수의 원자적 일시중지 및 IO 저장·제출·backfill 우회 방지를 구현한다. 여러 draft의 품목 합집합을 한 번에 prepare한다.
3. 구형 StockRequest DRAFT의 영향 품목(분해·재작업 자식 포함), 저장·제출 제한, 공통 응답을 연결한다.
4. PC/모바일 행 상태와 한 번의 이어서 작업, 오래 열린 편집기 보호를 구현한다. 구형 draft도 별도 확인 체크 없이 기존 수량으로 제출까지 이어간다.
5. 집중 회귀 검사: 내용 보존·예약해제, 일부/전체 관련 셀 APPLIED, 무관한 미완료 대상, 재계수, 부분 종료, 신규 회차, 수량 수정, 부족재고 rollback, 구 버전/token, 직접 저장/제출 우회, 화면 입력 보존.
6. 독립 명세 검토와 코드 검토 후 필요한 회귀만 실행한다. 현재 세션과 무관한 변경은 보존한다. 커밋·푸시·브랜치 전환은 하지 않는다.

## 구현·검증 기록 — 2026-10-23

- 질문을 구현 지시로 오해한 뒤 사용자의 명시적 요청에 따라 이번 변경만 별도 `stocktake-work-pause/ERP` 워크트리로 이전했다. 파일 바이트를 대조했고 원래 작업 폴더의 다른 변경은 보존했다.
- 위 상태 전이와 PC·모바일 재개 흐름, 구형 요청의 수량·분해 구성 수량 편집을 구현했다. 사용자 후속 요청에 따라 별도 수량 확인 체크와 긴 안내를 제거했다. 관리자 조회에도 일시중지 상태와 재개 이력을 연결했다.
- 구형 작업은 기존처럼 저장 자체로 예약을 만들지 않는다. 재개 시 실제 출발지별 남은 수량을 합산해 다른 작업·출하 예약을 제외한 가용량을 검사하고, 제출 시 기존 예약 절차를 따른다.
- 독립 명세·코드 검토에서 발견한 구형 출발지 재고 검사, 정규화 후 예약 전환의 조사 누락, 관리자 이력 계약, 변경된 자동 부서의 HTTP 재개 경로를 보완했다. 최종 재검토에서 추가 확정 P1/P2는 없었다.
- 최종 집중 백엔드 검증: 일시중지·구형 작업·재개 가용량·HTTP 경로·응답·모델·마이그레이션 테스트 75개 통과. 별도 기존 backfill·조사 흐름 회귀도 통과했다.
- 프론트엔드 관련 회귀와 타입 검사, 수정 파일 ESLint 통과. 마지막 관리자 표시 회귀 25개 통과.
- 격리 QA DB의 실제 서비스로 조사 시작과 관련 위치 반영을 실행했다. 브라우저에서는 내용 펼치기, 이어하기 비활성화, 수량 3→1 수정과 확인, 명시적 재개, 자재 예약 완료를 관찰했다. DB 재조회로 수량·예약 1, 물리재고 10 유지, 무관한 대상 미조사 및 회차 ACTIVE를 확인했다.
- 화면 증거는 `_attic/runtime/mes-browser-regression/pause-20261023-b/`에 보관한다. 이 스냅샷 이후 구형 HTTP 부서 정규화만 추가됐으며 해당 차이는 HTTP 회귀 테스트로 검증했다.
- 원본 개발·직원 DB에는 마이그레이션을 적용하지 않았다. PC 전체 화면의 수동 브라우저 검증은 수행하지 않았다. PostgreSQL의 후속 다중 연결 검증은 아래 기록을 따른다. 커밋·푸시·배포는 하지 않았다.

## PostgreSQL 후속 검증 — 2026-10-23 완료

- 사용자의 요청에 따라 원본 개발 SQLite DB를 읽기 전용으로 스냅샷하고, 현재 워크트리의 전용 PostgreSQL에 데이터 전체를 복제했다. 테이블별 행 수·내용 해시를 대조하고 새 마이그레이션은 복제본에만 적용했다. 각 시험은 baseline의 별도 TEMPLATE DB에서 실행했다.
- 실제 독립 연결로 저장/조사 시작 양방향, 중복 재개, 마지막 재고 경쟁, 재개/재계수 양방향, 마지막 반영/재개, 무관한 품목 병행, 구형 토큰 중복, 다품목 역순 동시 재개, 반영 전 거절 후 재시도 및 FK/부서 산정 잠금을 검증했다.
- 다품목 동시 재개에서 FK 참조 잠금과 조사 대상·품목 잠금의 순환으로 실제 데드락을 재현했다. `stocktake_guard.prepare_items`와 `inv_transfer.lock_items_for_department_routing`의 Item 잠금만 `FOR NO KEY UPDATE`로 맞춰 해결했다. 재고·Gate 잠금, 품목 순서, 부서 변경·삭제 보호는 유지한다.
- 수정 전 실패를 보존한 뒤 PostgreSQL 12개(경합·상태 전이 11개 + 부서 산정 잠금 1개), 직접 관련 백엔드 회귀 151개 통과. 실제 PID 잠금 대기와 무관한 품목의 선행 요청 커밋 전 완료를 확인했다. Python 구문·공백 검사 및 독립 코드 재검토 완료.
- 원본의 과거 문자열 길이·외래 참조 차이는 복제본에만 호환 처리를 해 데이터를 보존했다. 이번 동시성 결과를 기존 전체 데이터의 PostgreSQL 운영 전환 적합성으로 해석하지 않는다.
- 상세 증거는 `_attic/runtime/pause-pg-20261023/results.md`와 JUnit·실행 로그에 있다. baseline 보존과 case DB 잔존 0을 확인하고 전용 PostgreSQL만 정지했다. 스냅샷·dump·cluster 파일은 보존했다.
