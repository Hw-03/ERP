## UI 구현 계획·브라우저 검증 원칙

- 대상: 데스크톱 UI의 여백·표면·모서리·스크롤·레이아웃을 바꾸는 모든 후속 TODO.
- 구현 계획 전에는 실제 인증된 브라우저에서 해당 URL, 사용자 주석 당시의 뷰포트, 데이터·선택·스크롤 상태를 재현한다. 화면 캡처와 필요한 DOM/계산 스타일을 확인해, 표면·모서리·높이·스크롤 책임이 어느 컴포넌트에 있는지 코드와 함께 계획에 명시한다.
- 인증되지 않았거나 대상 화면 상태를 직접 재현할 수 없으면 TODO만 보완하고 구현 계획을 확정하지 않는다. 사용자가 대상 탭을 인증된 상태로 열어 둔 뒤 다시 확인해야 한다.
- 구현 뒤에는 같은 인증된 URL·뷰포트·스크롤 상태에서 수용 기준을 브라우저로 다시 검증한다. 단위 테스트는 코드 계약을, 브라우저 검증은 실제 표면·간격·모서리·상호작용을 각각 증명하며, 둘 중 하나만으로 완료를 선언하지 않는다.
- 브라우저 검증 결과는 계획·구현 결과에 URL, 뷰포트, 확인한 상태와 함께 남긴다. 검증하지 못한 상태는 통과로 표현하지 않는다.

### 4. 데스크톱 긴 목록의 하단 모서리와 작업 영역 높이를 사이드바 하단선에 맞춤

- 화면/영역:
  - 데스크톱 대시보드(`/mes?tab=dashboard`) > 자재 목록.
  - 데스크톱 입출고 내역(`/mes?tab=history`) > 거래 목록.
- 증상:
  - 두 화면 모두 목록이 길 때 상단 카드 모서리만 보이고, 현재 뷰포트의 하단에서는 목록 표면이 직선으로 잘린 듯 보여 상·하단의 모양이 연결되지 않는다.
  - 목록을 끝까지 내려야만 하단 모서리가 드러나며, 목록 카드의 실제 끝은 사이드바 하단 기준선보다 위에 남아 있다.
  - 각 탭의 목록만 다른데도 같은 하단 정렬·모서리 문제가 반복된다.
  - 입출고 내역은 외곽 상단의 곡선은 보이지만, 현재 뷰포트 하단에서는 거래 목록이 완결된 표면으로 끝나지 않아 대시보드보다 더 잘린 작업 영역처럼 보인다.
  - 사용자가 현재 입출고 내역 화면에서 거래 표의 좌·우 하단을 직접 지적했으며, 어떤 DOM 상자를 기준으로 보더라도 사람이 보는 목록 표면의 둥근 마무리가 완결되지 않은 느낌을 준다.
- 사용자 불편: 데스크톱 작업 영역의 큰 목록이 화면 끝에서 미완성 카드처럼 보이고, 좌측 사이드바와 콘텐츠의 하단 기준이 어긋나 전체 레이아웃이 어색하게 보인다. 사용자가 내부 컨테이너를 구분해야 할 정도로 표면의 하단 곡선 책임도 불분명하다.
- 확정 정책:
  - 데스크톱 대시보드와 입출고 내역의 목록 작업 영역 하단은 좌측 사이드바의 하단선과 같은 기준으로 정렬한다.
  - 긴 목록에서도 현재 화면 안에서 목록 카드의 상·하단 모서리가 하나의 완결된 표면으로 보이게 한다. 목록 끝까지 스크롤해야만 하단 모서리가 나타나는 상태는 없앤다.
  - 두 탭은 같은 하단 정렬·모서리 규칙을 사용하며, 사이드바·상단 바 자체의 크기나 디자인은 바꾸지 않는다.
  - 입출고 내역의 하단도 실제 데이터 끝을 기다리지 않고 현재 작업 영역의 끝에서 자연스럽게 마무리되어야 한다.
  - 목록 표면의 모서리는 사람이 보는 외곽 기준으로 한 번만 완결되어야 한다. 행 목록은 그 안에서만 스크롤하고, 하단 곡선·경계가 부모와 자식에서 이중이거나 어느 쪽에도 적용되지 않은 듯 보이면 안 된다.
- 구현 방향:
  - 탭 전체를 스크롤하는 현재 구조 대신, 상단 KPI/필터와 목록 카드의 높이 책임을 분리한다. 목록 카드는 탭 콘텐츠의 남은 높이를 채우고, 실제 행 목록만 카드 내부에서 스크롤되게 한다.
  - `DesktopInventoryView`와 `DesktopHistoryView`에 같은 `min-h-0`·flex 높이 전달 규칙을 적용해 마지막 카드의 하단 여백을 콘텐츠 바깥에 남기지 않는다.
  - 기존 sticky 헤더, 목록 더 보기, 필터 펼침, 우측 상세 패널, 수평/수직 스크롤 동작은 유지하며 이 변경으로 이중 스크롤바가 생기지 않게 한다.
- 수용 기준:
  - 두 화면의 긴 목록 시작 상태와 목록 하단 상태 모두에서 외곽 목록 카드의 하단 테두리·둥근 모서리가 보인다.
  - 목록 카드의 실제 하단이 데스크톱 좌측 사이드바 하단선과 같은 기준에 맞고, 임의의 큰 빈 여백 때문에 위로 떠 보이지 않는다.
  - 초기 목록·중간 스크롤·데이터 끝 어디서 보아도 입출고 거래 표의 좌·우 하단이 직선으로 잘리거나 별도 상자의 모서리와 충돌하지 않고 하나의 둥근 외곽으로 읽힌다.
  - 대시보드의 KPI·생산 가능·필터, 입출고 내역의 통계·검색·기간/필터를 사용해도 목록 영역이 남은 높이에 맞게 조정되고 행만 스크롤된다.
  - sticky 헤더, 행 선택, 더 보기, 필터 패널, 우측 상세 패널과 기존 스크롤바 조작이 정상이며 중복 세로 스크롤바가 생기지 않는다.
- 브라우저 확인 시나리오:
  - 1920×910 데스크톱에서 `/mes?tab=dashboard`를 열어 목록 맨 위와 맨 아래를 각각 확인하고, 카드의 하단 모서리와 사이드바 하단선이 모두 일관되게 보이는지 확인한다.
  - 같은 창 크기에서 `/mes?tab=history`를 열어 목록 맨 위·맨 아래, 기간·필터 패널을 각각 확인한다.
  - 실제 인증된 `/mes?tab=history` 화면에서 초기 목록·중간 스크롤·데이터 끝을 각각 확인해, 상단 곡선과 하단 마무리가 대시보드와 같은 완결감을 주는지 확인한다.
  - 대시보드에서 필터를 펼치고 품목을 선택한 뒤, 입출고 내역에서 필터·더 보기를 사용해도 목록 내부 스크롤만 변하고 카드 외곽·하단 정렬이 유지되는지 확인한다.

### 3. 우측 재고 상세 패널 탭의 상단 여백·폭과 품목 헤더 간격 정돈

- 화면/영역: 데스크톱 대시보드(`/mes?tab=dashboard`) > 자재 목록에서 품목 선택 > 우측 재고 상세 패널. 수집 기준 화면은 `전극(70kV)` 선택 상태다.
- 증상:
  - 2026-08-18 구현으로 `상세 정보`/`최근 내역` 탭은 이미 품목명·코드·상태보다 먼저 패널 최상단에 렌더된다.
  - 사용자 검토 화면에서 탭 상자가 아직 조금 낮고 가용 폭을 거의 다 써서 오른쪽 여백이 답답해 보인다. 탭과 그 아래 품목 헤더의 세로 간격도 더 자연스럽게 정돈할 필요가 있다.
  - `패널 닫기` 버튼에 대한 사용자 주석은 원하는 변경을 끝까지 설명하지 않아, 위치·크기·색 중 무엇을 조정할지는 확정되지 않았다.
- 사용자 불편: 상단의 화면 전환 조작과 품목 식별 정보가 기능상 분리되지는 않지만, 좌우·상하 여백이 균형 있게 느껴지지 않아 상세 패널의 첫 인상이 다소 빽빽하다.
- 확정 정책:
  - 현재 시각적 순서 `상세 정보/최근 내역 탭 → 품목명·코드·상태 → 선택 탭 본문`은 유지한다.
  - 탭 상자는 패널 상단 쪽으로 조금 올리고, 품목 헤더의 왼쪽 기준에 맞추되 가용 폭보다 조금 좁게 두어 오른쪽에 자연스러운 숨 쉴 여백을 남긴다.
  - 탭 상자와 품목 헤더 사이의 간격을 늘려 두 정보 단위가 겹치거나 지나치게 붙어 보이지 않게 한다.
  - 두 탭의 선택 상태, 기본 선택(`상세 정보`), 다른 품목 선택 시 상세 탭 복귀, 닫기·Escape 동작, 본문 스크롤과 하단 빠른 작업은 유지한다.
- 정책 확인 필요:
  - `패널 닫기` 버튼은 위치·크기·색상·탭과의 정렬 중 어느 부분을 어떻게 바꿔야 하는지 사용자 확인이 필요하다. 확인 전에는 시각 변경을 하지 않고 현재 닫기 기능·접근성만 유지한다.
- 구현 방향:
  - 공통 `DesktopRightPanel`의 폭·다른 상세 패널의 헤더를 바꾸지 않고, `DesktopInventoryRightPanel`이 넘기는 `topContent`와 바로 아래 품목 헤더의 간격만 재조정한다.
  - 탭 컨테이너에 패널 전용 최대 폭 또는 오른쪽 인셋을 주어, 좌측 정렬·오른쪽 여백·상단 위치가 데스크톱 폭에 맞게 함께 유지되게 한다.
  - 닫기 버튼 변경은 정책 확정 뒤에만 같은 패널 범위에서 반영하고, 기존 접근성 연결(`aria-labelledby`, `aria-controls`, 선택 상태)과 탭 전환 회귀 테스트를 유지한다.
- 수용 기준:
  - 1920×910 데스크톱에서 탭이 패널 최상단에 안정적으로 놓이고, 품목 헤더보다 앞서는 현재 DOM·시각 순서가 유지된다.
  - 탭 상자의 오른쪽에는 의도적인 여백이 보이고, 탭·품목 헤더·부족/정상 상태가 서로 겹치거나 잘리지 않는다.
  - 탭과 품목 헤더의 세로 간격이 제목이 긴 품목에서도 일정하게 유지되며, 본문 시작점이 답답하거나 들뜨지 않는다.
  - `최근 내역` 전환, 다른 품목 선택 뒤 `상세 정보` 복귀, 패널 닫기와 Escape, 상세 정보의 스크롤·빠른 작업이 기존처럼 동작한다.
- 브라우저 확인 시나리오:
  - 데스크톱 1920×910에서 `/mes?tab=dashboard`를 열고 `전극(70kV)`를 선택해 탭의 상단 위치, 오른쪽 여백, 탭과 품목 헤더 사이 간격을 확인한다.
  - 긴 품목명, 정상 품목, 부족 품목을 각각 열어 탭·헤더·상태 배지의 겹침과 잘림이 없는지 확인한다.
  - `상세 정보`와 `최근 내역`을 각각 열고 다른 품목으로 바꾼 뒤 탭 초기화, 스크롤, 닫기 버튼 클릭과 Escape를 확인한다.
- 우선순위: 중간

### 9. 자재 목록 sticky 헤더를 불투명 표면으로 고정

- 화면/영역: 데스크톱 대시보드(`/mes?tab=dashboard`) > 자재 목록 > `자재 목록` 제목과 품명·품목 코드 검색창이 있는 sticky 헤더.
- 증상:
  - 목록을 스크롤하면 헤더 뒤의 행·텍스트가 비쳐 보여, 고정된 헤더가 독립된 읽기 표면으로 보이지 않는다.
  - 검색창 자체는 표면을 가지지만 제목·검색창 주위 헤더 영역은 투명하게 합성돼 목록 내용과 시각적으로 섞인다.
  - 검색 헤더 하단과 표의 열 머리글 사이에 넓은 빈 띠가 남아, 두 요소가 같은 목록의 제어부와 시작점으로 자연스럽게 이어지지 않는다.
- 사용자 불편: 스크롤 중 검색·필터 기준을 읽을 때 뒤의 목록 정보가 겹쳐 보여 시선이 분산되고, 검색 뒤의 과도한 공백 때문에 목록의 시작점이 정돈되지 않아 보인다.
- 확정 정책:
  - sticky 헤더 전체는 목록 행을 완전히 가리는 불투명 표면을 사용한다.
  - 헤더 표면은 자재 목록 카드와 같은 중립적인 배경으로 자연스럽게 이어지며, 이를 해결하려고 별도의 푸른 띠·이중 테두리·추가 그림자를 만들지 않는다.
  - 검색 헤더와 표 열 머리글 사이 여백은 현재보다 줄여, 두 영역이 붙어 보이지는 않되 하나의 목록 제어·내용 시작점으로 촘촘하게 연결되게 한다.
  - 기존 sticky 위치·z-index·둥근 상단 모서리·검색 입력·행 선택·우측 상세 패널 동작은 유지한다.
- 구현 방향:
  - `InventoryTableStickyHeader`의 상속 배경을 명시적인 불투명 목록 카드 표면으로 교체하고, 라이트/다크 테마 모두에서 동일한 표면 토큰을 사용한다.
  - 헤더 외곽의 배경 책임과 열 머리글 앞 여백만 조정한다. 검색 입력의 별도 표면, 열 머리글의 행 높이, `DesktopInventoryView`의 카드·스크롤 구조는 바꾸지 않는다.
  - 렌더 테스트 또는 스타일 회귀 검증으로 sticky 헤더가 투명 또는 `inherit` 배경으로 되돌아가지 않게 한다.
- 수용 기준:
  - 1920×910 데스크톱에서 목록을 여러 행만큼 스크롤해도 제목·검색창 주위 헤더 영역에 행 텍스트·상태 배지·진행선이 비쳐 보이지 않는다.
  - 헤더와 자재 목록 카드의 배경은 한 표면처럼 이어지고, 굵은 푸른 띠·이중 테두리·새 그림자가 생기지 않는다.
  - 검색 입력 하단과 표 열 머리글 사이의 빈 띠가 현재보다 눈에 띄게 줄어들고, 검색창·열 머리글·첫 번째 행의 텍스트가 서로 붙거나 겹치지 않는다.
  - 검색, 필터, 목록 스크롤, 행 선택, 우측 상세 패널 열기와 긴 목록의 기존 sticky 동작이 유지된다.
- 브라우저 확인 시나리오:
  - `/mes?tab=dashboard`를 1920×910으로 열고 자재 목록을 처음 위치·중간·더 아래 위치까지 각각 스크롤해 헤더 뒤 비침이 없는지 확인한다.
  - 같은 화면에서 검색 입력과 표 열 머리글 사이의 간격이 줄었는지, 검색창·열 이름·첫 행이 읽기 좋게 분리되는지 확인한다.
  - 검색어 입력, KPI/필터 변경, 품목 선택과 우측 상세 패널 열기 뒤에도 헤더의 불투명 표면과 고정 위치가 유지되는지 확인한다.
  - 라이트·다크 테마에서 헤더와 카드의 표면 연결, 텍스트 대비, 검색 입력의 테두리와 모서리를 확인한다.
- 우선순위: 중간

### 12. BOM 구성 보기에서 유형 열을 없애고 품목코드·수량·재고 폭과 하위 계층 표현을 정돈

- 화면/영역:
  - 데스크톱 대시보드(`/mes?tab=dashboard`) > 자재 목록에서 품목 선택 > `BOM 구성 보기` 모달 > 구성품 트리 표.
  - 수집 기준은 1920×910이며, `DX3000_65kV, 1.7mA_USA_Vector [White]`의 구성품에 `34-PR-0114`, `3-PA-0004`처럼 세 구간 품목코드가 보이는 상태다.
  - 같은 BOM 모달의 헤더 오른쪽 `닫기` 제어와, 재고 우측 상세 패널 헤더의 기존 `패널 닫기` 제어.
  - 범위는 `BomDetailModal`이 여는 데스크톱 모달 표뿐이다. 대시보드 우측 상세 패널의 비모달 BOM, 모바일 BOM 뷰어, 출하의 동결된 step 5 카드와 다른 화면의 품목코드는 이번 변경 대상이 아니다.
- 증상:
  - 현재 표는 펼치기 칸·구성품명·`유형`·품목코드·소요량·현재재고의 6열이며, `유형`의 `Pack Raw`/`Packaging` 칩이 품목코드 두 번째 구간이 이미 담고 있는 공정 정보를 한 번 더 반복한다.
  - `유형` 96px 고정 열과 그 뒤의 넓게 늘어나는 품목코드 열 때문에 구성품명 뒤의 정보 시작점이 오른쪽으로 밀리고, 품목코드와 우측 수량·재고 사이에 업무 의미가 없는 넓은 빈 폭이 생긴다.
  - `34-PR-0114` 같은 품목코드는 현재 모두 같은 약한 글자색으로 렌더되어, 공정을 나타내는 가운데 `PR`·`PA`·`PF` 구간을 훑어 구분하기 어렵다.
  - 비선택 구성품 행은 포인터를 올려도 표면 변화가 없어, 대시보드의 다른 목록처럼 현재 훑는 행을 눈으로 따라가기 어렵다. 이 효과는 행 선택이나 재고 상태를 뜻하지 않아야 한다.
  - 부모의 화살표를 펼쳐도 자식 행은 구성품명 시작선이 거의 같고, 가는 계층선·들여쓰기·펼친 상태의 시각 앵커가 충분하지 않아 하위 자재 묶음이라는 관계가 즉시 읽히지 않는다.
  - 모달의 `닫기`는 같은 대시보드 안의 재고 상세 패널 `패널 닫기`와 크기·색·접근 가능한 이름이 달라, 같은 닫기 행동이 다른 제어처럼 보인다. 구현도 두 파일에 중복돼 한쪽만 고치면 다시 어긋날 수 있다.
- 사용자 불편: 구성품명에서 품목코드, 소요량, 현재재고로 시선이 이동할 때 중복 `유형` 칩과 빈 폭을 건너뛰어야 하며, 수량·재고의 우측 정보 영역도 여백 비율이 어색해 BOM을 빠르게 비교하기 어렵다. 펼친 BOM에서는 어느 행이 상위 구성품이고 어느 행이 하위 자재인지, 현재 포인터가 어느 행을 읽고 있는지도 빠르게 구분하기 어렵다. 또한 같은 닫기 행동의 모양과 위치가 다르면 화면 전환의 조작 문법이 끊긴다.
- 확정 정책:
  - 이 모달 표에서는 `유형` 머리글과 행의 공정 라벨 칩을 모두 제거한다. API 응답의 `process_type_code`, 트리 계층, 펼치기/접기 정보는 유지하며, 제거하는 것은 데스크톱 모달의 중복 표시에 한정한다.
  - 열은 `펼치기/계층`·`구성품명`·`품목코드`·`소요량`·`현재재고`의 5열로 재구성한다. 구성품명은 가장 넓은 읽기 영역으로 유지하고, 품목코드는 이름 바로 다음의 왼쪽 정보 영역으로 옮겨 중간의 이유 없는 빈 폭을 없앤다.
  - 소요량과 현재재고는 오른쪽에서 서로 읽기 좋게 분리하되, 둘 사이와 표의 우측 가장자리에 남는 폭을 자연스럽게 분배한다. 수량은 기존처럼 tabular 숫자·단위·가운데 정렬을 유지한다.
  - 세 구간의 비어 있지 않은 하이픈 코드(`34-PR-0114`, `3-PA-0004`)는 전체 문자열을 유지한 채 두 번째 구간만 굵은 공정 토큰 색으로 강조한다. 형식이 아닌 코드·누락 코드·알 수 없는 공정 코드는 억지로 분해하지 않고 기존의 안전한 원문 또는 `-` 표기로 남긴다.
  - 강조 방식은 출하 PF 구성품에서 이미 보이는 `SummaryCode`의 공정 구간 문법을 시각 기준으로 삼는다. 이를 위해 출하 화면을 함께 재배치하거나 동결된 step 5 카드의 크기·행·overflow를 바꾸지 않는다.
  - 마우스가 본문 데이터 행 위에 있을 때만 기존 대시보드 목록과 같은 중립 `s4` 계열의 낮은 대비 hover 표면을 150ms 안팎으로 적용한다. hover는 행 선택·부족·현재 포커스 상태를 대신하지 않으며, 파란 외곽선·행 높이 변화·열 이동을 만들지 않는다.
  - 펼친 부모는 회전한 chevron과 토큰 기반의 가벼운 활성 표면으로 자식이 열려 있음을 보인다. 자식 행은 입출고 내역 `BomBatchDetail`처럼 부모 조작부와 같은 폭의 계층 슬롯을 먼저 확보한 뒤 아이콘·구성품명을 시작해, 한 단계마다 최소 20px의 명확한 들여쓰기를 만든다. 깊이가 더 깊어지면 같은 슬롯 단위로 늘리되, 새 표 열·장식용 레일을 추가하거나 품목코드 시작선을 다시 오른쪽으로 밀지 않는다.
  - hover는 포인터 보조 피드백일 뿐 키보드 동작을 대체하지 않는다. 펼치기 버튼의 44px 조작 영역·`aria-expanded`·명확한 펼치기/접기 이름·focus-visible 표시는 유지한다.
  - BOM 모달의 닫기는 우측 상세 패널의 기존 빨간 원형 `패널 닫기` 문법과 같은 제어부를 사용한다. 현재 패널 버튼의 32px 시각 크기·빨간 tint·X 아이콘·hover 문법은 유지하고, 모달에서도 접근 가능한 이름을 `패널 닫기`로 통일한다.
  - 공유 제어부는 `DesktopRightPanel`의 기존 구현을 좁게 추출한 것으로 한정한다. 모달·우측 패널 외 모든 다이얼로그, `SlidePanel`의 회색 닫기, 이미지 라이트박스 등의 닫기 규칙을 일괄 통합하거나 재디자인하지 않는다.
- 구현 방향:
  - 구현 계획 전 실제 인증된 대시보드에서 모달을 열어 1920×910의 표 폭, 각 열의 계산된 폭, 긴 구성품명·하위 트리·수량 단위가 있는 행을 측정한다. 그 측정을 근거로 전용 `.bom-modal-grid`를 6열에서 5열로 바꾸되, 이름은 `minmax(0, …)`로 줄어들 수 있게 하고 코드·수량·재고의 최소 폭을 정해 겹침을 막는다.
  - `ModalBomTreeItem`과 모달 sticky 머리글에서 `유형` 전용 DOM과 `processStageLabel` 의존성을 제거한다. 같은 모달 경로가 쓰는 행과 머리글만 함께 바꾸고, 비모달 `BomTreeItem`의 상태·부서 배지·compact 레이아웃은 건드리지 않는다.
  - 품목코드 렌더는 기존 출하 `SummaryCode`와 같은 세 구간 판별 계약과 `processTypeColor`를 사용한다. 공유 순수 렌더러 추출이 중복 판별을 실제로 줄이는 가장 작은 변경인지 먼저 확인하고, 그렇지 않으면 모달 전용의 작은 렌더 경로로 한정한다. 전역 품목코드 스타일 일괄 변경이나 출하 컴포넌트 이동은 하지 않는다.
  - 모달 행에 CSS 기반 hover 전환을 추가하고, 펼친 상태는 부모 토글의 `aria-expanded`와 행/버튼의 상태 클래스로 연결한다. JS 포인터 상태를 따로 만들지 않는다. 모달의 가변 행 높이·5열 grid·현재 44px 조작 영역에서, 입출고 내역과 같은 고정 폭 조작/빈 계층 슬롯을 배치한다. 비모달 `Rail`·`Connector`를 그대로 복사하거나 새 장식용 선을 만들지 않는다.
  - `DesktopRightPanel`에 현재 인라인으로 있는 닫기 JSX만 ref 전달이 가능한 작은 공유 제어부로 추출하고, BOM 모달은 그것을 사용한다. 추출 뒤에도 우측 패널의 조건부 `onClose` 렌더·위치·클릭 동작은 그대로 둔다. BOM 모달의 `useFocusTrap` 초기 포커스 ref, Escape·바깥 클릭 닫기, 트리거로의 포커스 복귀는 보존한다.
  - 기존 `InventoryDetailPanel` 모달 테스트를 새 5열 계약으로 갱신한다. 유형 칩이 사라진 것, 공정 구간 강조와 형식 밖 코드의 안전한 fallback, 행 hover 클래스, 펼친 부모의 상태, 입출고 내역 기준의 깊이별 슬롯 들여쓰기, 긴 이름·중첩 행·수량/재고 정렬, 펼치기/접기와 모달 닫기 계약을 함께 보호한다. 모달 닫기 버튼의 초기 포커스·`패널 닫기` 이름·클릭/Escape/바깥 클릭·포커스 복귀와 우측 패널의 같은 제어부 회귀 테스트를 추가한다. 기존의 “모달 rail/connector 없음” 기대는 유지하고, 자식 행의 계층 spacer와 시작선만 새 회귀 기준으로 추가한다.
- 수용 기준:
  - 1920×910 대시보드 BOM 모달의 머리글은 빈 펼치기 칸을 제외하고 `구성품명`·`품목코드`·`소요량`·`현재재고`만 보이며, `유형`, `Pack Raw`, `Packaging` 같은 중복 공정 라벨 칩은 어느 행에도 남지 않는다.
  - 품목코드는 구성품명 바로 다음으로 당겨져 표시되고, 품목코드부터 우측 수량·재고까지 업무 의미 없는 큰 빈 띠가 보이지 않는다. 긴 이름은 기존처럼 여러 줄로 읽히며 코드·수량·재고를 밀어 겹치거나 숨기지 않는다.
  - `34-PR-0114`와 `3-PA-0004`에서는 각각 `PR`, `PA`만 기존 공정 토큰 색·굵기로 명확히 구분되고, 복사·보조기술·전체 코드 텍스트는 훼손되지 않는다. 두 번째 구간이 정의되지 않았거나 코드가 세 구간 형식이 아닌 경우에는 오류·빈 강조·잘린 텍스트 없이 원문이 읽힌다.
  - 소요량·현재재고의 열 제목과 값은 모든 행에서 수직으로 맞고, 1EA·2EA·대량 재고처럼 자릿수가 달라도 숫자 비교가 쉽다. 행 구분선·상단 sticky 머리글·트리 깊이 들여쓰기·펼치기/접기 아이콘은 유지된다.
  - 마우스를 행 위로 이동하면 해당 데이터 행만 낮은 대비의 대시보드식 표면으로 즉시 구분되고, 마우스를 떼면 원래 표면으로 돌아온다. 이때 열 폭·행 높이·구분선·수량/재고 값·선택 상태가 움직이거나 파란 선택 윤곽으로 오인되지 않는다.
  - 부모를 펼치면 chevron의 열린 상태와 자식 묶음의 시작이 함께 보이고, 한 단계 이상의 하위 자재는 입출고 내역처럼 부모의 고정 조작 칸 뒤에서 최소 20px 더 안쪽으로 시작한다. 부모를 접으면 자식 행과 그 계층 슬롯이 함께 사라지고, 다시 열어도 행 순서·코드·수량·재고가 바뀌지 않는다.
  - 키보드로 펼치기 버튼에 도달했을 때 포커스가 명확히 보이고, Enter/Space로 열고 닫을 때 `aria-expanded`와 시각 상태가 일치한다.
  - BOM 모달과 우측 상세 패널의 X는 같은 빨간 원형 문법·X 크기·hover 반응·`패널 닫기` 접근 이름으로 보인다. 두 위치 모두 중복 버튼 없이 한 번만 렌더되고, 모달 헤더의 제목·부제·스크롤바와 겹치지 않는다.
  - 모달이 열리면 공유 닫기 버튼에 초기 포커스가 가고, 클릭·Escape·바깥 클릭은 BOM 모달만 닫아 트리거에 포커스를 되돌린다. 우측 상세 패널의 닫기는 기존처럼 선택 해제만 수행한다.
  - 모달의 포커스 트랩, Escape·닫기 버튼·바깥 클릭 닫기, 내부 세로 스크롤, API 로딩·오류·재시도, 라이트/다크 토큰 대비가 기존처럼 동작한다.
- 브라우저 확인 시나리오:
  - 구현 계획 전, 실제 인증된 `/mes?tab=dashboard`를 1920×910으로 열어 사용자와 같은 BOM 모달·구성품 데이터를 재현한다. 캡처와 DOM/계산 스타일로 현재 6열의 폭·빈 폭·sticky 머리글·행 소유 컴포넌트를 확인하고, 인증된 화면을 열 수 없으면 계획을 확정하지 않는다.
  - 구현 뒤 같은 URL·뷰포트에서 `34-PR-0114`와 `3-PA-0004`가 있는 행을 확인해 `유형` 열/칩의 완전한 제거, 품목코드의 왼쪽 이동, 수량·재고 폭의 균형, 공정 두 번째 구간 강조를 캡처와 DOM으로 검증한다.
  - 포인터로 최상위·하위·부족·정상 구성품 행을 각각 hover해, 한 행만 대시보드와 같은 낮은 대비의 표면으로 반응하고 열/행 높이·선택 의미가 바뀌지 않는지 확인한다. 라이트·다크 테마에서도 hover 대비가 충분한지 확인한다.
  - 두 단계 이상 중첩된 하위 구성품, 긴 구성품명, 부족·정상 재고, 큰 수량이 있는 BOM을 각각 열어 입출고 내역의 부모 조작 칸·자식 시작선과 같은 깊이별 슬롯 들여쓰기, 열 맞춤·가로 넘침·행 높이를 확인한다. 부모를 반복해 펼치고 접어 자식·계층 슬롯의 동시 표시/제거와 코드·수량·재고의 불변성을 확인하고, 키보드 Enter/Space·`aria-expanded`도 확인한다.
  - 각 트리를 펼치고 접은 뒤 모달 내부 스크롤·Escape·닫기 버튼·바깥 클릭 닫기까지 확인한다.
  - 같은 1920×910 대시보드에서 재고 우측 상세 패널과 BOM 모달을 번갈아 열어 두 X의 크기·색·아이콘·hover·`패널 닫기` 접근 이름이 일치하는지 확인한다. BOM 모달의 X는 클릭·Escape·바깥 클릭 후 모달만 닫고 트리거로 돌아가며, 우측 패널 X는 모달을 만들지 않고 선택만 해제하는지 확인한다.
  - 비교 기준인 출하 PF 구성품 화면도 읽기 전용으로 확인해 공정 코드 강조의 색·굵기 문법이 맞는지만 대조하고, 출하 카드 크기·배치가 바뀌지 않았음을 회귀 확인한다.

- 증상:
  - 현재 완제품 SN은 독립 카드로, 인보이스 번호는 라벨이 입력창 위에 놓인 별도 편집 섹션으로 나뉜다.
  - 두 정보는 같은 출하 식별·문서 관리 단위지만, 인보이스 라벨이 한 단계 위에 떠 있고 입력·저장 버튼만 낮게 시작해 완제품 SN 카드와 상단·본문 정렬선이 어색하다.
  - 같은 `InvoiceNumberEditor`가 다른 두 화면에서도 쓰이므로, 공용 컴포넌트의 기본 배치를 일괄 변경하면 요청 상세와 준비 작업 상세까지 예기치 않게 달라질 수 있다.
- 사용자 불편: 출하를 식별하는 시리얼과 문서 번호를 함께 훑을 때 정보 묶음이 두 개의 독립 카드처럼 분리되어, 헤더의 좌우 균형과 시선 흐름이 끊긴다.
- 정책 확인 필요:
  - 최종 배치는 다음 중 하나로 확정한다. (1) 인보이스를 완제품 SN 상자의 왼쪽에 라벨·입력·저장을 한 줄로 둔다. (2) 완제품 SN 상자 안에 인보이스 편집을 보조 필드로 넣어 한 카드 안에서 정렬한다.
  - 어느 안이든 인보이스 라벨은 입력창 위의 독립 행으로 뜨지 않고, 해당 입력과 같은 정보 단위 안에서 읽혀야 한다.
- 구현 방향:
  - `historyWork`의 `ViewHeader` 오른쪽 호출부에만 적용되는 컴팩트/인라인 배치를 만든다. 공용 `InvoiceNumberEditor`의 기본 구조는 요청 상세·준비 작업 상세에서 그대로 유지하고, 필요한 경우 이력 헤더 전용 variant 또는 래퍼로 범위를 한정한다.
  - 선택한 배치 안에서 완제품 SN, 인보이스 라벨·입력·저장 버튼의 상단·본문 기준선을 맞추고, 헤더의 기존 둥근 모듈·중립 표면·`gap-3` 리듬을 따른다. 인보이스 저장, 공백 제한, 오류 표시, 쿼리 무효화와 상태별 표시 계약은 바꾸지 않는다.
  - 픽업 완료 이력에서는 SN과 인보이스를 함께 표시하고, 취소 이력에서는 SN 없이도 인보이스 편집이 빈 공간처럼 보이지 않게 배치한다. 동결된 출하 단계 5의 카드 높이·열·넘침 규칙은 변경하지 않는다.
  - 이력 헤더 레이아웃 테스트에는 선택한 배치와 공유 컴포넌트의 다른 두 사용처가 기존 배치를 유지하는 회귀 검증을 추가한다.
- 수용 기준:
  - 픽업 완료 이력에서 완제품 SN과 인보이스가 하나의 출하 식별·문서 정보 묶음으로 읽히며, 인보이스 라벨만 상단에 떠 보이지 않는다.
  - 선택한 위치에서 SN 카드와 인보이스 필드의 상단·본문 정렬이 자연스럽고, 저장 버튼·뒤로가기·제목·상세 카드와 겹치지 않는다.
  - 취소 이력은 SN이 없어도 인보이스 편집의 폭·정렬·저장 동작이 자연스럽고, 기존 번호 비우기 제한·저장 실패 문구·상태 배지·픽업 완료 취소·수정 이력·거래 로그가 유지된다.
  - 긴 완제품 SN·긴 인보이스 번호와 좁은 데스크톱 너비에서 텍스트가 겹치거나 잘리지 않으며, 필요한 경우 헤더 안에서 안전하게 다음 줄로 전환된다.
- 브라우저 확인 시나리오:
  - 구현 계획 전, 실제 인증된 1920×910 브라우저에서 위 픽업 완료 URL과 요청을 다시 열어 현재 SN 카드·인보이스 라벨·입력·저장 버튼의 DOM 소유와 계산된 폭·간격을 확인한다.
  - 구현 뒤 같은 URL·뷰포트에서 선택한 배치가 한 정보 묶음으로 보이는지, 긴 SN·긴 인보이스에서 줄바꿈·가로 넘침·세로 겹침이 없는지 확인한다.
  - 승인된 검증 데이터에서 인보이스 변경·저장, 준비 이력이 있는 기존 번호 비우기 차단, 저장 오류를 확인하고, 취소 이력에서는 SN 없는 헤더를 별도로 확인한다.
  - 요청 상세와 준비 작업 상세도 열어 공용 `InvoiceNumberEditor`의 기존 배치와 저장 동작이 바뀌지 않았는지 확인한다.
- 우선순위: 중간

### 7. 출하 요청 목록의 상태 열을 남은 작업 영역 높이까지 채움

- 화면/영역: 데스크톱 출하 > 출하 관리(`/mes?tab=shipping&shippingView=requestList`) > `출하 요청`·`준비 중`·`준비 완료` 3개 상태 열.
- 증상:
  - 세 상태 열은 내부 요청 수만큼의 높이만 차지하고, 그 아래의 큰 작업 영역은 아무 표면 없이 비어 있다.
  - 각 `ListColumn`은 자체적으로 전체 높이를 채우도록 작성돼 있지만, 요청 목록 진입 애니메이션 래퍼가 남은 높이를 전달하지 않아 실제 화면에서는 그 규칙이 발휘되지 않는다.
- 사용자 불편: 요청이 적은 정상적인 날에도 출하 관리 화면이 상단에만 내용이 몰린 미완성 보드처럼 보이고, 상태별 업무 열의 작업 공간이 충분히 확보되지 않는다.
- 확정 정책:
  - 데스크톱 출하 요청 목록에서는 데이터가 0건 또는 소수여도 `출하 요청`·`준비 중`·`준비 완료`의 세 상태 열이 제목 아래의 남은 작업 영역을 같은 높이로 채운다.
  - 빈 상태와 소수 요청 행은 지금처럼 열의 상단에 표시하고, 남는 높이는 각 상태 열의 같은 표면 안에 자연스럽게 남긴다.
  - 요청이 많아지면 전체 화면이 다시 늘어나지 않고 각 상태 열의 목록 본문만 스크롤한다. 새 요청 만들기·요청 행 선택·상태별 내용은 유지한다.
- 구현 방향:
  - `requestList` 진입에만 적용되는 애니메이션 래퍼와 `RequestListEntry` 사이에 `min-h-0`·`flex-1` 높이 전달을 복구해, 기존 `shipping-request-list-grid`와 `ListColumn`의 높이 채움 규칙이 실제로 이어지게 한다.
  - 애니메이션 자체와 다른 진입 화면(`historyList`, 출하 단계 5)을 바꾸지 않으며, 각 열의 기존 `overflow-y-auto` 본문을 유지한다.
  - 요청 목록 레이아웃 테스트에 애니메이션 진입 상태에서도 요청 목록 패널·그리드·세 상태 열이 전체 높이 체인에 연결되는 회귀 검증을 추가한다.
- 수용 기준:
  - 0건/1건/1건처럼 내용이 적은 요청 목록에서도 세 상태 열의 하단이 동일한 작업 영역 하단선까지 이어진다.
  - 빈 상태와 새 요청 만들기 버튼, 요청 행은 기존처럼 각 열의 상단에서 보이고, 큰 빈 영역이 열 밖의 캔버스로 남지 않는다.
  - 긴 상태 목록에서는 각 열의 내부 목록만 세로 스크롤되고, 출하 관리 헤더·다른 열·사이드바 높이가 밀리거나 이중 스크롤바가 생기지 않는다.
  - 요청 목록으로의 진입/복귀 애니메이션과 요청 선택 후 상세 진입은 기존대로 동작한다.
- 브라우저 확인 시나리오:
  - 1920×910에서 `/mes?tab=shipping&shippingView=requestList`를 열어 0건·1건·1건 상태의 세 열이 남은 작업 영역을 같은 높이로 채우는지 확인한다.
  - 새 요청 만들기를 누르고 목록으로 돌아오며 애니메이션 중에도 열 높이가 수축하지 않는지 확인한다.
  - 한 상태에 여러 요청이 있는 데이터에서 해당 열의 내부 스크롤, 요청 행 선택·상세 진입·뒤로가기를 확인한다.
- 우선순위: 중간

### 8. 출하 이력의 연·월 폴더를 클릭마다 반드시 접고 펼침

- 화면/영역: 데스크톱 출하 > 출하 이력(`/mes?tab=shipping&shippingView=historyList`) > 연도·월 폴더 요약 행.
- 증상:
  - 현재 선택된 연도 또는 월의 summary를 다시 클릭해도 `<details>`가 닫히지 않는다.
  - 선택 상태가 폴더의 `open` 상태를 강제하고, summary 클릭의 브라우저 기본 토글을 막은 뒤 같은 연·월 선택을 조기 반환하기 때문이다.
- 사용자 불편: 삼각형이 있는 연·월 폴더가 일반적인 접기/펼치기 문법을 따르지 않아, 긴 출하 이력에서 보고 싶은 기간만 접어 작업 공간을 정리할 수 없다.
- 확정 정책:
  - 연도와 월 summary를 클릭할 때마다 해당 폴더는 반드시 열린 상태와 닫힌 상태를 서로 전환한다.
  - 이미 선택·조회된 연·월을 닫는 것은 데이터 선택이나 API 재조회가 아니라 표시만 접는 행동이다. 다시 열면 현재 선택된 데이터가 그대로 보인다.
  - 다른 연·월을 처음 선택할 때의 기존 조회·선택 흐름은 유지하되, 새로 열린 폴더도 이후 클릭으로 다시 닫을 수 있어야 한다.
- 구현 방향:
  - 이력 조회에 쓰는 `selectedYear`/`selectedMonth`와 연·월 disclosure의 열림 상태를 분리한다. native `<details>`의 토글 상태 또는 별도 접근성 상태를 사용하되, 클릭·키보드 모두 같은 토글 계약을 따른다.
  - 이미 선택된 연·월의 summary 클릭에서는 `preventDefault`로 닫힘을 막지 않고, 닫기/다시 열기가 불필요한 API 호출이나 URL 상태 변경을 만들지 않게 한다.
  - 연도 상위 폴더를 닫으면 그 안의 월·요청 행을 숨기고, 다시 열면 현재 선택 월과 기존 데이터가 정상적으로 표시되게 한다.
  - 현재 두 번째 클릭 뒤에도 `open`을 기대하는 출하 이력 테스트를 열림→닫힘→다시 열림 검증으로 바꾸고, 다른 연·월 선택 시 기존 조회 횟수 규칙도 함께 보호한다.
- 수용 기준:
  - 열린 `2026년`을 클릭하면 즉시 닫히고, 다시 클릭하면 월 목록이 다시 보인다.
  - 열린 `8월 · N건` 또는 `7월 · N건`을 클릭하면 해당 요청 행이 숨겨지고, 다시 클릭하면 같은 행이 다시 보인다.
  - 폴더를 접고 다시 펴는 동안 같은 연·월 이력 API를 중복 호출하지 않으며, 상태 전환·검색·더 보기·요청 선택·상세 진입은 기존처럼 동작한다.
  - 마우스와 키보드로 summary를 조작해도 열림 상태와 접근성 의미가 일치한다.
- 브라우저 확인 시나리오:
  - `/mes?tab=shipping&shippingView=historyList&shippingHistoryStatus=PICKED_UP`에서 2026년, 8월, 7월을 각각 두 번 이상 클릭해 열림/닫힘이 매번 반전되는지 확인한다.
  - 한 달을 열어 요청 행을 확인한 뒤 접고 다시 열어 행·선택·스크롤 위치가 자연스러운지 확인한다.
  - 다른 연도와 다른 월을 선택한 뒤에도 이전 선택 조회가 유지되고, 새로 연 폴더도 같은 방식으로 접고 펼 수 있는지 확인한다.
  - 검색 결과와 요청 취소 상태에서도 연·월 폴더를 키보드 Enter/Space로 조작해 확인한다.
- 우선순위: 중간

### 11. 입출고 작성 중·승인함의 빈 작업 영역을 같은 큰 안내 모듈로 통일

- 화면/영역:
  - 데스크톱 입출고 > `작성 중`(`/mes?tab=warehouse&section=cart`)의 작업 중 요청 빈 상태.
  - 데스크톱 입출고 > `창고 승인함`(`/mes?tab=warehouse&section=queue`)의 승인 대기 빈 상태.
  - 데스크톱 입출고 > `부서 승인함`(`/mes?tab=warehouse&section=dept-queue`)의 부서 결재 대기 빈 상태.
  - 수집 기준은 1920×910 데스크톱이며, 각 화면에 표시할 요청이 없는 상태다. `내 요청`과 실제 요청 행이 있는 상태는 이번 범위에 포함하지 않는다.
- 증상:
  - 작성 중의 빈 상태는 상단의 낮은 둥근 카드 안에만 있고, 탭 아래에서 사이드바 하단까지 이어지는 큰 작업 영역은 바깥 캔버스 색으로 비어 있다.
  - 창고 승인함과 부서 승인함은 같은 빈 업무 상태임에도 카드 표면 없이 작은 `compact` 텍스트만 상단에 표시되어, 작성 중과 다른 화면처럼 보인다.
  - 세 화면의 제목·설명·아이콘·행동 버튼은 `compact` 크기라 1920px 작업 화면의 넓은 빈 영역에 비해 너무 작고, 빈 상태의 다음 행동이 보조 정보처럼 약하게 읽힌다.
- 사용자 불편: 요청이 없는 정상적인 날에도 업무 화면이 미완성 캔버스처럼 보이며, 작성 중·창고 승인·부서 승인 사이를 전환할 때 같은 빈 업무 상태가 서로 다른 구조와 밀도로 보여 흐름이 끊긴다.
- 확정 정책:
  - 위 세 빈 상태는 탭 아래의 남은 작업 영역을 하나의 둥근 업무 표면으로 자연스럽게 채우고, 안내 내용을 그 표면의 시각적 중심에 둔다.
  - 새 `작성 중` 빈 상태를 기준으로 창고 승인함·부서 승인함도 같은 표면·중앙 정렬·여백 문법을 사용한다. 승인함의 업무 문구는 각각 유지하며, 작성 중에만 `요청 작성` 행동을 계속 제공한다.

### 14. 입출고 요청 작성의 상단 탭·본문 간격을 12px로 복원

### 1. 재작업 묶음 취소가 단일 객체 재고 효과에서 422로 중단되는 문제를 처리

- 화면/영역: 입출고 내역 > 재작업 묶음 상세 > `취소 확정` 모달. 관찰 대상은 `8-VA-0018` 검색 결과의 `defect-disassemble:` 묶음이다.
- 증상:
  - `0fe9b11` 뒤에도 실제 취소 요청은 422로 끝날 수 있다.
  - 빈 목록의 `DEFECT_SCRAP` 자식은 새 예외 처리로 통과하지만, 같은 묶음의 `MARK_DEFECTIVE` 자식은 `inventory_effect`가 목록이 아닌 단일 객체라 취소 서비스의 형식 검증에서 중단된다.
- 사용자 불편: 정상적인 재작업 묶음이라도 과거 이력 형식 차이 때문에 전체 취소가 막혀 재고·불량 정정을 완료할 수 없다.
- 정책 확인 필요 (대화 재시작으로 보류):
  - 유효한 단일 효과 객체(`scope`, `delta` 등 필수값 보유)를 한 항목 목록으로 정규화해 과거 이력도 취소할지, 별도 보정 절차로만 처리할지 결정한다.
  - 앞선 선택은 재확인 전 확정으로 취급하지 않는다.
- 구현 방향:
  - 취소 서비스와 역재고 적용부의 입력 계약을 일치시키고, 유효 단일 객체만 안전하게 처리한다.
  - 생성 경로·기존 이력을 함께 조사해 앞으로는 목록 형식만 저장되는지 확인한다.
  - `0fe9b11`의 빈 `DEFECT_SCRAP` 회귀 케이스에 단일 객체 `MARK_DEFECTIVE` 자식을 포함한 묶음 취소를 추가한다.
- 수용 기준:
  - 빈 목록 `DEFECT_SCRAP`와 유효 단일 객체 `MARK_DEFECTIVE`를 함께 가진 묶음이 정상 취소된다.
  - 잘못된 효과 객체는 422로 중단하고 어떤 재고·취소 상태도 남기지 않는다.
  - 새 이력은 목록 형식으로 저장되며, 기존 객체 형식 이력의 처리 근거가 테스트로 남는다.
- 브라우저 확인 시나리오:
  - 정책 확정 뒤 테스트 DB 또는 별도 승인된 검증 묶음에서 `8-VA-0018` 재작업 이력을 검색하고 `취소 확정` 모달까지 진입한다.
  - 유효 단일 객체 효과를 가진 자식이 포함된 묶음과 잘못된 효과 객체를 가진 묶음을 각각 취소해, 확정 정책에 따른 정상 취소 또는 422 차단과 재고·취소 상태의 원자성을 확인한다.
  - 취소 뒤 입출고 내역, 격리 재고, 취소 사유·감사 기록을 함께 확인해 묶음의 일부만 남지 않았는지 검증한다.
- 우선순위: 높음

### 2. 취소 모달의 `Failed to fetch`를 사용자용 연결 오류로 전환하고 수동 재시도를 안내

- 화면/영역: 입출고 내역 > 재작업 묶음 상세 > `취소 확정` 모달.
- 증상:
  - 브라우저에서 취소 뒤 원본 영문 `Failed to fetch`가 그대로 노출됐다.
  - 프런트 공통 쓰기 요청은 `fetch` 네트워크 예외를 업무 오류와 구분하지 않아, 모달이 원문을 그대로 표시한다.
  - 프록시의 `localhost:8011` 연결 거절 이력은 있으나, 그 이력이 해당 클릭과 정확히 같은 시점인지는 아직 확정하지 않았다.
- 사용자 불편: 서버가 처리했는지, 다시 눌러도 되는지, PIN·권한 문제인지 알 수 없다.
- 정책 확인 필요 (대화 재시작으로 보류):
  - 응답 유실·연결 단절 뒤에는 자동 재시도를 하지 않고 사용자가 명시적으로 다시 시도할지 결정한다.
  - 앞선 선택은 재확인 전 확정으로 취급하지 않는다.
- 구현 방향:
  - 공통 쓰기 요청에서 연결 단절·시간 초과를 표준 오류로 변환하고, 취소 모달에는 "처리 여부를 확인한 뒤 다시 시도"하도록 안내한다.
  - 연결 오류, 권한/PIN 오류, 서버의 업무 규칙 오류를 서로 다른 한국어 문구와 동작으로 표시한다.
- 수용 기준:
  - 연결 단절에서 원본 `Failed to fetch`가 보이지 않고, 사용자가 다음 행동을 알 수 있다.
  - 자동 재시도로 이중 취소가 발생하지 않으며, 사유·PIN·대상은 사용자가 닫거나 다시 시도할 때까지 유지된다.
  - 403·422 같은 서버 응답은 연결 오류와 구별되어 표시된다.
- 브라우저 확인 시나리오:
  - 정상 취소, PIN/권한 오류, 422 업무 규칙 오류, 백엔드 연결 단절을 각각 확인한다.

- 우선순위: 높음

- 수용 기준:

### 10. 입출고 거래 표 네 모서리를 하나의 완결된 표면으로 맞춤

- 화면/영역: 데스크톱 입출고 내역(`/mes?tab=history`) > 사람이 하나의 거래 표로 보는 목록 외곽. 첫 열 `일시`·마지막 열 `담당자`가 있는 sticky 표 머리글의 좌·우 상단과, 현재 작업 영역에 보이는 좌·우 하단이 대상이다. 사용자가 실제 화면에서 표의 네 모서리 부근을 지적했으며, 내부 DOM 상자의 이름을 사용자가 구분할 필요는 없다. 수집 기준은 1920×910, `8-VA-0018` 재작업 묶음이 보이는 상태다.
- 증상:
  - 거래 목록 외곽 상단의 `rounded-[24px]` 곡선은 자연스럽게 보인다.
  - 그러나 `일시`와 `담당자`의 sticky `<th>` 배경은 사각형으로 끝나, 외곽 테두리의 양끝 곡선 위를 덮거나 곡선과 어색하게 만난다.
  - 데이터가 로딩 중일 때도 같은 표 구조를 별도로 렌더하므로, 한쪽 경로만 고치면 재진입 시 모서리 문법이 다시 달라질 수 있다.
  - 현재 작업 영역의 하단은 표의 실제 데이터 끝이 아니어서 좌·우 하단 곡선의 소유가 보이지 않거나 다른 외곽선과 어색하게 만난다. 이 높이 책임은 4번 항목과 연결된다.
- 사용자 불편: 표 전체는 둥근 업무 표면으로 인식되는데, 상단 머리글·하단 경계 중 일부가 사각형 또는 잘린 면처럼 보여 사람이 화면을 확인할 때 완결된 카드인지 판단하기 어렵다.
- 확정 정책:
  - 거래 표는 사람이 보는 하나의 외곽 표면으로서 좌·우 상단과 좌·우 하단이 모두 같은 곡선·경계 문법으로 완결되어야 한다.
  - 외곽 상단 곡선은 첫 번째와 마지막으로 보이는 sticky 머리글까지 끊기지 않고 이어져야 하며, 4번의 남은 높이 작업 영역 안에서 하단 곡선도 항상 보이는 상태를 목표로 한다.
  - `일시`·`담당자` 열의 너비, 열 머리글 배경·구분선, sticky 동작, 수평 반응형 숨김 규칙과 행 선택은 유지한다.
  - 이 변경은 표의 모서리·경계 소유만 다루며, 목록 전체를 새 카드로 중첩해 감싸거나 행·상태 배지 디자인을 바꾸지 않는다.
- 구현 방향:
  - 구현 전 `DesktopHistoryView`의 작업 영역과 `HistoryTable`의 외곽 표면 중 어느 요소가 사람이 보는 경계·반경·overflow clip을 하나만 소유해야 하는지 계산된 스타일과 실제 1920×910 화면으로 확인한다.
  - `HistoryTable`의 첫·마지막 표시 열에는 외곽 `rounded-[24px]`와 같은 상단 코너 반경을 적용하고, 일반 데이터 표와 `HistoryTableSkeleton`에 같은 규칙을 반영한다. 실제 표시되는 양끝 열을 기준으로 해 sticky 머리글이 스크롤 중에도 외곽 곡선을 덮지 않게 한다.
  - 4번 항목의 높이 체인과 함께, 목록 행만 내부 스크롤되고 외곽 하단 경계·곡선은 현재 작업 영역 끝에서 clip되게 한다. 표면을 중첩하지 않고 단일 소유자를 유지한다.
  - `HistoryTable.test.tsx`와 `DesktopHistoryView.scrollbar.test.tsx`에 일반·로딩 표의 양끝 머리글, 외곽 표면·내부 스크롤 소유, 기존 sticky·열 정의가 함께 유지되는 회귀 검증을 추가한다.
- 수용 기준:
  - 1920×910 입출고 내역에서 표 상단 왼쪽 `일시`와 오른쪽 `담당자` 배경이 외곽 테두리와 한 번의 연속된 곡선으로 보이며, 사각형 색 블록이 남지 않는다.
  - 현재 작업 영역 안에서 표의 좌·우 하단도 같은 외곽 곡선·경계로 완결되어, 데이터가 더 남아도 직선으로 잘리거나 다른 상자의 모서리와 충돌해 보이지 않는다.
  - 목록을 스크롤해도 네 모서리·배경·테두리가 깨지지 않고, 열 제목과 첫 번째 거래 행이 겹치지 않는다.
  - 로딩·데이터 있음·우측 상세 패널을 연 상태에서도 표 너비, sticky 머리글, 행 선택과 가로 넘침 동작이 기존처럼 유지된다.
- 브라우저 확인 시나리오:
  - 실제 인증된 `/mes?tab=history`를 1920×910으로 열고, 사용자가 지적한 표의 좌·우 상단·좌·우 하단을 한 화면에서 확인해 하나의 둥근 거래 표로 읽히는지 확인한다.
  - 목록을 중간·하단까지 스크롤하고 우측 상세 패널을 열어, sticky 머리글의 양끝 곡선, 하단 외곽 곡선, 열 정렬이 계속 유지되는지 확인한다.
  - 데이터 재조회 또는 로딩 상태에서도 같은 모서리 문법이 나타나는지 확인한다.
