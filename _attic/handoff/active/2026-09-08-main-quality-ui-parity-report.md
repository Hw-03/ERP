## 직원 관점 한 페이지 결론

고정 main과 품질 개선 버전을 서로 다른 합성 DB·포트·브라우저 세션에서 비교했다. 화면만 본 것이 아니라 로그인, 입력, 저장, 결재 요청·승인·반려·취소, 창고·부서 재고 이동, 생산·분해, 출하 준비·픽업·취소, 불량 처리와 관리자 CRUD를 실제 UI로 수행했다. 재고가 바뀌는 시험은 클릭 전 예상 수량, API 응답, 독립 SQL 전후 값, 화면·이력·원장을 함께 대조했다.

전체 206개 시나리오의 최종 분류는 **동일 177, 의도된 품질 개선 차이 21, 회귀 또는 불편 0, 미검증 8**이다. 확인한 범위에서 품질 버전이 직원의 기존 업무를 깨뜨리는 차이는 남아 있지 않다.

직원이 알 필요가 있는 차이는 다음과 같다.

- 잘못된 PIN은 명확한 오류로 구분하고, 연결 실패·서버 오류를 PIN 오류로 오인시키지 않는다.
- 일반 세션은 마지막 사용자 활동 후 30분에 잠긴다. 29분에 경고와 `로그인 유지`가 표시되며, 자동 조회는 시간을 연장하지 않는다.
- 만료 시 미저장 입력은 가린 뒤 같은 직원이 재인증한 경우에만 현재 탭 메모리에서 복구한다.
- 창고 담당자는 창고 결재, 부서 담당자는 담당 부서 결재, 두 역할 겸임자는 둘 다 처리할 수 있다. 역할 없는 직원과 관리자 인증만 한 직원은 결재 권한을 얻지 않는다.
- 인수인계 작성 화면이 없는 부서의 직접 API 작성도 차단한다.
- 대시보드 전체 카드에 `출하 중간 공정·공정 완료 품목 제외`가 표시되고, 목록 위의 별도 설명 행은 제거됐다.

실제 벽시계 30분 대기는 사용자 결정으로 생략했다. 대신 제어된 서버 시간과 +31분 절전 복귀 조건에서 잠금, 다중 탭 동기화, 활동 연장, 자동 조회 제외를 검증했다. 실물 모바일 센서·카메라·운영체제 인쇄 대화상자와 외부·직원 서버 연동은 보호 조건 또는 장비 부재로 실행하지 않았다. 이 항목들은 검증표에 이유와 함께 남겼다.

품질 후보는 GitHub의 독립 PostgreSQL 16에서 필수 두 연결 잠금·경합 게이트를 통과했다. 고정 main의 동일 PostgreSQL A/B 실행은 하지 않았으므로 해당 비교 행 자체는 미검증으로 유지한다. SQLite 결과를 PostgreSQL 통과로 대신하지 않았다.

기존 후보 뒤 main에 추가된 5개 커밋을 모두 검토해 최신 main `76a56416…`을 품질 브랜치에 정상 병합했다. 출하 취소 재처리, BOM 1EA 증분, 출하 재진행 배포 검증, B급·구형 자재 관리와 자동 부서 라우팅, 불량 화면 번들 예산을 유지하면서 품질 버전의 세션·권한·재고 안전장치를 함께 보존했다. 34개 내용 충돌을 기능별로 해결했고 최종 후보는 `94afc622…`이다.

## 주요 실제 업무 결과

### 로그인·세션

성공·실패·잘못된 PIN, 연결 거절·지연·재시도, 새로고침 복원, 다른 탭 로그인·로그아웃 전파, 세션 만료, 관리자 인증, 로그아웃 응답 유실을 비교했다. 품질 버전은 서버가 확인한 `expires_at`을 기준으로 활동을 갱신하며, 만료·폐기 세션을 늦은 활동 요청으로 되살리지 않는다. 클릭·키보드·스크롤은 활동이고 자동 조회와 단순 탭 활성화는 활동이 아니다. 관련 구현은 `backend/app/services/operator_session.py:18-19,136-190`, `backend/app/routers/operator_sessions.py:418-436`, `frontend/app/mes/_components/login/useOperatorIdleSession.ts:16-196`이다.

### 결재·권한

창고 담당만, 부서 담당만, 겸임, 역할 없음의 네 조합에서 메뉴·건수·목록·상세·승인·반려 API를 대조했다. 직접 URL·API 우회도 같은 권한표로 차단됐다. 관리자 인증만으로 업무 결재 권한이 생기지 않았고, 요청자의 본인 요청 조회·취소는 유지됐다. 관련 구현은 `backend/app/routers/stock_requests.py:227-405,558-571,675-728`이다.

### 입출고·재고

창고/부서 입출고, 부서 이동, 자동 부서 지정, 여러 부서가 섞인 요청, BOM, 생산·분해, 자가승인·일반승인·반려·취소를 UI에서 실행했다. 확장 시나리오에서 양쪽 모두 요청 8건(완료 4·반려 2·취소 2), batch 8건, transaction 8건, 중복 client request ID 0이었고 최종 재고가 초기값으로 돌아왔다.

stale 부족 시험에서는 다른 UI 요청이 마지막 가용 1개를 먼저 예약한 뒤 오래 열린 요청을 제출했다. 양쪽 모두 422로 거절되고 대상 요청·batch·거래·재고 변화가 없었다. 품질의 처리 완료 후 응답 유실 재시도는 원 batch를 조회해 복구하며 수량을 두 번 반영하지 않았다.

### 출하

생성·검색·더보기, 준비·픽업, 각 취소, 구성품 변경, 예약·실재고·상태·이력을 확인했다. 경쟁 출하가 출하 위치 10개를 먼저 예약한 뒤 대상 준비를 누르면 422로 거절되고 대상 allocation·event·operation·거래·재고가 변하지 않았다. 고정된 5단계 카드 높이·2열·내부 스크롤도 유지됐다.

### 불량·보고서·관리자

불량 격리·정상 복귀·다건 처리·폐기·반품·분해, 통계 기간·검색·분류, 실패 후 선택 유지와 재시도를 확인했다. 일일작업일보의 작성자·날짜·탭·상세 전환과 저장·수정·취소, 주간보고·체크리스트, 창고지도와 관리자 CRUD도 실행했다. 삭제·보정·복구는 폐기 가능한 합성 데이터에서만 수행했다.
