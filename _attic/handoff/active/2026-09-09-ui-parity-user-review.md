## 로그아웃 회귀 수정 및 재검증

- IO-22 응답 유실 후 재제출: 기존 `io-response-loss/main-after-retry.png`, `quality-after-retry.png`와 results.json을 제시한 뒤 사용자가 품질 방식 유지를 승인했다. 현재 개발 3001에서 재현한 것으로 간주하지 않는다.
- IO-27 창고 담당 부서 승인함: 기존 `io-approval/main-approval-queue.png`, `quality-approval-queue.png`에서 같은 합성 창고 정담당의 상단 탭 차이를 확인하여 사용자 확인 대상으로 제시한다.

- IO-20 정정: 개발에서도 재고 0개에 1개를 요청하도록 수량 화면을 맞췄고 품질의 재고 1개에 2개 요청과 동일한 부족 안내·제출 비활성화를 확인했다. 기존 연결 증거에는 제출 422와 문구 차이가 없어 의도된 차이 판정을 철회한다. 제출 직전 재고 감소가 원인이라는 이전 설명도 확인되지 않은 추정이므로 철회한다. 이 항목의 제출 시점 동등성은 미검증으로 남긴다. 사용자에게 불필요한 선택을 요구하지 않는다.

- 원인: DELETE 204 성공 후 세션 재조회 GET 401이 인증 이벤트를 발생시키면서 순번이 변경되어 재조회 catch 처리가 무효화됐다. 인증 이벤트 처리에서는 이전 pending boundary를 다시 유지하여 실제 미완료 표식이 없어도 로그인을 막았다.
- 수정: `frontend/app/mes/_components/login/MesLoginGate.tsx:136`에서 인증 필요 이벤트 발생 시 실제 미완료 로그아웃 표식으로만 로그인 차단 여부를 판단한다. 서버 로그아웃 실패 표식이 남은 경우에는 계속 차단한다.
- 검증: 실제 인증 이벤트를 발생시키는 회귀 테스트가 수정 전 실패하고 수정 후 통과했다. MesLoginGate/useCurrentOperator/api-operator-session 관련 42개 테스트 통과. production build 통과 (`_attic/runtime/ui-parity-20260908-155732/logs/build/quality-logout-fix.log`).
- 실제 인앱 브라우저 재검증: 김현우 로그인 → 동일 품질 서버 새 탭에서 로그인 유지 → 새 탭 로그아웃 확인창 승인 → 양쪽 탭 모두 오류 없이 입력 가능한 로그인 화면으로 복귀. 직원 서버는 조작하지 않았다.
- 품질 전용 실행은 `manual-review2` 프로세스 영수증에 기록했다. 화면 확인을 이어가기 위해 품질 전용 서버는 유지 중이다. commit/push/merge/deploy는 하지 않았다.
