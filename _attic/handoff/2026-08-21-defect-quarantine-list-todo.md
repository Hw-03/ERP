## 불량

### 1. 격리 수량을 행의 독립 강조 정보로 표시

- 화면/영역: 데스크톱 불량 > 격리 목록 > 부서별 품목 행의 수량·격리 날짜·처리자 메타데이터.
- 증상: 현재 수량이 `5개 격리 2026-07-01 · 김건호`처럼 날짜·처리자와 한 줄로 이어져 있어 목록을 훑을 때 격리 수량이 눈에 띄지 않는다.
- 사용자 불편: 처리 우선순위와 작업량을 판단할 핵심 수량을 메타데이터 속에서 다시 찾아야 한다.
- 확정 정책: 격리 수량은 날짜·처리자와 분리된 시각 단위로 표시해 한눈에 읽힌다. 날짜·처리자와 처리 버튼의 기존 정보·역할은 유지한다.
- 구현 방향: 행의 정보 위계를 품목 식별, 강조된 수량, 격리 일자·처리자, 사유·메모 순으로 재배치한다. 수량만 장식용 배지로 과도하게 만들지 않고, 모든 행에서 일관된 크기·대비로 표시한다.
- 수용 기준:
  - 각 격리 행에서 수량이 날짜·처리자 문자열과 분리되어 즉시 식별된다.
  - `1개`와 여러 개 수량이 실제 격리 건 수량과 일치한다.
  - 품목명, 격리 일자, 처리자, 사유·메모, 처리 버튼이 겹치거나 잘리지 않으며 기존 처리 동선은 유지된다.
- 브라우저 확인 시나리오: 데스크톱 `/mes?tab=defect`에서 수량이 서로 다른 여러 격리 행을 확인한다 → 수량이 날짜·처리자와 분리되어 읽히는지 확인한다 → 긴 품목명·긴 메모가 있는 행에서도 정보와 `처리` 버튼이 겹치지 않는지 확인한다 → 필터·정렬·처리 진입 후 목록 복귀 동작을 확인한다.
- 우선순위: 높음

### 2. 격리 건 메모 수정 기능 제공

- 화면/영역: 데스크톱 불량 > 격리 목록 > 각 격리 행의 `사유 ... · 메모` 표시 영역.
- 증상: 격리 사유와 함께 표시되는 메모가 읽기 전용이라, 보관 상태 변화나 추가 설명을 해당 격리 건에 보완할 수 없다.
- 사용자 불편: 후속 처리자가 최신 상황을 알기 위해 별도 경로로 전달받아야 하며, 격리 기록의 맥락이 화면에 남지 않는다.
- 확정 정책: 각 격리 건의 메모는 목록에서 수정할 수 있어야 하며, 수정 결과는 새로고침 후에도 해당 건에 유지된다. 격리 사유 자체와 수량·일자·처리 단위는 메모 수정으로 바꾸지 않는다.
- 정책 확인 필요: 메모 수정 권한을 격리 등록자만 허용할지, 해당 부서의 권한 사용자에게 허용할지와 수정 이력(최종 수정 시각·수정자)을 남길지 결정한다.
- 구현 방향: 행의 메모 표시에서 해당 건을 식별해 편집 모드·저장·취소를 제공하고, 저장 중복 실행과 저장 실패를 사용자에게 명확히 알린다. 기존 불량 처리 권한·거래 기록 모델과 충돌하지 않도록 메모 변경의 API·감사 범위를 정한다.
- 수용 기준:
  - 사용 권한이 있는 사용자가 특정 격리 행의 메모를 수정·저장·취소할 수 있다.
  - 저장한 메모는 해당 격리 건에만 반영되고, 같은 품목의 다른 격리 건 메모는 바뀌지 않는다.
  - 빈 메모 처리, 저장 중 중복 클릭 방지, 저장 실패 안내가 정해진 정책에 맞게 동작한다.
  - 격리 사유·수량·일자·처리 버튼과 기존 복귀·폐기·반품 처리 흐름은 유지된다.
- 브라우저 확인 시나리오: 메모가 있는 격리 행과 빈 메모 행을 각각 연다 → 메모를 수정하고 저장한 뒤 목록을 새로고침해 값이 유지되는지 확인한다 → 저장 전 취소, 저장 중 중복 클릭, 저장 실패 응답을 확인한다 → 같은 품목의 다른 격리 건과 처리 버튼을 확인해 의도치 않은 변경이 없는지 확인한다.
- 우선순위: 높음

### 3. 동일 품목의 격리 기록을 건별 행으로 유지

- 화면/영역: 데스크톱 불량 > 격리 목록 > 부서별 품목 목록과 각 행의 `처리` 진입.
- 증상: 같은 품목을 다른 날짜에 여러 번 격리했을 때 현재 목록이 품목 단위로 합쳐질 수 있어, 각 격리 기록을 분리해 확인·처리할 수 없다.
- 사용자 불편: 서로 다른 격리 사유·메모·일자·수량을 하나의 재고처럼 오해할 수 있고, 처리 시 어느 격리 건을 대상으로 하는지 판단하기 어렵다.
- 확정 정책: 동일 품목이라도 격리 기록이 서로 다르면(다른 일자·거래·메모·사유 등) 각 기록을 별도 행으로 유지하며, 각 행은 독립적으로 후속 처리한다. 품목별 합계가 필요한 KPI·요약은 기존 목적에 맞게 별도로 유지한다.
- 구현 방향: 격리 목록의 조회·표시 단위를 현재 품목 집계가 아니라 고유 격리 거래/기록 단위로 맞추고, 행의 `처리` 동작도 선택한 기록의 수량·메모·사유만 대상으로 전달한다. 동일 품목의 여러 행은 일자와 기록 식별 정보로 구분 가능하게 정렬·표시한다.
- 수용 기준:
  - 같은 품목을 서로 다른 날짜에 격리한 기록은 각각 별도 행으로 보인다.
  - 각 행에는 자신의 수량·격리 일자·처리자·사유·메모가 정확히 표시된다.
  - 한 행을 처리해도 다른 격리 행의 수량·메모·처리 가능 상태가 변경되거나 함께 소진되지 않는다.
  - 부서 필터, 격리자 필터, 정렬, 1년 초과 경고 및 KPI의 집계 기준은 명시적으로 보존·검증된다.
- 브라우저 확인 시나리오: 같은 품목을 다른 날짜·수량·사유로 두 번 이상 격리한 데이터를 준비한다 → 목록에서 각 기록이 별도 행인지, 각 행의 정보가 맞는지 확인한다 → 한 행만 복귀·폐기·반품 처리한 뒤 다른 행이 그대로 남고 처리 가능한지 확인한다 → 부서/격리자 필터와 최신순·오래된순 정렬, 1년 초과 경고·KPI 합계를 비교한다.
- 우선순위: 높음

### 4. 넓은 격리 목록 행을 정보 구획형 레이아웃으로 재구성

- 화면/영역: 데스크톱 불량 > 격리 목록 > 부서별 격리 행의 전체 가로 폭과 우측 `처리` 버튼 전 영역.
- 증상: 데스크톱 목록 행은 넓은 가로 폭을 사용하지만 품목명·수량·일자·처리자·사유·메모가 좌측의 짧은 세로 텍스트 묶음에만 모여 있고, 우측 공간은 대부분 비어 있다.
- 사용자 불편: 행마다 쓸 수 있는 공간에 비해 정보가 조밀하게 쌓여 수량·사유·메모를 빠르게 훑기 어렵고, 행 사이의 정보 비교도 느리다.
- 확정 정책: 데스크톱 격리 행은 넓은 가로 폭을 적극 사용해 품목 식별, 강조 수량, 격리 일자·처리자, 사유·메모를 명확한 가로 구획으로 배치한다. 우측 `처리` 버튼은 현재처럼 즉시 접근 가능하게 유지하며, 모바일·좁은 폭에서는 안전하게 세로 배치로 전환한다.
- 구현 방향: 고정된 넓은 화면에서 행을 다열 정보 블록 또는 좌·중·우 영역으로 나누고, 메모는 남는 폭을 사용해 불필요하게 일찍 줄바꿈되지 않게 한다. 1번 수량 강조와 2번 메모 편집, 3번 건별 행 정책을 같은 행 레이아웃에 일관되게 결합하며 긴 품목명·메모의 말줄임/줄바꿈 규칙을 명시한다.
- 수용 기준:

  - 품목명, 수량, 격리 일자·처리자, 사유·메모, 처리 동작의 우선순위와 구분이 한눈에 보인다.
  - 긴 품목명·긴 메모에서도 다른 열·처리 버튼을 밀거나 가리지 않고, 필요한 경우 정해진 규칙으로 줄바꿈 또는 말줄임된다.
