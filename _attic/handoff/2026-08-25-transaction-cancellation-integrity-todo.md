## 확정된 취소 계약

### 공통 작업 원장과 역전 작업

- 모든 신규 사용자 작업은 공통 `InventoryOperation` 하나를 만들고, 해당 작업이 생성한 모든 `TransactionLog`, 불량 이동, 예약·배정 변화와 업무 소유 상태가 같은 `operation_id`를 공유한다.
- `InventoryOperation`은 최소한 `operation_id`, 작업 종류, 업무 종류, 실행 상태, 처리자·부서, 사유, `effective_at`, 생성 시각과 멱등 요청 키를 가진다.
- 취소는 새 `InventoryOperation(kind=CANCELLATION)`을 만들고 `reverses_operation_id`로 원 작업을 참조한다. `reverses_operation_id`에는 고유 제약을 둬 한 원 작업에 성공한 취소가 하나만 존재하게 한다.
- 취소 작업은 원 작업의 각 재고 효과와 불량 이동을 반대로 기록하는 새 로그를 가진다. 각 역전 로그에는 취소 직전 재고를 `before`, 취소 직후 재고를 `after`로 새로 저장한다.
- 원 작업의 거래 수량·재고 스냅샷·처리자·시각은 수정하지 않는다. 원 작업의 `REVERSED` 상태는 연결된 성공 취소 작업의 존재로 투영한다.
- 기존 `TransactionLog.cancelled*` 필드는 과거 데이터 호환용으로만 유지한다. 신규 취소의 단일 근거는 원 작업과 `CANCELLATION` 작업의 연결이다.
- 취소 작업 자체의 취소, 취소의 취소, 부분 수량과 부모·자식 일부 취소는 지원하지 않는다.

### 현재 주 거래

- KST 월요일 00:00을 주차 경계로 삼고 원 작업과 취소 작업이 같은 주에 속할 때만 취소를 허용한다.
- 후속 거래가 있다는 사실만으로 취소를 막지 않는다. 로트 추적이 없는 현재 수량재고에서는 같은 품목·위치의 재고를 동등하게 취급한다.
- 산출품이 사용됐더라도 취소 시점에 같은 품목·위치의 동등 가용재고가 충분하면 전체 작업을 원자적으로 역전한다.
- 정상·불량재고가 음수가 되거나 예약·활성 출하배정을 침범하거나 불량 원장 잔량이 성립하지 않으면 취소 작업을 남기지 않고 전체 실패한다.
- 사전검사 결과와 실행 결과는 품목·위치·정상/불량 구분·수량별로 같아야 하며 실행 트랜잭션 안에서 다시 검증한다.
- 동시 취소 요청은 잠금과 고유 역전 관계로 정확히 하나만 성공한다.
- 가용재고 부족 안내는 다음 문구로 통일한다.

> **현재 재고가 부족하여 취소할 수 없습니다. 현재 재고를 확인한 뒤 다시 시도해 주세요.**

### 지난 주 이전 거래

- 지난 주 이전 원 작업은 마감된 주간보고와 스냅샷을 바꾸므로 소급 취소하지 않는다.
- 지난 주 차단 경로에서는 `CANCELLATION` 작업, 반대 거래, 자동 보정, 입력값과 업무 상태를 하나도 만들거나 변경하지 않는다.
- 기존의 제한적 `RECEIVE`·`SHIP` 수량 보정 API를 일반 자동 보정 엔진으로 확대하지 않는다.
- 모든 거래 유형에 같은 안내를 표시한다.

> **지난 주 내역은 취소할 수 없습니다.**
>
> 현재 재고를 맞추려면 입출고 탭에서 낱개 입고·출고를 진행해 주세요.

- 안내창은 `입출고로 이동`과 `닫기`만 제공한다. 화면을 이동하더라도 품목·수량·사유를 자동 입력하거나 저장하지 않는다.
- 과거 불량·재작업 기록과 활성 불량 원장은 보존한다. 이후 처리는 정상복귀·재작업·폐기 등 현재 주의 정상 업무로 새로 기록한다.

### 연결 업무 상태

- 취소 성공 시 재고, 예약, 출하배정과 불량 원장은 원 작업의 반대 효과로 역전한다.
- 완료된 `IoBatch`, `StockRequest`, `ShippingRequest`, 인계 문서 같은 업무 소유 엔터티는 이전 `대기·승인·진행` 상태로 되살리지 않고 최종 `취소됨`으로 닫는다.
- 취소된 업무를 다시 수행하려면 새 요청 또는 새 작업을 생성한다. 기존 요청을 재활성화하지 않는다.
- 업무별 취소 어댑터가 소유 상태·배정·예약·불량 원장을 검증하고 같은 DB 트랜잭션에서 닫는다. 전용 규칙이 없는 업무는 일부만 역전하지 않고 안전하게 실패한다.

### 전향 적용과 기존 데이터

- 직원 서버 동기화에서 정합성 진단을 통과하면 신규 작업 원장과 역전 작업을 즉시 활성화한다. 검증된 새 주간보고 기준은 다음 KST 월요일 00:00부터 활성화한다.
- 적용 전 `TransactionLog`와 기존 `cancelled` 데이터는 자동으로 `InventoryOperation`에 끼워 맞추거나 취소 작업을 역생성하지 않는다.
- 이미 기존 방식으로 취소된 건은 변환하지 않고 기존 표시를 유지한다. 방금 취소한 2026-08-25 14:17 테스트 건도 그대로 둔다.
- 원장 활성화 뒤 아직 취소되지 않은 같은 주 레거시 거래를 취소하면 `operation_batch_id`, 지원되는 출하 참조 묶음, 단일 로그 순으로 범위를 잠근다. 전체 로그의 재고 효과·역할·처리자·연결 업무를 확정할 수 있을 때만 원래 시각의 `BUSINESS` 작업으로 편입하고 즉시 별도 `CANCELLATION` 역전 작업을 생성한다.
- 레거시 원 작업에는 `legacy-cancel-source:<scope>` 멱등 키를 기록하고 `PRODUCE→PRODUCT_OUTPUT`, `BACKFLUSH→COMPONENT_INPUT`, 이동→`TRANSFER`, 조정→`CORRECTION`, 일반 입출고·내부사용→`PRIMARY` 역할을 부여한다. 원 로그의 `cancelled*` 필드는 변경하지 않는다.
- 같은 묶음의 일부가 이미 취소됐거나 일부만 새 원장에 연결됐거나 재고 효과·처리자·연결 요청을 확정할 수 없으면 편입 흔적과 재고 변화 없이 전체 실패한다. 불량·정상복귀·재작업·폐기·반품처럼 기존 불량 원장 연결을 확정할 수 없는 거래도 같은 방식으로 차단한다.
- 불량·재작업 레거시 차단 문구는 `전환 전에 생성된 불량·재작업 내역은 안전하게 취소할 수 없습니다. 현재 불량 상태를 확인한 뒤 새 작업으로 처리해 주세요.`로 고정한다. 그 밖의 효과 불명확 건은 `전환 전 작업의 전체 재고 영향을 확인할 수 없어 취소할 수 없습니다. 현재 재고를 확인한 뒤 새 작업으로 처리해 주세요.`로 고정한다.
- 새 원장이 활성화되지 않은 호환 환경에서만 기존 직접 원복 경로를 유지한다. 지난 주 이전 레거시 거래는 편입하지 않고 기존 확정 문구로 차단한다.
- 주중 전환 주에는 다음 안내를 크게 표시하고 기존 보고를 유지한다.

표시 열 제목은 아래 문구로 고정한다.

`전주 재고 | 생산 | 입고 | 출고 | 불량 | 현재 재고 | 증감`

- 주간보고는 기존처럼 F 품목만 행으로 만든다. R·A는 현재 코드상 집계 행이 없으므로 별도 제외 로직이나 표시 정책을 추가하지 않는다.
- `전주 재고`와 `현재 재고`는 창고와 `PRODUCTION` 위치에 실제 존재하는 F 정상재고다.
- `DEFECTIVE` 위치는 정상재고에서 제외한다. 예약은 물리 이동이 아니므로 정상재고에서 차감하지 않는다.
- 화면의 각 칸은 합계 숫자 하나만 표시한다. 낱개 입출고·복귀·재작업 회수·신규 불량과 취소 짝 같은 근거 구분은 API와 상세 내역에서 제공한다.

### 활동 열 분류

| 표시 열 | 포함하는 정상재고 효과 |
|---|---|
| `생산` | 이번 주 BOM 생산으로 생성된 F 수량 |
| `입고` | 낱개 입고, 정상복귀, 증가 조정, 재작업에서 회수된 모든 F 결과품 |
| `출고` | 낱개 출고, 출하, BOM 투입·백플러시, 내부사용, 감소 조정 |
| `불량` | 정상 F가 처음 격리·직접 재작업·직접 폐기된 수량, 재작업에서 새로 나온 불량·폐기 F 결과품 |

- 정상 부모의 직접 재작업은 `불량`에만 집계하고 `출고`에는 다시 집계하지 않는다.
- 이미 불량으로 집계된 같은 품목을 후속 재작업하거나 폐기할 때는 그 품목의 `불량`을 다시 늘리지 않는다. 상태 전이와 처리 이력은 불량 상세 원장에만 남긴다.
- 재작업에서 나온 정상 F 자식은 `입고`에만 집계한다.
- 재작업에서 새로 나온 불량·폐기 F 자식은 정상재고를 경유하지 않되 보고상 `입고 +수량`과 `불량 +수량` 근거를 동시에 만든다.
- 지난주부터 불량이던 F를 이번 주 정상복귀하면 `입고`에 집계한다.
- 회수 자재를 사용해 F를 다시 만들면 새 F는 일반 BOM `생산`으로 집계한다.
- 같은 주의 원 작업과 성공 취소 작업은 `reverses_operation_id`로 짝지어 `생산·입고·출고·불량`에서 둘 다 제외한다. 취소 역전 수량을 별도 입고·출고·수량조정 실적으로 집계하지 않는다.
- 서로 다른 F 공정 단계에서 같은 실물 계보가 각각 불량으로 보일 수 있으므로 품목·공정별 불량 합계를 고유 불량 실물 총개수로 해석하는 별도 KPI는 만들지 않는다.

### 부호와 복식 검산

- `전주 재고·생산·입고·출고·불량·현재 재고`는 항상 0 이상이어야 한다.
- `증감`만 증가 `+`, 감소 `-`, 동일 `±0`으로 표시한다.
- 모든 F 품목 행, 공정 합계와 전체 합계에서 아래 두 식이 동시에 성립해야 한다.

```text
증감 = 현재 재고 - 전주 재고
증감 = 생산 + 입고 - 출고 - 불량
```

- 증감 이외 열에서 음수가 계산되거나 정상재고 효과가 어떤 활동 열에도 분류되지 않거나 두 식의 차이가 0이 아니면 해당 보고를 공개하지 않는다.
- 이 경우 0 또는 빈칸으로 대체하지 않고 품목·작업·원인 거래와 검산 차이를 포함한 구조화된 `집계 검산 실패`를 표시한다.

### 대표 수치 예시

| 상황 | 해당 F 품목의 이번 주 표시 | 검산 |
|---|---|---|
| 정상 VF 1개 직접 재작업 후 VF 1개 재생산 | `생산 1 · 불량 1 · 증감 ±0` | `1 + 0 - 0 - 1 = 0` |
| NF 재작업에서 정상 VF 1개 회수 | `입고 1 · 증감 +1` | `0 + 1 - 0 - 0 = 1` |
| NF 재작업에서 불량 VF 1개 회수 | `입고 1 · 불량 1 · 증감 ±0` | `0 + 1 - 0 - 1 = 0` |
| 지난주부터 격리된 VF를 이번 주 재작업·폐기 | VF 추가 `불량 0 · 증감 ±0` | 이미 지난주 정상재고에서 제외됨 |
| 지난주 불량 VF 1개를 이번 주 정상복귀 | `입고 1 · 증감 +1` | `0 + 1 - 0 - 0 = 1` |
| 같은 주 부서 출고 7개를 취소 | 원 작업·취소 작업 모두 활동 열에서 제외, `증감 ±0` | 원 작업 `-7`과 역전 작업 `+7`이 재고에서 상쇄됨 |

## 입출고 취소

### 1. 공통 `InventoryOperation`과 별도 취소 역전 작업 도입

- 구현 상태: 완료

- 화면/영역: 모든 재고·불량·생산·입출고·출하·인계 작업의 생성, 상세와 취소 API.
- 증상: 현재 취소는 원 거래 로그의 `inventory_effect`를 반대로 적용하고 `cancelled` 상태를 덮어써 수량 원복 자체는 가능하지만, 취소라는 새 업무 사실과 반대 방향 품목별 내역이 남지 않는다.
- 사용자 불편: 실제로 재고가 돌아온 이유를 독립된 행으로 확인할 수 없고, 대시보드·주간보고·연결 업무가 각자 원 로그의 취소 상태를 다르게 해석할 수 있다.
- 확정 정책: 신규 사용자 작업은 공통 `InventoryOperation`을 만들며 취소는 원 작업을 수정하는 명령이 아니라 원 작업을 참조하는 별도 `CANCELLATION` 작업이다. 한 원 작업에는 취소 작업 하나만 허용하고 취소 작업의 취소와 부분 취소는 금지한다.
- 구현 방향: `InventoryOperation`과 `TransactionLog.operation_id`를 추가하고, 취소 작업에 고유 `reverses_operation_id`, 멱등 요청 키, 사유·처리자·부서·취소 시각을 저장한다. 원 작업의 각 재고 효과를 반대로 기록하는 새 거래 로그를 만들고 당시 취소 직전·직후 재고를 저장한다. 원 작업의 `REVERSED`는 연결 관계로 투영한다.
- 수용 기준:
  - 신규 작업의 부모·자식·정상/불량 이동과 업무 상태 효과가 하나의 `operation_id`에 속한다.
  - 취소 뒤 원 작업 로그의 수량·당시 재고·작업자·시각은 바뀌지 않고 반대 수량의 취소 작업이 별도로 존재한다.
  - `reverses_operation_id`와 멱등 키 고유 제약으로 순차·동시 중복 취소 작업이 생성되지 않는다.
  - 취소 작업이나 묶음 일부에 다시 취소를 요청하면 어떤 데이터도 변경되지 않는다.
- 브라우저 확인 시나리오: 낱개 입출고, BOM 생산과 다품목 부서 입출고를 각각 생성한다 → 상세에서 취소한다 → 원 작업과 `○○ 취소` 작업이 별도 행으로 남고 각 부모·자식 수량이 정확히 반대인지 확인한다.
- 우선순위: 높음

### 2. 현재 주 취소와 지난 주 일괄 차단을 서버 계약으로 고정

- 구현 상태: 완료

- 화면/영역: 입출고 내역 > 거래 상세 > 취소 확인창, 취소 사전검사·실행 API.
- 증상: 거래 주차 판정이 모든 업무 취소 경로에 공통으로 적용되지 않으면 과거 주 활동은 그대로 둔 채 현재 재고만 움직여 주간 검산이 깨질 수 있다.
- 사용자 불편: 같은 취소 버튼인데 업무 유형에 따라 과거 내역이 취소되거나 문구가 달라질 수 있고, 마감된 주간보고의 의미를 신뢰할 수 없다.
- 확정 정책: KST 기준 현재 주의 원 작업만 취소한다. 지난 주 이전 원 작업은 모든 거래 유형에서 차단하고 확정 안내와 `입출고로 이동`·`닫기`만 제공한다. 지난 주 차단은 취소 작업·자동 보정·자동 입력·자동 저장을 만들지 않는다.
- 구현 방향: KST 주차 경계 판정을 단일 서버 함수로 사용하고 사전검사와 실행 API에서 동일하게 적용한다. 안정적인 오류 코드와 확정 문구를 반환하며 프런트 조건만으로 허용 여부를 결정하지 않는다.
- 수용 기준:
  - 일요일 23:59:59.999999 KST 원 작업은 다음 주에 취소할 수 없고 월요일 00:00:00 KST 원 작업은 같은 주에 취소할 수 있다.
  - 지난 주 입고·출고·생산·BOM 사용·격리·복귀·재작업·폐기·출하가 모두 같은 문구로 차단된다.
  - 차단 요청 뒤 `InventoryOperation`, 거래 로그, 재고, 불량 원장과 연결 업무 상태가 모두 불변이다.
  - `입출고로 이동`은 화면만 이동하며 어떤 값도 자동 입력하거나 저장하지 않는다.
- 브라우저 확인 시나리오: 이번 주 거래와 지난 주 각 거래 유형을 열어 취소한다 → 이번 주는 영향 미리보기 뒤 취소 작업이 생기고 지난 주는 확정 안내만 보이는지 확인한다 → 새로고침 뒤 지난 주 데이터가 불변인지 확인한다.
- 우선순위: 높음

### 3. 작업 전체 가용량·예약·배정·동시성 사전검사

- 구현 상태: 완료

- 화면/영역: 모든 현재 주 취소의 사전검사 API, 실행 API와 오류 안내.
- 증상: 현재는 일부 재고 셀과 예약을 검사하지만 작업 전체의 정상·불량재고, 활성 출하배정, 불량 원장 잔량과 동시 요청을 하나의 역전 조건으로 검증하지 않는다.
- 사용자 불편: 사용 가능한 것으로 보인 수량이 실제로는 예약돼 있거나, 빠른 중복 실행으로 재고와 업무 상태가 두 번 역전될 수 있다.
- 확정 정책: 후속 거래 자체는 차단 사유가 아니다. 같은 품목·위치의 동등 가용재고로 작업 전체 역전이 가능할 때 허용한다. 정상·불량재고 음수, 예약·활성 출하배정 침범, 불량 원장 불일치 중 하나라도 있으면 전체 실패한다. 동시 요청은 하나만 성공한다.
- 구현 방향: 사전검사가 작업 전체의 품목·위치별 현재수량·가용량·예약·배정·불량 원장과 연결 업무 효과를 반환하게 한다. 실행 시 원 작업, 업무 소유 행과 재고 셀을 일관된 순서로 잠그고 트랜잭션 안에서 재검사한 뒤 취소 작업을 원자적으로 생성한다.
- 수용 기준:
  - 산출품을 사용한 뒤 같은 품목·위치에 동등 수량이 재입고된 경우 전체 가용량이 충분하면 취소된다.
  - 가용량이 부족하거나 예약·배정을 침범하면 확정된 부족 문구를 표시하고 모든 테이블이 불변이다.
  - 같은 작업의 동시 취소 두 건 중 정확히 하나만 성공하고 나머지는 충돌 응답을 받는다.
  - 사전검사 미리보기와 실제 커밋 영향이 품목·위치·정상/불량 구분·수량별로 일치한다.
- 브라우저 확인 시나리오: 산출품 사용 후 동일 품목을 재입고한 경우, 수량 부족·예약·출하배정이 있는 경우를 각각 취소한다 → 취소 버튼을 빠르게 중복 실행한다 → 성공·차단 문구와 새로고침 뒤 재고를 대조한다.
- 우선순위: 높음

### 4. 불량 이동 원장과 물리 불량재고를 함께 역전

- 구현 상태: 완료

- 화면/영역: 불량 격리, 정상복귀, 재작업, 폐기, 공급업체 반품과 각 작업의 취소.
- 증상: `DefectQuarantineRecord.remaining_quantity`가 일반 취소와 함께 역전되지 않아 활성 불량 원장 합계와 `DEFECTIVE` 위치 수량이 달라질 수 있다.
- 사용자 불편: 재고가 없는 유령 불량 건을 처리하거나 실제 불량재고는 있지만 선택할 원장이 없는 상태가 생긴다.
- 확정 정책: 불량 원장은 삭제·덮어쓰기 대신 격리, 정상복귀, 재작업, 폐기, 자식 불량 생성과 취소 역전을 누적 기록한다. 현재 주 취소는 부모 원장 잔량 복구와 자식 원장 역전을 물리 재고와 같은 트랜잭션에서 수행하며 과거 기록은 보존한다.
- 구현 방향: 불량 이동 원장에 `operation_id`, 원본 이동 ID, 역전 대상 ID, 역할, 품목, 부서·위치, 수량과 처리자를 기록한다. 취소 작업은 원본 이동을 참조하는 반대 항목을 추가한다. `품목·부서별 활성 불량 원장 잔량 합 = 실제 DEFECTIVE 위치 수량` 불변식을 런타임과 진단에 추가한다.
- 수용 기준:
  - 격리 취소는 정상 위치와 불량 위치를 함께 역전하고 원 격리 이동의 취소 관계를 보존한다.
  - 정상복귀·재작업·폐기·반품 취소는 원 기록 잔량과 물리 불량재고를 함께 복구한다.
  - 재작업 취소는 부모 잔량을 복구하고 해당 작업이 만든 자식 불량 이동만 역전한다.
  - 성공·실패·동시 요청 뒤에도 활성 불량 원장 합계와 불량 위치 수량이 항상 같다.
- 브라우저 확인 시나리오: 같은 품목의 격리 건 두 개를 만든다 → 한 건에서 복귀·재작업·폐기·반품을 각각 수행하고 같은 주에 취소한다 → 선택한 원장만 역전되고 목록 합계와 불량 위치 수량이 같은지 확인한다.
- 우선순위: 높음

### 5. 재작업 부모·자식 효과를 한 번만 기록하고 취소

- 구현 상태: 완료

- 화면/영역: 정상·불량 재작업 완료, 거래 상세, 취소 미리보기와 주간보고 근거 상세.
- 증상: 부모 소비와 정상·불량·폐기 자식 산출을 거래 타입이나 부호만으로 분류하면 정상 부모를 `출고`와 `불량`에 두 번 차감하거나 이미 격리된 부모의 후속 처리를 새 불량으로 다시 셀 수 있다.
- 사용자 불편: `8-VF-0006 CSGR + CSCB`를 재작업하고 회수품으로 다시 VF를 만들었을 때 실제 정상재고와 보고 수치가 달라 보인다.
- 확정 정책:
  - 정상 F 부모 직접 재작업은 부모의 `불량`에만 표시하고 `출고`에는 표시하지 않는다.
  - 이미 불량인 같은 F 부모의 후속 재작업·폐기는 추가 `불량 0`이다.
  - 정상 F 자식은 `입고`, 불량·폐기 F 자식은 보고상 `입고`와 `불량`에 같은 수량을 기록한다.
  - 회수품으로 다시 만든 F는 별개의 일반 BOM `생산`이다.
  - 현재 주 재작업 취소는 부모, 모든 자식, 정상·불량재고와 불량 이동을 하나의 취소 작업으로 역전한다.
- 구현 방향: 거래 로그에 `부모 정상`, `부모 불량`, `자식 정상`, `자식 불량`, `자식 폐기` 역할을 명시하고 취소·주간 집계의 단일 근거로 사용한다. 메모·참조번호·부호로 역할을 추정하지 않는다.
- 수용 기준:
  - 정상 VF 1개 직접 재작업 후 VF 1개 재생산 결과가 `생산 1·불량 1·증감 ±0`이다.
  - NF 재작업의 정상 VF 자식은 `입고 1·증감 +1`, 불량 VF 자식은 `입고 1·불량 1·증감 ±0`이다.
  - 지난주부터 불량인 VF를 이번 주 재작업·폐기해도 VF의 추가 불량은 0이다.
  - 같은 주 취소 뒤 원 재작업과 취소 작업이 연결되고 부모·자식 활동, 재고와 불량 원장 효과가 모두 상쇄된다.
- 브라우저 확인 시나리오: 정상 VF 직접 재작업, 격리된 VF 후속 재작업·폐기, NF에서 정상·불량 VF 혼합 회수와 회수품을 사용한 VF 재생산을 실행한다 → 품목 상세와 두 검산식을 대조한 뒤 같은 주 재작업을 취소한다.
- 우선순위: 높음

### 6. 연결 업무를 이전 상태로 되살리지 않고 최종 `취소됨`으로 닫기

- 구현 상태: 완료

- 화면/영역: `IoBatch`, `StockRequest`, `ShippingRequest`, `ShippingAllocation`, 인계 문서와 연결된 거래의 취소.
- 증상: 일반 이력 취소가 재고만 복구하고 완료된 요청·출하·배정·인계 상태를 남기거나, 반대로 완료 업무를 과거 대기 상태로 되살리면 실제로 끝났던 업무 이력과 시스템 상태가 달라질 수 있다.
- 사용자 불편: 재고는 돌아왔지만 픽업 완료가 남거나, 이미 완료 후 취소한 요청이 다시 승인 대기 목록에 나타나 같은 업무를 중복 처리할 수 있다.
- 확정 정책: 취소 성공 시 재고·예약·배정·불량 효과는 역전하지만 원 요청·출하·인계 업무는 이전 상태로 복원하지 않고 최종 `취소됨`으로 닫는다. 같은 업무를 다시 하려면 새 요청을 생성한다. 업무 전용 역전 규칙이 없으면 부분 취소하지 않고 전체 실패한다.
- 구현 방향: 업무 유형별 취소 어댑터가 소유 엔터티와 예약·배정 상태를 검증하고, 취소 작업·재고·불량 원장과 같은 트랜잭션에서 소유 업무를 `취소됨`으로 전이한다. 일반 거래 취소 경로가 업무 전용 규칙을 우회하지 못하게 한다.
- 수용 기준:
  - 취소 성공 뒤 재고·예약·배정이 역전되고 원 요청·배치·출하·인계 문서는 `취소됨`이다.
  - 취소된 업무는 대기·승인·진행 목록에 다시 나타나지 않으며 재처리는 새 요청으로만 가능하다.
  - 구성 요소 하나라도 역전하거나 닫을 수 없으면 전체 롤백되고 원 완료 상태가 유지된다.
  - 새로고침 전후 UI 상태가 서버 커밋 상태와 같다.
- 브라우저 확인 시나리오: 픽업 완료 SHIP, 완료 StockRequest, 입출고 배치와 다품목 인계를 각각 취소한다 → 재고·배정과 문서 상태를 확인한다 → 취소된 문서가 대기 목록에 재등장하지 않고 새 요청만 만들 수 있는지 확인한다.
- 우선순위: 높음

### 7. 원 작업과 별도 취소 작업을 입출고 내역·대시보드에 동일하게 표시

- 구현 상태: 완료

- 화면/영역: 데스크톱 입출고 내역의 상위·하위 행, 대시보드 > 품목 상세 > 최근 내역, 거래 목록·상세 API.
- 증상: 입출고 내역은 원 행에 취소 상태만 덧씌우고 하위 행의 취소 표현이 일관되지 않으며, 대시보드 최근 내역에는 취소로 수량이 원복된 활동이 보이지 않는다. `취소 이력` 알약도 실제 취소 상태와 의미가 겹친다.
- 사용자 불편: 관리자는 하위 자재까지 취소됐는지, 재고가 언제 누구에 의해 왜 돌아왔는지 확신할 수 없고 대시보드 수량 변화와 최근 내역을 대조할 수 없다.
- 확정 정책:
  - 두 화면 모두 원 작업과 별도 취소 작업을 실제 행으로 표시한다.
  - 예시는 원 작업 `부서 입출고 -7 EA`, 취소 작업 `부서 입출고 취소 +7 EA`로 표시한다.
  - 취소된 원 작업의 부모와 모든 하위 행에서 `일시 텍스트 시작점~수량 알약 오른쪽 끝`과 `작업 후 재고 박스의 왼쪽 끝~오른쪽 끝`에 각각 하나의 긴 연속 취소선을 표시하고 해당 셀만 흐림 처리한다. 연속선은 품목코드·수량 및 작업 후 재고의 창고·부서 알약 위를 끊김 없이 지나가야 한다.
  - 작업 전 재고와 실제 `취소`·`취소됨` 상태 알약은 정상 명도와 형태를 유지한다. 행 전체 `opacity`는 사용하지 않는다.
  - 취소 작업 행은 선택된 출하 행과 같은 빨강 10% 배경으로 표시하고, 호버하면 이 행만 빨강 20%로 강조한다. 일반·불량·재작업·취소된 원 작업 행의 기존 호버 강도(기본 14%, 선택 18%)는 변경하지 않는다. 선택 테두리는 불량·재작업 행과 같은 빨강으로 고정하고 작업 알약도 빨강으로 표시한다. 취소선·흐림은 적용하지 않으며 반대 수량, 취소 처리자·취소 시각과 취소 직전·직후 재고를 보여준다.
  - 대시보드 최근 5개 안에 원 작업과 취소 작업이 함께 있으면 원 작업의 작업명·수량·시각은 취소선·흐림 처리하고 취소 작업 행은 정상 표시한다.
  - 중복 의미인 `취소 이력` 알약은 제거한다.
- 구현 방향: 거래 목록·상세 응답을 작업 중심으로 투영해 원 작업 상태, 연결된 취소 작업 ID, 작업 종류, 처리자·시각과 품목별 역전 로그를 제공한다. 입출고 내역은 같은 `operation_id`로 부모·하위를 묶고 선택적 취소 스타일을 각 셀에 적용한다. 대시보드 최근 내역은 선택 품목에 영향을 준 최신 작업 5개를 작업 발생 시각순으로 조회해 취소 작업도 독립 활동으로 표시한다.
- 수용 기준:
  - 원 작업과 취소 작업이 별도 행으로 남고 수량 부호가 정확히 반대다.
  - 원 작업을 펼치면 부모와 모든 하위 자재가 같은 취소 상태를 보이며 작업 전 재고 알약은 흐리거나 취소선 처리하지 않는다.
  - 취소 작업을 펼치면 부모와 하위 자재의 반대 수량 및 새 before/after 재고가 정상 명도로 보이고, 상위 행과 작업 알약은 확정된 빨강으로 구분된다.
  - 부모 품목과 각 하위 품목의 대시보드 최근 내역에서 해당 품목의 취소 작업이 취소 시각 기준으로 나타난다.
  - 대시보드에 원 작업도 남아 있으면 원 작업은 취소 표현, 취소 작업은 정상 표현으로 서로 구분된다.
  - `취소 이력` 알약은 없고 실제 취소 상태 알약은 정상 명도로 남는다.
  - 입출고 내역 통계의 `전체`와 원 업무 유형에는 원 작업과 취소 작업을 각각 한 작업으로 계산하며 취소 작업을 `수량조정`으로 분류하지 않는다.
  - 모바일 입출고 내역은 새 API 응답으로 기존 기능이 깨지지 않지만 이번 TODO에서 별도 시각 개편은 하지 않는다.
- 브라우저 확인 시나리오: 다품목 부서 입출고와 BOM 작업을 취소한다 → 입출고 내역에서 원 작업·하위 행의 선택적 취소선과 별도 취소 작업을 확인한다 → 부모와 하위 품목을 대시보드에서 각각 선택해 최근 내역의 반대 수량·처리자·취소 시각을 확인한다.
- 우선순위: 높음

### 8. 정상·불량 기준선과 버전 스냅샷을 전향 도입

- 구현 상태: 완료

- 화면/영역: 주간보고의 `전주 재고`, `현재 재고`, 기준 주차와 스냅샷 저장.
- 증상: 기존 스냅샷은 불량을 포함한 총재고만 저장해 과거 시점의 정상·불량 수량을 신뢰성 있게 분리할 수 없다.
- 사용자 불편: 사용할 수 없는 불량재고가 현재 재고에 포함되거나 불량 열을 추가했을 때 증감과 맞지 않을 수 있다.
- 확정 정책: 신규 기준부터 정상재고와 불량재고를 분리 저장하고 집계 기준 버전을 남긴다. 기존 과거 스냅샷은 추정 재구성하거나 덮어쓰지 않는다. 진단과 기준선 확인을 마친 다음 KST 월요일부터 새 계약을 적용한다.
- 구현 방향: 스냅샷에 기준 버전, 정상 수량과 불량 수량을 추가한다. 정상 기준은 창고+`PRODUCTION`, 불량 기준은 `DEFECTIVE`로 계산하고 예약은 별도 정보로 둔다. API가 선택 주차의 기준 버전과 데이터 연속성을 명시하며 불완전한 구간은 실패 폐쇄한다.
- 수용 기준:
  - 정상 7개·불량 3개·예약 2개인 F 품목은 정상재고 7, 불량재고 3으로 저장된다.
  - 예약 생성·해제만으로 정상재고 스냅샷이 변하지 않는다.
  - 기존 스냅샷 원본은 변경되지 않고 새 기준 적용 주차가 명확히 식별된다.
  - 기준선과 활성 불량 원장 합계가 일치하지 않으면 신규 기준을 활성화하지 않는다.
- 브라우저 확인 시나리오: 기존 주차와 새 기준 주차를 번갈아 조회한다 → 기준 버전 안내와 과거 숫자 보존을 확인한다 → 정상·불량·예약이 함께 있는 F 품목의 실제 위치 수량과 보고 값을 대조한다.
- 우선순위: 높음

- 증상: 현재 집계는 정상재고 효과를 하나의 계약으로 분류하지 않고 원 작업과 취소 작업의 명시적 관계도 없어 현재 재고와 활동 합계를 표만 보고 검산할 수 없다.
- 사용자 불편: 어떤 F가 왜 줄었는지 보이지 않거나 불량인 VF가 아무 변화 없이 정상으로 보일 수 있으며, 취소 거래가 입고·출고 실적으로 중복 노출될 수 있다.
- 확정 정책: 표시 열은 `전주 재고 | 생산 | 입고 | 출고 | 불량 | 현재 재고 | 증감`으로 고정한다. F 품목만 집계하고 모든 비증감 열은 비음수 합계 하나를 표시한다. 같은 주 원 작업·취소 작업은 연결 관계로 둘 다 활동 열에서 제외한다. 모든 행·공정·전체 합계에서 두 검산식을 강제한다.
- 구현 방향: 주간 API에 `defect_qty`, 입고·불량 근거, 원 작업·취소 작업 연결, 집계 기준 버전, 두 계산 증감, 검산 차이와 원인 거래를 추가한다. 명시적인 작업·재작업 역할과 정상재고 효과로 분류하고 프런트는 서버 검산 성공 응답만 표로 공개한다.
- 수용 기준:
  - 모든 F 품목 행·공정·전체에서 `현재 재고 - 전주 재고`와 `생산 + 입고 - 출고 - 불량`이 같은 증감이고 차이는 0이다.
  - `전주 재고·생산·입고·출고·불량·현재 재고`는 API와 화면 모두 0 이상이고 증감만 음수가 될 수 있다.
  - 정상 부모 직접 재작업은 `불량`에만 한 번 표시되고 이미 불량인 부모 후속 처리에는 추가 불량이 없다.
  - 불량 F 자식은 `입고`와 `불량`에 같은 양수로 표시돼 증감 0이면서 발생 사실이 보인다.
  - 같은 주 원 작업과 취소 작업은 활동 열 어디에도 남지 않으며 현재 재고와 증감이 원상태와 같다.
  - 미분류 정상재고 효과, 음수 활동 열 또는 검산 차이가 하나라도 있으면 잘못된 표 대신 품목과 원인 거래를 포함한 `집계 검산 실패`를 보여준다.
- 브라우저 확인 시나리오: 낱개 입고·출고, 생산·BOM 투입, 내부사용, 증가·감소 조정, 격리·복귀, 정상·불량 재작업과 폐기를 F 품목별로 실행한다 → 일부 작업을 같은 주에 취소한다 → 표의 합계·상세 근거와 두 검산식을 대조한다.
- 우선순위: 높음

## 복구·검증

### 10. 기존 불일치 진단과 전향 적용·건별 승인 복구 절차 마련

- 구현 상태: 완료

- 화면/영역: 관리자용 읽기 전용 정합성 진단, 신규 원장·주간 기준선 활성화와 운영 복구 절차.
- 증상: 기존 방식으로 처리된 취소 중에는 물리 재고, 활성 불량 원장과 요청·출하 상태가 어긋난 데이터가 있을 수 있으며 신규 역전 원장만 적용해도 과거 불일치는 사라지지 않는다.
- 사용자 불편: 신규 취소는 정상이어도 기존 유령 불량 기록이나 완료 상태 불일치 때문에 재고와 주간보고를 신뢰하기 어렵다.
- 확정 정책: 시스템이 과거 데이터를 자동 추정·일괄 변환하지 않는다. 먼저 읽기 전용 진단으로 원거래·기존 취소·현재 정상/불량재고·불량 원장·업무 상태·주간 검산 차이를 제시하고 사용자가 승인한 건만 복구한다. 진단 통과 뒤 신규 원장은 동기화 즉시 적용하고 새 주간 기준은 다음 KST 월요일부터 적용한다.
- 구현 방향: 활성 불량 원장 합계와 `DEFECTIVE` 수량, 취소 로그와 완료 `IoBatch`·`StockRequest`, 취소된 PICKUP과 출하·배정, 부분 취소 의심 묶음, 중복 취소 감사, 미분류 정상재고 효과와 주간 검산 차이를 점검한다. 복구 전 백업, 건별 dry-run, 전후 값과 승인자를 기록한다. 전향 적용 뒤 신규 거래만 `InventoryOperation`을 필수로 사용한다.
- 수용 기준:
  - 진단은 DB를 변경하지 않고 같은 스냅샷에서 재실행하면 같은 결과를 낸다.
  - 각 불일치가 원인 거래와 예상 복구 영향을 품목·위치·수량별로 제시한다.
  - 승인 복구는 선택한 항목만 한 트랜잭션으로 처리하고 실패 시 전체 롤백한다.
  - 활성화 뒤 신규 작업은 모두 공통 작업 원장을 가지며 기존 기록과 스냅샷은 보존된다.
  - 복구·활성화 뒤 불량 원장 불변식과 주간 두 검산식이 모두 통과해야 완료로 표시된다.
- 브라우저 확인 시나리오: 테스트 DB에 유령 불량 원장, 완료 업무 상태 잔존, 부분 취소와 주간 미분류 표본을 만든다 → 진단 결과를 확인한다 → 일부만 dry-run·승인 복구한다 → KST 월요일 전향 적용 전후의 기존 이력 보존과 신규 두 행 문법을 확인한다.
- 우선순위: 높음

## 필수 회귀 검증 묶음

- 작업 원장: 모든 신규 거래 유형의 `operation_id`, 부모·자식 역할, 원 작업 불변성, 취소 작업의 정확한 반대 수량과 before/after 스냅샷.
- 주차 경계: 일요일 23:59:59.999999 KST, 월요일 00:00:00 KST, 같은 주 취소, 지난 주 모든 거래 유형의 차단과 확정 문구.
- 단일·묶음: 낱개 입고·출고, 부서 이동, BOM 생산·투입, 품목전환, 정상·불량 재작업, 인계, 내부사용, 출하 준비·픽업.
- 불량 계보: 격리, 부분 정상복귀, 재작업, 폐기, 반품, 정상·불량·폐기 자식 혼합, 같은 품목의 격리 원장 두 건과 부모·자식 작업 취소.
- 후속 재고: 산출품 사용 뒤 부족 차단, 같은 품목·위치 재입고 뒤 허용, 예약과 활성 출하배정 차단.
- 원자성: 정상·불량재고, 불량 이동 원장, `IoBatch`, `StockRequest`, `ShippingRequest`, `ShippingAllocation`, 인계 상태 중간 강제 실패 시 원 작업·취소 작업·재고 모두 부분 변경 0건.
- 동시성: 동일 작업 취소 두 건, 묶음의 서로 다른 행에서 동시 취소, 일반 경로와 업무 전용 경로 경쟁에서 취소 작업 정확히 1건.
- 업무 상태: 취소 성공 뒤 원 업무는 최종 `취소됨`, 대기 목록 재등장 없음, 새 요청으로만 재처리.
- 이력 화면: 원 작업과 취소 작업 두 행, 부모·하위의 `작업일시~작업 수량` 및 `작업 후 재고` 연속 취소선, 작업 전 재고 정상 표시, 취소 작업 행·알약의 빨강 구분, `취소 이력` 알약 제거.
- 대시보드: 부모·하위 각 품목 최근 내역의 반대 수량, 취소 처리자·시각, 최신 5개 작업 정렬.
- 모바일 호환: 신규 작업·취소 작업 응답을 받아 기존 모바일 입출고 내역의 조회·상세·필터가 깨지지 않음. 별도 시각 개편은 검증 대상이 아니다.
- 보고 수치: 모든 비증감 열 비음수, 증감 부호, 품목·공정·전체 두 검산식, 대표 수치 예시, 같은 주 원 작업·취소 작업 쌍 제외.
- 실패 폐쇄: 음수 활동 값, 미분류 정상재고 효과, 기준선 단절과 검산 차이를 만들어 잘못된 표 대신 `집계 검산 실패` 표시.
- 과거 보존: 지난 주 취소 요청과 전향 적용이 기존 거래 로그·취소 이력·스냅샷·불량 이력과 업무 기록을 바꾸지 않음.

## 구현 순서와 단계별 완료 게이트

1. **공통 작업 원장**: `InventoryOperation`, `TransactionLog.operation_id`, 역할과 멱등·고유 역전 관계를 추가한다. 신규 생성 경로의 누락이 0이고 기존 데이터 읽기 호환 테스트가 통과해야 다음 단계로 간다.
2. **도메인 효과 연결**: 정상·불량 재고, 불량 이동, 예약·배정과 업무 소유 상태를 `operation_id`에 연결한다. 생성 작업별 영향 합계가 실제 커밋과 같아야 다음 단계로 간다.
3. **원자 취소**: 주차 차단, 전체 사전검사, 잠금, 별도 취소 작업과 업무 `취소됨` 전이를 구현한다. 성공·실패·동시성 테스트에서 부분 변경 0건이어야 다음 단계로 간다.
4. **작업 중심 이력 화면**: 원 작업·취소 작업 API 투영, 입출고 내역 선택적 취소 표현과 대시보드 최근 내역을 적용한다. 부모·하위 검증과 모바일 호환 테스트가 통과해야 다음 단계로 간다.
5. **주간 기준선·집계**: 정상·불량 버전 스냅샷, 확정 열, 활동 분류, 같은 주 취소 짝 제외와 fail-closed 검산을 적용한다. 대표 예시와 전체 검산이 통과해야 활성화한다.
6. **전향 적용**: 직원 동기화에서 기존 데이터 진단을 통과하면 신규 원장을 즉시 활성화하고, 새 주간 기준은 다음 KST 월요일 00:00부터 활성화한다. 적용 전후 기준선과 검산 결과를 감사 기록으로 남긴다.
