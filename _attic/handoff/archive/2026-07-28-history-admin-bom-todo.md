- 실제 재고 변화는 사용자 메모보다 먼저, 거래 의미에 맞는 영역에서 보여야 한다.

- 한 화면에 모은 기능도 목적별 구역과 제목을 분명히 해 탐색 부담을 늘리지 않는다.
- 선택 상태는 충분히 식별하되 과도한 그림자나 테두리로 작업 내용을 압도하지 않는다.
- 같은 작업대의 좌우 패널은 제목, 검색, 필터의 위계를 일관되게 맞춘다.
- 필터 묶음은 의미 단위로 분리하고, 좁은 폭에서도 잘리거나 패널 밖으로 넘치지 않아야 한다.

## 확정 결정 요약

- `동반 출하: <품목명>`은 시스템 생성 출하 설명이며 사용자 메모가 아니다. 동반 출하품은 재고 변화로만 명확히 보인다.
- 출하 이력의 담당자는 요청자가 아니라 `준비 완료`를 실행한 직원이다. 요청자 정보는 별도 정보로 보존한다.
- 시스템 메뉴의 `내보내기`와 `외부 제출용 로그`는 하나의 `내보내기` 화면 안에서 목적별 섹션으로 함께 제공한다.
- 관리자 상단 탭의 활성 그림자는 그 탭에만 약하게 적용하고, 전역 선택 버튼의 시각 규칙은 바꾸지 않는다.
- BOM 편집 패널은 좌측 `상위 품목 선택`, 우측 `하위 품목 추가 + 검색`과 한 줄의 의미별 필터 묶음으로 정리한다.
- 출하 준비 연결은 완전히 폐기한다. 새 생산·재작업을 출하 요청에 귀속하는 진입·저장·표시를 없애되, 이미 연결된 과거 이력은 삭제하지 않고 조회 가능하게 보존한다.

## 이력

### 1. 동반 출하 시스템 설명을 메모가 아닌 재고 변화로만 표시

- 상태: 구현 완료 (2026-07-28).
- 화면/영역: 데스크톱 이력 > 출하 이력 상세 우측 패널의 메모와 재고 변화.
- 증상: `동반 출하: SOLO 카톤 박스 …`처럼 시스템이 생성한 출하 설명이 메모로 노출된다. 같은 거래의 동반 출하품은 재고 변화에서 보여야 하지만 메모와 함께 보이면 의미가 중복되고 잘못 해석된다.
- 사용자 불편: 실제 재고 감소가 사용자 작성 메모처럼 보이며, 어떤 품목이 출하로 차감됐는지 한눈에 확인하기 어렵다.
- 확정 정책: `동반 출하: <품목명>`은 사용자 메모 카드·목록 메모 알약에 표시하지 않는다. 동반 출하품은 품목명, `출하 재고`, 감소 수량·단위를 가진 재고 변화 행으로 한 번만 표시한다. 사용자가 실제로 입력한 메모는 그대로 보존한다.
- 구현 방향: 시스템 생성 메모 판별이 실제 동반 출하 생성 문자열과 일치하도록 보완한다. 재고 수량을 다시 계산하거나 거래를 새로 만들지 말고, 기존 `inventory_effect` 그룹의 표시와 회귀 테스트를 검증한다.
- 수용 기준:
  - 동반 출하 완료 이력에서 `동반 출하: …` 메모 카드·알약이 보이지 않는다.
  - 재고 변화에는 동반 출하품의 품목명, `출하 재고`, 예: `-10 EA`가 정확히 한 행으로 표시된다.
  - 일반 사용자 메모와 일반 출하품 재고 변화는 기존대로 표시된다.
- 브라우저 확인 시나리오: 동반 출하품 10 EA가 포함된 출하 완료 건을 이력에서 연다 → 메모 영역에 시스템 동반 출하 문구가 없는지 확인한다 → 재고 변화에서 해당 품목과 `-10 EA`를 확인한다 → 사용자 메모가 있는 다른 출하 건과 비교한다.
- 우선순위: 높음.

### 2. 출하 이력 담당자를 준비 완료 실행자로 기록·표시

- 상태: 구현 완료 (2026-07-28).
- 화면/영역: 데스크톱 이력 > 출하 행의 `담당자` 열과 출하 상세의 담당자 메타.
- 증상: 현재 담당자는 요청자(`requested_by_name`)를 우선 사용하며, 준비 완료를 실제로 누른 직원은 출하 요청·이벤트·재고 로그에 저장되지 않는다.
- 사용자 불편: 실제 출하 준비 책임자가 이력에서 드러나지 않아 작업 추적과 책임 확인이 어렵다.
- 확정 정책: 출하 이력의 담당자는 `준비 완료`를 실행한 활성 직원이다. 요청자는 요청자 정보로 별도 보존하며 담당자와 대체하지 않는다. 이후 출하 단계에서 생성되는 관련 재고 로그도 저장된 준비 담당자를 사용한다. 기존 이력은 기존 요청자 값 또는 담당자 미기록으로 안전하게 표시한다.
- 구현 방향: 출하 요청 또는 준비 완료 이벤트에 준비 담당자 ID·이름을 영속화하고, 준비 완료 API가 현재 직원(`X-MES-Employee-Code`)을 해석·검증해 저장하도록 한다. 이력 응답과 목록 표시가 준비 담당자를 우선 사용하도록 바꾸며, `producer_employee_id`와 `produced_by`도 같은 직원으로 기록한다.
- 수용 기준:
  - 직원 A가 요청하고 직원 B가 준비 완료한 출하의 이력 담당자는 B이다.
  - 해당 새 출하 로그의 `producer_employee_id`와 `produced_by`도 B와 일치한다.
  - 요청자 A의 정보는 요청자 맥락에서 남아 있고, 기존 이력 조회는 오류 없이 폴백한다.
- 브라우저 확인 시나리오: 직원 A로 출하 요청을 만든다 → 직원 B로 로그인해 준비 완료한다 → 픽업 완료 후 이력 탭을 연다 → 해당 출하 행·상세의 담당자가 B인지, 요청자 정보와 혼동되지 않는지 확인한다.
- 우선순위: 높음.

### 3. `내보내기`와 `외부 제출용 로그`를 하나의 내보내기 화면으로 통합

- 상태: 구현 완료 (2026-07-28).
- 화면/영역: 데스크톱 관리자 > 시스템 메뉴와 내보내기 본문.
- 증상: 데이터 내보내기와 외부 제출용 로그가 별도 탭(`export`, `audit`)으로 나뉘어 있지만, 사용 목적은 모두 내보내기다.
- 사용자 불편: 외부 제출용 파일을 찾기 위해 별도 메뉴를 다시 탐색해야 하며, 같은 업무 범주의 기능이 분리되어 보인다.
- 확정 정책: 시스템 메뉴에는 `내보내기` 하나만 둔다. 그 본문 안에는 `데이터 내보내기`(F705, 전체 Excel, 선택 CSV, 최근 기록)와 `외부 제출용 로그`(F704, 월별 시스템 원본 로그, 재생성·다운로드)를 제목이 분명한 독립 섹션으로 함께 둔다. 기존 파일 형식, 권한, 확인 절차, 다운로드·재생성 동작은 바꾸지 않는다.
- 구현 방향: 상단 탭과 상태에서 별도 `audit` 진입을 제거하거나 통합 화면의 내부 섹션으로만 유지한다. 두 기존 화면의 API·다운로드 핸들러를 재사용하되, 중복 페이지 헤더 없이 한 화면의 목적별 본문으로 조합한다.
- 수용 기준:
  - 관리자 > 시스템에는 `내보내기` 탭 하나만 보인다.
  - 한 화면에서 F705, 전체 Excel, 선택 CSV, 최근 내보내기 기록과 F704, 월별 CSV/XLSX 다운로드, 로그 재생성을 모두 접근할 수 있다.
  - 연도 입력, 파일 다운로드, 재생성 확인·취소, 오류·비활성 상태가 기존과 동일하게 작동한다.
- 브라우저 확인 시나리오: 관리자 PIN 해제 → 시스템 `내보내기` 진입 → F705·전체 Excel·선택 CSV를 각각 실행 → 같은 화면에서 F704와 월별 CSV/XLSX 다운로드 실행 → 로그 재생성 취소·확인 및 오류 상태를 확인 → 좁은 폭의 메뉴·본문 스크롤을 확인한다.
- 우선순위: 중간.

### 4. 관리자 상단 탭의 활성 테두리·그림자 강도 완화

- 사용자 불편: 탭 선택 상태가 작업 화면의 내용보다 시각적으로 과도하게 튄다.
- 확정 정책: 관리자 상단 탭에만 활성 inset 그림자·테두리를 더 약하게 적용한다. 파란 글자, 연한 활성 배경, `aria-current`, 키보드·마우스 선택 동작은 유지한다. 다른 화면의 선택 버튼, KPI, 사이드바 등 전역 선택 버튼 스타일은 변경하지 않는다.
- 구현 방향: `AdminSectionTabs`의 활성 버튼에만 국소 식별자를 두고 라이트·다크 테마에서 전역 선택 규칙보다 우선하는 약한 그림자(또는 제거)를 적용한다. 선택 접근성 속성과 기존 탭 전환 테스트는 유지한다.
- 수용 기준:

  - 활성 그림자는 기존 전역 inset 그림자보다 명확히 약하다.
  - 다른 화면의 선택 버튼 그림자와 관리자 탭의 키보드/클릭 전환에는 회귀가 없다.
- 브라우저 확인 시나리오: 관리자 PIN 해제 → 모델 관리 선택 → 품목 관리·BOM 관리·보안으로 전환 후 재선택 → 라이트/다크와 Tab/Enter 조작에서 활성 상태·포커스·그림자 강도를 비교한다.
- 우선순위: 낮음.

## 관리자 BOM 관리

### 5. BOM 편집의 상위 품목 선택·하위 품목 추가 헤더와 필터를 2행 구조로 정리

- 상태: 구현 완료 (2026-07-28).
- 화면/영역: 데스크톱 관리자 > BOM 관리 > 편집 모드의 좌측 `BomParentList`와 가운데 `BomChildAddBox`.
- 증상: 좌측 부모 품목 목록에는 패널 제목이 없고, 우측 후보 패널은 `하위 품목 추가`, `980개 후보`, 검색창, 공정 필터, 단계 필터가 세 줄 이상으로 분리돼 있다. 두 패널의 정보 위계가 비대칭이며 후보 수 표시는 작업에 필요하지 않다.
- 사용자 불편: 상위 품목을 고르는 영역과 하위 품목을 더하는 영역의 역할이 즉시 구분되지 않고, 검색·필터가 필요한 것보다 많은 세로 공간을 차지한다.
- 확정 정책:
  - 좌측 목록 상단에는 `상위 품목 선택`, 우측에는 `하위 품목 추가` 제목을 표시한다.
  - 우측 제목 옆에는 기존 후보 검색창을 둔다. 검색 대상·정규화 동작은 유지한다.
  - `980개 후보` 표시는 제거한다.
  - 우측 제어부는 기본 데스크톱에서 두 행으로 구성한다: 첫 행은 `하위 품목 추가 + 검색`, 둘째 행은 단계 필터(전체·원자재·중간공정·공정완료)를 왼쪽, 공정 필터(전체·튜브·고압·진공·튜닝·조립·출하)를 오른쪽에 둔다.
  - 두 필터 묶음 사이에는 관리자 메뉴의 그룹 경계와 같은 성격의 세로 구분선과 좌우 여백을 둔다. 브라우저 코멘트 14는 관리자 메뉴 변경 요청이 아니라 이 구분선의 시각 참고다.
  - 가운데 패널 폭이 부족하면 둘째 필터 행만 가로 스크롤한다. 필터 칩은 한 줄을 유지하고 줄바꿈·축약·패널 밖 넘침을 허용하지 않는다.
- 구현 방향: `BomParentList`에 제목을 추가하고 `BomChildAddBox`의 후보 수 계산·표시를 제거한다. 검색·공정(`deptFilter`)·단계(`stageFilter`) 상태와 교집합 필터링은 그대로 유지한 채, 단계 필터·세로 구분선·공정 필터 순서의 한 줄 그룹으로 재배치한다. 기존 후보 중복 비활성화, 수량 입력, Escape 취소 동작도 보존한다.
- 수용 기준:
  - 좌측에 `상위 품목 선택`, 우측에 `하위 품목 추가`가 보인다.
  - 우측 제목 옆의 검색창은 계속 품목명·MES 코드 검색을 수행하고 `N개 후보`는 보이지 않는다.
  - 둘째 행에서 단계 필터는 왼쪽, 공정 필터는 오른쪽이며 두 묶음 사이에 세로 구분선이 보인다.
  - 공정·단계·검색어를 동시에 적용하면 교집합 후보만 표시된다.
  - 좁은 폭에서는 필터 행만 가로 스크롤하며 버튼·텍스트가 잘리거나 패널 밖으로 넘치지 않는다.
  - 이미 BOM에 등록된 후보의 비활성화, 후보 선택 후 수량 입력 및 Escape 취소는 유지된다.
- 브라우저 확인 시나리오: 관리자 > BOM 관리 > 편집에서 부모 선택 전후 좌우 패널 제목·검색·2행 필터 구성을 확인한다 → `튜브`와 `원자재`, 검색어를 순서대로 적용해 교집합만 남는지 확인한다 → 후보를 선택해 수량을 입력하고 Escape로 취소한다 → 기본·좁은 데스크톱 폭에서 구분선과 반응형 정책을 확인한다.
- 우선순위: 중간.

## 입출고·출하 준비

### 6. 출하 준비의 `준비 작업 시작`·`출하 준비 연결` 흐름을 완전히 제거

- 상태: 구현 완료 (2026-07-28).
- 화면/영역: 데스크톱 출하 > 준비 작업의 `준비 작업 시작` 버튼과, 그 버튼을 통해 이동한 입출고 > 작업 유형 선택 화면의 `출하 준비 연결` 안내 배너.
- 증상: 출하 요청이 `PREPARING` 상태가 되면 `준비 작업 시작` 버튼이 나타난다. 이 버튼은 출하 준비 완료가 아니라 입출고의 `process` 작업으로 이동시키고, 생산 등록·재작업 결과에 출하 요청 ID를 연결한다. 일반 출하 준비를 하려는 사용자에게는 요청하지 않은 별도 생산 흐름으로 보인다.
- 사용자 불편: 출하 요청을 만든 직후 무엇을 반드시 해야 하는지 알 수 없고, 버튼을 누르면 출하와 관계가 불명확한 생산·재작업 화면으로 이동한다. 잘못 이해하면 정상 출하에 불필요한 작업·초안·거래를 만들 위험이 있다.
- 확정 정책: 출하 준비 연결을 완전히 폐기한다. 일반 출하와 특수 상황 모두에서 `준비 작업 시작`, 입출고의 `출하 준비 연결` 배너, 생산·재작업 결과의 출하 요청 귀속을 새로 만들 수 없게 한다. 기존의 `준비 완료`와 `픽업 완료` 흐름은 별도 의미로 유지하며, 과거에 이미 연결된 이력은 삭제하지 않고 조회만 가능하게 보존한다.
- 구현 방향: 출하 준비 화면의 버튼, 출하에서 입출고로 넘기는 `shippingPrepare` 진입 의도, 프런트 연결 배너·입력 제약·타입, 백엔드의 새 요청 ID 연결과 `PREPARE` 단계 기록 경로를 모두 제거한다. 기존 데이터 조회·이력 표시의 호환성만 남기고, 정상 출하의 재고 확인·준비 완료·픽업 완료 동작은 변경하지 않는다. 관련 코드·테스트·문서에서 옛 이름을 전부 검색해 갱신한다.
- 수용 기준:
  - 새 출하 요청의 준비 화면에는 목적이 불명확한 생산·재작업 진입 버튼이 보이지 않는다.
  - 사용자는 기존처럼 인보이스 입력, 재고·구성 확인, `준비 완료`, `픽업 완료`만으로 정상 출하를 처리할 수 있다.
  - 기존에 이미 연결된 출하 준비 이력은 조회 오류 없이 남고, 결정한 보존 정책과 맞게 표시된다.
- 브라우저 확인 시나리오: 출하 요청 생성 → 준비 작업 진입 → 정상 출하에 필요한 제어만 노출되는지 확인 → 인보이스 입력 후 준비 완료·픽업 완료를 수행 → 기존 연결 이력이 있는 출하 건의 상세·이력도 조회한다.
- 우선순위: 높음.

## 2026-07-28 BOM 필터 밀도 후속 확정

- 표준 데스크톱 화면에서 하위 필터 행은 가용 폭 556px보다 약 51px 넓어 가로 스크롤이 생긴다.
- 최종 승인안은 12px 글자와 26px 칩 높이, 패널 비율을 유지하고 칩 좌우 패딩을 10px에서 8px로 줄이되 칩 간격은 6px를 유지하는 방식이다.
- 단계·공정 사이의 세로 구분선은 유지하되 왼쪽 여백과 안쪽 여백을 함께 한 단계 줄인다.
- 공정 필터를 오른쪽 끝으로 강제하던 `ml-auto`는 제거해 그룹 사이가 벌어지지 않게 하고, 남는 폭은 각 그룹의 칩 간격이 자연스럽게 사용한다.
- 상위 품목 단계 필터에도 같은 칩 패딩·간격·한 줄 정렬을 적용하고, 품목 건수는 오른쪽 정렬을 유지한다.
- 표준 데스크톱 폭에서는 스크롤이 생기지 않아야 한다. 더 좁은 폭의 안전장치로 하위 필터 행의 `overflow-x-auto`는 유지한다.
- 검색·단계 필터·공정 필터의 상태와 교집합 동작, 패널 폭은 변경하지 않는다.
