- 구현 방향: `InventoryItemsTable`의 열 제목과 `InventoryItemRow`의 표시값·상태 판정 입력을 `available_quantity`로 통일한다. 프런트엔드에서 불량·예약 수량을 재계산하지 않고 기존 API 값을 사용한다. 관련 단위 테스트의 열 제목·수량·상태 기대값을 갱신한다.

### 2. [완료] 부족 품목 전체 가져오기를 한 번 클릭으로 완료

- 화면/영역: 입출고 > 요청 작성 > Step 4 수량 조정 > `부족 9개 전체 가져오기`.
- 증상: 부족 품목 전체 가져오기를 처음 클릭하면 원 작업이 `작성 중`으로 저장되고 URL에 초안 ID가 남지만, 화면에는 원래 1개 품목만 남는다. 같은 버튼을 두 번째 클릭해야 창고 반출 품목 9개가 새 카트에 표시된다.
- 사용자 불편: 버튼 이름은 전체 가져오기인데 실제로는 첫 클릭이 저장만 한 것처럼 보인다. 사용자는 전환이 실패한 것으로 판단하거나 같은 동작을 반복해야 하며, 중간 초안과 새 작업의 관계를 이해해야 한다.
- 확정 정책: `부족 N개 전체 가져오기`는 한 번 클릭으로 부족 품목 전체를 새 `창고 → 부서` 반출 작업에 담아 Step 4에 표시한다. 원 작업은 `작성 중` 초안으로 보존하되, 원 초안의 URL 복원이 새 반출 작업을 덮어쓰지 않아야 한다.
- 구현 방향: 원 작업 저장·URL 기록·새 반출 카트 전환의 비동기 순서를 하나의 원자적 화면 전환으로 정리한다. 원 초안 저장 뒤 그 초안의 URL 복원 효과가 실행 중인 새 카트를 복원값으로 덮어쓰지 않도록 전환 중 복원을 억제하거나, 새 반출 카트가 완성된 뒤에만 최종 URL 상태를 기록한다. 부족 품목 1개·여러 개, 선택한 항목만 가져오기, 초안 저장 실패를 자동화 테스트로 분리한다.
- 수용 기준:
  - 부족 9개 전체 가져오기를 한 번 클릭하면 원 작업은 작성 중 목록에 1건으로 보존되고, 현재 화면은 창고 → 부서 반출의 9개 품목·라인이 담긴 Step 4로 전환된다.
  - 첫 클릭 뒤 원 작업의 1개 품목이 새 반출 카트를 덮어쓰지 않으며 두 번째 클릭이 필요하지 않다.
  - 특정 부족 라인을 선택한 경우에는 선택한 품목만 한 번의 클릭으로 새 카트에 담긴다.
  - 저장·미리보기 실패 시 새 반출 작업의 일부 품목이나 잘못된 URL·초안 상태가 남지 않고 오류를 명확히 표시한다.
  - 원 작업의 초안 저장, 작성 중 개수, 뒤로 가기와 새로고침 후 각 초안 복원 동작은 기존 계약을 유지한다.
- 브라우저 확인 시나리오: 부족 라인이 9개인 Step 4에서 `부족 9개 전체 가져오기`를 한 번 클릭한다 → 즉시 창고 → 부서 반출 Step 4에 9개 묶음·9개 라인이 표시되는지 확인한다 → 작성 중에 원 작업이 하나 보존됐는지 확인한다 → 원 작업으로 돌아가 복원한 뒤, 부족 라인 일부를 선택해 한 번 클릭으로 선택 품목만 가져오는지 확인한다 → 새로고침·뒤로 가기 후 각 초안이 서로 바뀌지 않는지 확인한다.

- 수용 기준:
  - 모델·단계·부서·검색어 중 하나 이상을 적용한 뒤 Step 4로 이동하고 Step 3으로 돌아와도 모든 값과 필터 결과가 동일하다.

  - compact·데스크톱 레이아웃, 빠른 작업 강조 검색, 기존 임시저장 복원과 뒤로 가기 동작은 유지된다.

## 동기화 스킬

### 4. [완료] 직원 업무 데이터를 개발 서버로 선택 동기화

- 화면/영역: 직원 서버의 대시보드 재고 수량, 입출고 내역, 출하 관리의 준비중·준비 완료, 출하 이력과 이를 개발 서버에서 재현하기 위한 동기화 스킬·운영 명령.
- 증상: 현재 `deploy-to-employee` 스킬과 `sync-to-employee.ps1`은 개발 코드만 직원 환경으로 배포한다. 두 DB 파일은 복사 대상에서 제외되므로 직원 환경에서 발생한 재고·입출고·출하 업무 데이터가 개발 서버에 반영되지 않는다.
- 사용자 불편: 실제 업무 상태를 기준으로 개발 화면·수정 결과를 확인하려면 직원 화면과 개발 화면을 따로 비교해야 한다. 특히 재고 수량, 거래 이력, 출하 준비·완료·픽업 이력이 개발 서버에서 달라 재현과 검증이 어렵다.
- 확정 정책: 방향은 직원 DB(`C:\ERP-dev\backend\mes.db`)에서 개발 DB(`C:\ERP\backend\mes.db`)로만 한다. 동기화 대상 업무 결과는 재고 수량, 입출고 내역, 출하 준비중·준비 완료·출하 이력이다. 기존 코드 배포 명령과 분리된 명시적 명령으로 실행하며, 매일 예약은 코드 단계 정상 종료 뒤에만 `-Apply`를 호출한다. 기존 개발→직원 코드 동기화의 DB 제외 정책은 유지한다.
- 확정된 충돌 정책: 대상 업무 테이블을 부분 병합하지 않고, 직원 DB 전체를 읽기 전용 스냅샷으로 만든 뒤 개발 최신 migration과 검증을 적용해 개발 DB를 원자적으로 교체한다. 설치 전 검증된 개발 DB 전체 백업을 만들며 실패 시 해당 백업으로 자동 복구한다.
- 구현 방향:
  - `sync-from-employee-data.ps1`과 이를 호출하는 스킬 절을 별도로 만든다. 기존 `sync-to-employee.ps1`의 방향과 `-Force` 금지 규칙은 유지하고, 매일 예약에 코드→데이터 순차 실행을 추가한다.
  - 소스 직원 DB는 실행 중 파일 복사가 아니라 SQLite backup API로 읽기 전용 일관 스냅샷을 만든 뒤 검증한다. 스냅샷과 개발 DB 모두 `bootstrap_db.py --check`, SQLite integrity check, 스키마 revision 일치, 참조 품목·직원 존재 여부를 먼저 확인한다.
  - 개발 서버 8011/3001을 안전하게 정지하고 개발 DB의 검증된 전체 백업을 만든다. 설치·검증·재기동 실패 시 검증된 이전 개발 DB로 자동 복구하고 8011/3001 재기동을 시도한다.
  - 재고·입출고·출하를 독립 테이블로 복사하지 않고 참조 폐쇄 묶음으로 처리한다. 최소 대상은 `inventory`, `inventory_locations`, `transaction_logs`, `transaction_edit_logs`, `io_batches`, `io_bundles`, `io_lines`, `stock_requests`, `stock_request_lines`, `shipping_requests`, `shipping_request_bom_lines`, `shipping_request_companion_lines`, `shipping_allocations`, `shipping_request_checklist_lines`, `shipping_request_events`, `shipping_request_revisions`이다. 거래가 건별 불량 원장을 참조하면 `defect_quarantine_records`와 `defect_quarantine_memo_revisions`도 같은 실행에 포함하거나 안전하게 중단한다.
  - 완료 뒤 재고 합계·위치 재고·예약·활성 출하 배정·거래/배치/출하 참조 무결성, 대상별 행 수·키 집합·해시 diff를 검증한다. 개발 서버를 재기동해 8011/3001 헬스체크와 대시보드·입출고 내역·출하 준비/이력 조회를 확인한다.
  - 스킬 문서에는 방향, 대상/제외 테이블, dry-run 기본값, 명시적 실행 승인, 충돌 정책, 백업/사후검증/복구 절차를 추가한다. 실제 실행 시 사용자가 선택한 범위와 소스·대상 DB 경로를 보고한다.
- 수용 기준:
  - 기본 dry-run은 양쪽 DB를 변경하지 않고 스키마 revision, 대상 테이블 행 수·키 차이, 누락 참조, 충돌과 예상 적용 범위를 보고한다.
  - 기본 실행은 dry-run이며, 실제 실행은 명시적 `-Apply` 플래그 없이는 개발 DB를 변경하지 않는다. 소스 직원 DB는 어떤 경우에도 변경하지 않는다.
  - 실행 전 개발 DB 전체 백업이 성공·검증되지 않으면 개발 DB와 서버를 변경하지 않는다.
  - 동기화 성공 뒤 개발 DB의 재고 수량·입출고 내역·출하 준비중·준비 완료·출하 이력이 직원 스냅샷과 대상 범위에서 일치한다.
  - 모든 대상 거래·입출고 배치·결재·출하 하위 행의 외래키가 유효하고, 재고 수량과 위치·예약·출하 배정 무결성 검사가 통과한다.
  - 중간 실패 시 개발 DB에 부분 복사된 행이 없고, 개발 서버는 기존 DB로 재기동되거나 검증된 백업 경로와 수동 복구 절차를 명확히 남긴다.
  - 기존 개발→직원 코드 동기화의 DB 제외 정책과 직원 서버 업무 DB는 유지하며, 예약은 코드 성공 뒤 데이터 가져오기를 순차 실행한다.
- 브라우저 확인 시나리오: 직원 DB 스냅샷에 재고 수량, 해당 월 입출고 거래, 준비중·준비 완료 출하 요청, 픽업 완료 출하 이력이 있는 상태를 준비한다 → 개발 DB에 dry-run을 실행해 범위·충돌·참조 검증 결과를 확인한다 → 명시 승인 후 실제 동기화를 실행한다 → 개발 서버 3001에서 대시보드 재고 목록, 입출고 내역, 출하 관리의 준비중·준비 완료, 출하 이력을 차례로 열어 직원 스냅샷과 대조한다 → 개발 DB 무결성 결과와 백업 경로를 확인한다 → 직원 서버 3000의 데이터·서비스가 변하지 않았는지 확인한다.
- 우선순위: 높음

### 5. [완료] 직원 일일 작업 일보를 개발 서버로 함께 동기화

- 화면/영역: 직원 서버의 `일일 작업 일보`와 개발 서버의 동일 화면, 직원 → 개발 업무 데이터 동기화 명령·스킬.
- 증상: 현재 계획한 업무 데이터 동기화 범위에는 재고·입출고·출하만 명시되어 있어, 직원 서버에 작성한 일일 작업 일보 내용은 개발 서버에 나타나지 않는다. 작업 일보 화면은 같은 날짜·직원의 거래 활동과 함께 보여 주므로, 일보만 빠지면 실제 업무 맥락이 끊긴다.
- 사용자 불편: 개발 서버에서 실제 직원의 작업 일지를 보며 화면을 확인하거나 수정 결과를 검증할 수 없다. 입출고 이력은 동기화됐는데 해당 직원의 일보 서술은 없는 불일치가 발생한다.
- 확정 정책: 직원 DB의 `daily_work_reports`를 재고·입출고·출하 동기화와 같은 **직원 → 개발** 승인형 실행에 포함한다. 일보 내용은 직원 시스템의 기록을 정본으로 하며, 기존 개발→직원 코드 동기화의 DB 제외 정책은 그대로 유지한다.
- 구현 방향: TODO 4의 참조 폐쇄 대상에 `daily_work_reports`를 추가한다. `employee_id`가 개발 DB의 `employees`에 존재하는지 사전 검증하고, 없거나 이름·부서 값이 해당 직원 기준과 충돌하면 행을 추측해 생성하지 말고 dry-run에서 중단 사유로 보고한다. `employee_id + work_date` 유일 키의 충돌은 TODO 4에서 확정할 전체 충돌 정책을 동일하게 적용한다. 사후 검증에는 날짜·직원별 일보 키 집합, 내용과 `updated_at` 해시/값 비교를 포함하고, 해당 날짜의 일보 화면과 거래 활동을 함께 확인한다.
- 수용 기준:
  - dry-run 결과에 작업 일보의 신규·변경·충돌 건수, 누락 직원 참조, 적용될 날짜 범위가 별도 표시된다.
  - 실제 승인 실행 뒤 개발 DB의 대상 날짜·직원별 일보 내용과 갱신 시각이 직원 스냅샷과 일치한다.
  - 개발 DB에 없는 직원 참조나 직원 정합성 오류가 있으면 일보를 임의 생성·부분 반영하지 않고 전체 동기화를 안전하게 중단한다.
  - 기존 입출고 거래 활동 조회, 작업일보 편집·저장, 직원 삭제 제한, 개발→직원 코드 동기화에는 회귀가 없다.
- 브라우저 확인 시나리오: 직원 서버에서 동일 날짜에 일보가 있는 직원과 없는 직원을 준비한다 → 개발 대상 dry-run에서 일보 건수·날짜·직원 참조 결과를 확인한다 → 명시 승인 후 개발 서버 3001의 `일일 작업 일보`에서 해당 날짜를 선택한다 → 일보 작성자·내용·MES 거래 활동을 직원 서버와 대조한다 → 일보가 없는 직원은 빈 상태가 유지되는지, 직원 서버 3000의 일보가 변경되지 않았는지 확인한다.
- 우선순위: 높음
