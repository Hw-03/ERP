- 수용 기준:
  - 현장 사용자가 기존 엑셀의 각 핵심 정보(날짜·부서·작성자·모델·작업내역·수량·불량·완료·비고/기타 사항)를 MES 화면의 한 위치와 일대일로 이해할 수 있다.
  - 사용자가 시간대별 행을 반복 입력하지 않아도 개인별 하루 1건을 저장·수정할 수 있다.
  - MES에서 자동 집계한 값과 직접 작성할 값의 구분·출처가 명확하며 같은 수량을 두 번 입력하지 않는다.
  - 본인 일보는 편집 가능하고 전체 일보의 타인 기록은 읽기 전용이며, 과거 날짜·미작성·거래 없음 상태가 명확하다.
  - 자동 수량·불량·완료 계산의 기준 거래와 취소 제외 규칙은 기존 활동 API와 상세 거래에서 검산 가능하다.
- 브라우저 확인 시나리오: 거래가 없는 날·생산/입출고/불량 거래가 섞인 날·과거 작성 일자를 각각 연다 → 헤더와 모델/작업/수량/비고의 대응을 엑셀 `02.02` 시트와 비교한다 → 자동값의 거래 상세를 펼쳐 검산한다 → 본인 저장·수정, 전체 일보의 타인 읽기 전용, 모바일 폭을 확인한다.
- 우선순위: 높음.

### 4. 작성 영역이 남은 데스크톱 세로 공간을 채우도록 확장

- 화면/영역: 데스크톱 `/mes?tab=dailyReport`의 `내 일보` 작성 화면에서 `MES 작업 기록`과 `작업 내역` 카드 및 `작업 내역` 입력 상자.
- 증상: 1919×910 화면에서 두 카드가 고정된 높이로 종료되어 아래에 큰 빈 공간이 남는다. `작업 내역` 입력 상자는 긴 일일 기록을 쓰기에는 불필요하게 낮다.
- 사용자 불편: 넓은 데스크톱 화면의 세로 공간을 쓰지 못하고, 작업 내역을 작성·검토할 때 입력 상자가 빠르게 부족해진다.
- 확정 정책: 데스크톱 작성 화면에서는 상단 공통 헤더와 일보 도구 막대를 제외한 가용 세로 공간을 `MES 작업 기록`·`작업 내역` 영역이 채운다. 자동 MES 기록 카드는 내용에 맞는 높이를 유지하고, 남는 공간은 `작업 내역` 카드와 그 입력 상자에 배분한다.
- 구현 방향: 작성 본문을 세로 `flex` 레이아웃으로 구성해 상위 컨테이너가 가용 높이를 갖도록 하고, `MES 작업 기록`은 내용 기준 크기, `작업 내역` 카드는 남은 공간을 차지하게 한다. 카드 안의 입력 상자는 카드 내부에서 늘어나며, 좁은 데스크톱 높이에서는 전체 본문 또는 필요한 내부 영역만 스크롤되어 저장 안내와 저장 버튼이 가려지지 않게 한다. 모바일의 현재 문서 흐름은 바꾸지 않는다.
- 수용 기준:
  - 1919×910 데스크톱의 `내 일보` 화면에서 `MES 작업 기록`·`작업 내역` 작성 영역 아래에 목적 없는 큰 빈 공간이 남지 않는다.
  - `작업 내역` 입력 상자는 자동 MES 기록 카드가 차지한 뒤의 가용 세로 공간까지 확장된다.
  - 작업 기록이 없거나 여러 개인 날 모두에서 안내 문구·자동 기록·글자 수·저장 안내·저장 버튼이 겹치거나 화면 밖으로 밀리지 않는다.
  - 낮은 데스크톱 높이와 모바일 폭에서는 가로 오버플로 없이 읽기·입력·저장이 가능하다.
- 브라우저 확인 시나리오: 1919×910에서 거래가 없는 날과 자동 MES 기록이 있는 날의 `내 일보`를 각각 연다 → `MES 작업 기록` 아래 `작업 내역` 입력 상자가 남은 세로 공간을 채우는지 확인한다 → 긴 작업 내역을 입력하고 저장 안내·저장 버튼의 표시와 동작을 확인한다 → 낮은 데스크톱 높이와 모바일 폭에서 스크롤·오버플로를 확인한다.
- 우선순위: 높음.

### 5. 작업 내역 저장 결과를 즉시 확인할 수 있도록 표시

- 화면/영역: `/mes?tab=dailyReport`의 `내 일보` 화면에서 `작업 내역` 입력 상자, 글자 수·저장 안내, `저장` 버튼.
- 증상: 사용자가 `저장`을 눌러도 저장 중·성공·실패 어느 상태도 분명히 표시되지 않아 실제로 서버에 반영됐는지 알 수 없다.
- 사용자 불편: 저장 여부를 확신할 수 없어 같은 내용을 중복 저장하거나, 저장에 실패한 내용을 성공으로 오인할 수 있다.
- 확정 정책: 저장 요청 직후에는 진행 중 상태를, 성공 시에는 해당 일보가 저장됐음을 명확히, 실패 시에는 저장되지 않았음을 재시도 방법과 함께 표시한다. 성공 피드백은 단순 안내 문구와 구별되어야 하며, 선택한 날짜의 저장 결과임을 사용자가 알 수 있어야 한다.
- 구현 방향: 저장 동작의 비동기 상태를 버튼과 가까운 상태 표시로 연결한다. 요청 중에는 중복 클릭을 막고 진행 중임을 알리며, 성공하면 `저장 완료`와 저장 시각 또는 동등한 최신 저장 상태를 보여 준다. 실패하면 입력 내용은 유지한 채 오류와 재시도 동선을 보여 준다. 페이지를 다시 열었을 때 서버에서 불러온 값으로 저장 성공을 검증할 수 있는 기존 흐름은 유지한다.
- 수용 기준:
  - 변경한 작업 내역에서 `저장`을 누르면 즉시 저장 진행 상태가 보이고, 중복 저장 요청을 만들 수 없다.
  - API 성공 후에는 선택한 날짜의 작업 내역이 저장됐다는 성공 표시가 나타나며, 사용자가 일반 안내 문구와 혼동하지 않는다.
  - API 실패 시 성공 표시가 나오지 않고, 입력한 내용이 사라지지 않으며 실패 이유와 재시도 동선이 보인다.
  - 저장 후 다른 날짜로 이동했다가 돌아오거나 새로고침해도 저장한 내용이 유지되어 성공 표시와 실제 데이터가 일치한다.
  - 데스크톱·모바일에서 상태 표시와 저장 버튼이 겹치거나 화면 밖으로 밀리지 않는다.
- 브라우저 확인 시나리오: 식별 가능한 작업 내역을 입력한다 → `저장`을 누른 직후 진행 상태를 확인한다 → 성공 표시를 확인한 뒤 다른 날짜 이동·복귀와 새로고침으로 저장 값을 검증한다 → 저장 API 실패를 재현해 입력 보존, 오류 표시, 재시도 성공을 확인한다.
- 우선순위: 높음.

### 6. 전체 일보의 네 박스가 기본 데스크톱 높이에 스크롤 없이 맞도록 조정

- 화면/영역: 데스크톱 `/mes?tab=dailyReport`의 `전체 일보`에서 상단 일보 헤더, `작성한 직원`, `MES 작업 기록`, `작업 내역` 네 박스가 쌓인 본문.
- 증상: 1919×910 뷰포트에서 기본 상태의 네 박스 높이 합계가 본문 가용 높이를 조금 넘겨 전체 일보 본문이 미세하게 세로 스크롤된다.
- 사용자 불편: 기본 정보를 한 번에 확인할 수 있는데도 아주 짧은 스크롤을 해야 하고, 화면이 맞지 않은 것처럼 보인다.
- 확정 정책: 1919×910·100% 배율에서 작성한 직원 한 명을 선택하고 MES 작업 기록 상세가 접힌 기본 상태라면, 네 박스 전체가 본문 컨테이너에 들어가 `scrollHeight`가 `clientHeight`를 넘지 않아야 한다. 상단 헤더·작성한 직원·MES 작업 기록은 내용에 맞는 컴팩트한 높이를 유지하고, 내 일보의 작업 내역 편집 카드는 MES 카드와 12px 간격을 제외한 본문 영역을 채우는 628px 높이를 유지한다. MES 상세를 펼쳐 본문 높이가 늘어나면 일보 전체 본문에서 세로 스크롤한다.
- 구현 방향: 기본 상태의 네 박스 높이 예산을 본문 가용 높이에 맞춘다. 내 일보의 작업 내역 편집 카드는 1919×910·100% 배율에서 본문 하단까지 채우는 628px로 고정하고, MES 상세의 개별 카드 내부 최대 높이와 스크롤을 제거해 일보 본문 스크롤로 이어지게 한다. 44px 조작 영역과 카드 내부 읽기 순서는 유지한다.
- 수용 기준:
  - 1919×910·100% 배율의 전체 일보 기본 상태에서 네 박스 컨테이너는 세로 스크롤바가 없고 `scrollHeight <= clientHeight`다.
  - 전체 일보에서 본인 기록과 다른 직원 기록을 각각 선택해도 작성자 선택, MES 안내·요약, 작업 내역 읽기·저장 동선이 가려지거나 겹치지 않는다.
  - MES 상세를 펼쳐 본문 높이가 늘어나면 일보 전체 본문에서 스크롤할 수 있고, 작업 내역 편집 카드와 저장 버튼의 위치는 유지된다.
  - 내 일보의 작업 내역 입력 공간, 모바일 문서 흐름, 상단 바-본문 공통 12px 여백은 유지된다.
- 브라우저 확인 시나리오: 100% 배율·1919×910에서 전체 일보를 연다 → 작성자 한 명을 선택한 기본 상태에서 네 박스 컨테이너의 `scrollHeight`와 `clientHeight`를 비교하고 스크롤바가 없는지 확인한다 → 본인·다른 직원 기록을 각각 확인한다 → MES 상세를 펼쳐 일보 전체 본문이 스크롤되는지와 628px 작업 내역 카드·저장 버튼 위치를 확인한다 → 내 일보와 모바일 폭을 확인한다.
- 우선순위: 높음.

## 공통

### 7. 모든 데스크톱 메뉴의 상단 바-본문 여백을 12px로 통일

- 화면/영역: 대시보드, 입출고 내역, 일일 작업 일보를 포함한 일반 데스크톱 메뉴의 상단 바와 첫 번째 본문 블록 사이 세로 여백.
- 증상: 공통 셸의 상단 여백이 `mt-3`(12px)로 통일되어 메뉴별로 상단 바와 본문이 지나치게 붙어 보이던 문제가 해소되었다. 입출고 내역·대시보드의 본문 카드 구획도 `gap-3`(12px)를 사용한다.
- 사용자 불편: 메뉴를 전환할 때 상단 바와 본문 사이의 시각적 호흡이 부족하고, 메뉴마다 레이아웃 밀도가 일관되지 않게 느껴진다.
- 확정 정책: 일반 데스크톱 메뉴는 상단 바 하단과 `desktop-tab-content` 본문 상단 사이에 12 CSS px를 둔다. 기준값은 기존 본문 카드 구획의 `gap-3`이며, 전 메뉴에 같은 값으로 적용한다. 상단 바를 숨기는 창고 지도 전체 화면은 이 기준의 예외로 유지한다.
- 구현 방향: 각 메뉴에 개별 `margin`을 추가하지 않고 데스크톱 셸의 공통 `desktop-tab-content` 상단 여백만 `mt-3`(12px)로 둔다. 본문 내부의 `gap-3`, 카드 패딩, 카드 높이는 변경하지 않는다.
- 수용 기준:
  - 100% 배율의 일반 데스크톱 메뉴에서 상단 바 하단과 본문 컨테이너 상단의 계산된 여백이 12 CSS px다.
  - 대시보드·입출고 내역·일일 작업 일보를 전환해도 같은 상단 여백이 유지된다.
  - 본문 카드 사이 간격, 카드 내부 패딩, 표·검색·필터·저장 버튼의 위치는 이 여백 변경 때문에 달라지지 않는다.
  - 창고 지도 전체 화면과 모바일 레이아웃은 기존 동작·여백을 유지한다.
- 브라우저 확인 시나리오: 100% 배율·1919×910에서 대시보드, 입출고 내역, 일일 작업 일보를 차례로 연다 → 각 상단 바와 첫 본문 블록 사이를 `getBoundingClientRect()`로 측정해 12px인지 확인한다 → 대시보드의 재고 목록, 입출고 내역의 검색·필터, 일일 작업 일보의 MES 작업 기록과 작업 내역 내부 간격이 전과 같은지 확인한다 → 창고 지도 전체 화면과 모바일 폭을 확인한다.
- 우선순위: 높음.
