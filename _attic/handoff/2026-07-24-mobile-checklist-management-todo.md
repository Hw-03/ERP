## 조립 체크리스트

### 1. `순서 변경` 선택 상태와 정렬 모드 전환 정리

- 화면/영역: 모바일 > 체크리스트 > 관리 > 제품 상세 상단의 `순서 변경`과 목록 맨 아래 `박스 추가`.
- 증상: 같은 상단 제어 묶음에 있던 두 버튼이 서로 다른 반응과 역할로 보여, 정렬 선택 상태가 별도 화면 전환처럼 느껴진다.
- 사용자 불편: 사용자가 정렬 모드의 선택 여부를 바로 파악하기 어렵고, 정렬 중 박스를 추가해도 되는지 알기 어렵다.
- 정정 정책: 첫 박스 바로 위 오른쪽에 작은 `순서 변경` 버튼만 둔다. 버튼 텍스트는 정렬 전후 모두 유지하고, 선택 상태만 파란 틴트·테두리·아이콘 강조로 표시한다. 정렬 상태에서는 연필·항목 추가·박스 추가를 숨기고 드래그 아이콘만 표시한다. 놓은 직후에는 이동한 행에만 `저장 중` 상태를 보이고, 성공 시 조용히 없앤다.
- 구현 방향: 상단 `박스 추가`를 제거하고, 첫 박스 바로 위 오른쪽의 `순서 변경`에만 토큰 기반 배경·테두리 색을 적용한다. 정렬 상태에서는 편집·추가 조작을 렌더링하지 않고 박스와 항목의 드래그 아이콘만 렌더링한다. 저장 실패 시 위치를 되돌린 뒤 오류 메시지를 표시한다.
- 수용 기준:
  - `순서 변경`을 선택해도 첫 박스 바로 위 오른쪽에서 버튼 문구와 위치가 유지된다.
  - 선택 상태는 색·테두리·아이콘만으로 분명히 보이고 `완료` 문구나 안내 문구는 없다.
  - 정렬 중에는 연필·항목 추가·목록 맨 아래 `박스 추가`가 보이지 않고, 드래그 아이콘만 보인다.
  - 드롭 직후 이동한 행에서만 `저장 중` 상태가 보이며, 실패하면 원래 순서로 복구되고 오류 메시지가 표시된다.
- 브라우저 확인 시나리오: COCOON 관리 화면에서 일반 상태와 순서 변경 선택 상태를 번갈아 비교해 버튼의 선택 표현과 목록 아래 박스 추가의 비활성 상태를 확인한다.
- 우선순위: 중간

### 2. 목록 하단 `박스 추가` 아이콘과 텍스트의 시각적 균형 조정

- 화면/영역: 모바일 > 체크리스트 > 관리 > 제품 상세 목록 맨 아래 `박스 추가` 버튼.
- 증상: `+` 아이콘이 텍스트와 떨어져 보이며, 별도 장식처럼 보인다.
- 사용자 불편: 박스 추가의 의미는 알 수 있지만 아이콘과 텍스트가 하나의 행동으로 읽히지 않아 어색하다.
- 정정 정책: `+`는 별도 장식처럼 보이지 않는 선행 아이콘으로 두고, 16px 크기·수직 기준선·좁은 간격을 사용한다. 목록 맨 아래 `박스 추가`는 항목 추가와 구별되는 테두리 있는 가로 전체 버튼으로 둔다.
- 구현 방향: 목록 하단 보조 행동의 아이콘-텍스트 간격과 중앙 정렬을 조정하고, 가로 전체 테두리 버튼으로 렌더링한다. 새 아이콘 체계나 별도 버튼 모양은 추가하지 않는다.
- 수용 기준:
  - `+`와 `박스 추가` 텍스트가 하나의 중앙 정렬된 레이블로 보인다.
  - 아이콘이 버튼의 가운데에서 과도하게 떨어지거나 치우치지 않는다.
  - 목록 하단에서 `+`와 `박스 추가`가 하나의 보조 행동으로 읽힌다.
  - `박스 추가`는 항목 추가 행과 구분되는 가로 전체 테두리 버튼으로 보인다.
- 브라우저 확인 시나리오: COCOON 관리 화면에서 목록 맨 아래 `박스 추가`를 보고, 아이콘과 텍스트가 한 덩어리로 중앙 정렬되는지 확인한다.
- 우선순위: 중간

### 3. 정렬 선택 상태에서 `완료` 문구 제거

- 화면/영역: 모바일 > 체크리스트 > 관리 > 제품 상세 > 순서 변경 선택 상태.
- 증상: 순서 변경을 누르면 같은 버튼 자리에 `완료`가 표시돼, 사용자가 새로운 완료 단계나 별도 화면으로 느낄 수 있다.
- 사용자 불편: 정렬 모드가 단순 선택 상태라는 의도가 약해지고, 종료 행동이 불필요하게 강조된다.
- 정정 정책: 버튼의 보이는 텍스트는 선택 전후 모두 `순서 변경`으로 유지한다. 선택 상태는 파란 틴트·테두리·정렬 아이콘 강조와 `aria-pressed`로만 알린다. 같은 버튼을 다시 누르면 정렬 상태가 해제된다.
- 구현 방향: 정렬 상태의 `Check` 아이콘과 `완료` 텍스트를 제거하고, `ListOrdered` 아이콘과 `순서 변경` 레이블을 유지한다. 저장 대기는 만들지 않는다.
- 수용 기준:
  - 순서 변경 선택 상태에서도 화면 제목은 모델명이며 버튼 문구는 `순서 변경`이다.
  - `완료`라는 보이는 문구와 체크 아이콘은 없다.
  - 버튼은 선택 상태를 시각적으로 분명히 나타내고, 다시 누르면 일반 관리 목록으로 돌아온다.
- 브라우저 확인 시나리오: COCOON 관리 화면에서 순서 변경을 두 번 탭해 선택·해제 상태를 확인하고, 드래그 핸들이 선택 시에만 나타나는지 확인한다.
- 우선순위: 높음

### 4. 정렬 안내 문구 제거

- 화면/영역: 모바일 > 체크리스트 > 관리 > 제품 상세 > 순서 변경 선택 상태의 상단 버튼 아래.
- 증상: `박스와 항목을 길게 누르고 끌어 순서를 바꾸세요. 놓을 때마다 바로 저장됩니다.` 안내 문구가 정렬 목록 시작 전의 공간을 차지한다.
- 사용자 불편: 반복적으로 보이는 안내가 조작 자체보다 더 눈에 띄고 첫 항목을 아래로 밀어 화면 밀도가 떨어진다.
- 정정 정책: 안내 문구는 완전히 제거하며, 같은 자리에 대체 문구나 빈 여백을 남기지 않는다.
- 구현 방향: 정렬 상태에서만 렌더링하는 설명 `<p>`를 제거한다. 드래그 핸들과 삽입 표시가 조작 방법을 충분히 전달한다.
- 수용 기준:
  - 순서 변경 선택 시 상단 버튼 아래에 안내 문구가 표시되지 않는다.
  - 첫 박스가 버튼 묶음 다음의 기본 간격으로 바로 이어진다.
  - 일반 관리 상태와 정렬 상태 모두 스크롤과 하단 탭 바 동작이 유지된다.
- 브라우저 확인 시나리오: COCOON 관리 화면에서 순서 변경을 선택해 안내 문구가 없고 첫 박스가 바로 보이는지 확인한다.
- 우선순위: 낮음

### 5. 박스 메뉴의 역할과 배치 재정의

- 화면/영역: 모바일 > 체크리스트 > 관리 > 제품 상세 > 각 박스 헤더 오른쪽 `⋯` 메뉴.
- 증상: 박스 헤더와 분리된 작은 `⋯` 버튼이 무엇을 바꾸는지 바로 알기 어렵고, 카드 안에서 과도하게 독립된 조작처럼 보인다.
- 사용자 불편: 박스 이름 수정·삭제를 찾기 위해 임의의 메뉴를 눌러 봐야 하며, 박스 자체를 편집하는 흐름인지 구분하기 어렵다.
- 정정 정책: 박스 편집은 헤더 오른쪽의 연필 아이콘 버튼으로 연다. `⋯` 메뉴는 제거한다. 삭제는 어떤 선택지에서도 박스 편집 시트 안에만 둔다. 박스·항목 편집 시트의 저장 버튼은 하단에 고정하고, 변경 후 닫기에는 변경사항 폐기 확인을 둔다.
- 구현 방향: 결정된 진입 방식에 맞춰 박스 헤더의 정보 계층과 편집 액션을 재배치한다. 항목 행의 편집 진입과 혼동되지 않도록 아이콘·레이블·터치 영역을 분리한다. 편집 시트는 하단 고정 `저장` 버튼과 변경사항 폐기 확인 시트를 사용한다.
- 수용 기준:
  - 사용자가 박스 이름을 바꾸거나 박스를 삭제할 위치를 첫 화면에서 예측할 수 있다.
  - 박스 편집 액션이 항목 편집 행이나 정렬 핸들과 혼동되지 않는다.
  - 박스 삭제는 기존 확인 시트와 항목 수 안내를 유지한다.
  - 박스·항목 편집 시트에서 긴 입력을 해도 하단 `저장` 버튼을 항상 누를 수 있고, 변경 뒤 닫기에는 폐기 확인이 나온다.
- 브라우저 확인 시나리오: COCOON 관리 화면에서 기본 항목 박스의 편집 진입을 찾고, 이름 수정·삭제 확인까지의 흐름을 한 번에 확인한다.
- 우선순위: 중간

### 6. 박스와 항목 생성·편집의 계층 재검토

- 화면/영역: 모바일 > 체크리스트 > 관리 > 제품 상세의 목록 맨 아래 `박스 추가`, 박스 안 `항목 추가`, 박스 편집·항목 편집 시트.
- 증상: 박스를 추가한 뒤 항목을 채우고, 다시 박스 메뉴에서 박스 자체를 다루는 현재 구조가 사용자의 실제 입력 단위와 맞는지 불분명하다.
- 사용자 불편: 사용자가 지금 추가·수정하는 대상이 박스인지 항목인지, 새 박스를 만들 때 어떤 내용을 먼저 입력해야 하는지 판단하기 어렵다.
- 정정 정책: 체크리스트 관리의 기본 입력 단위는 `항목 추가·수정`이다. 박스는 아래 항목을 담는 제목으로만 보이며, 새 박스 생성은 항목을 담을 새 박스가 필요한 경우에만 사용하는 보조 흐름으로 둔다. 기존 데이터의 박스·항목 구조와 일반 체크 수행 화면은 유지한다. 사용자 화면의 용어는 `박스`로 통일하고, 새 박스는 목록 맨 아래의 `+ 박스 추가`로 만든다. 박스 간격은 12px, 카드 안쪽 여백은 16px, 항목 행 최소 높이는 52px로 둔다.
- 구현 방향: 상단의 `박스 추가` 행동은 없애고, 박스가 하나도 없는 제품에서는 화면 중앙에 `+ 박스 추가`만 표시한다. 박스가 있으면 모든 박스를 펼친 상태에서 12px 간격의 흰 카드로 묶고 카드 안쪽 여백은 16px으로 둔다. 박스 헤더는 제목과 오른쪽 연필 아이콘만 두고 `n개 항목` 표시는 제거한다. 카드 안 항목은 최소 52px 높이의 작은 일반 순번과 얇은 구분선으로 나눈 행으로 표시하고, 긴 문구는 생략하지 않고 자연스럽게 줄바꿈한다. 오른쪽 연필 아이콘과 행 탭으로 항목 편집 시트를 열며, 빈 박스에는 안내 문구 없이 `+ 항목 추가`만 표시한다. 각 박스의 마지막 줄 `+ 항목 추가`는 구분선 다음의 가운데 한 줄 행동으로 둔다. 목록 전체 맨 아래에 테두리 있는 가로 전체 보조 행동 `+ 박스 추가`를 두고, 공용 항목 추가 버튼은 만들지 않는다. 항목 편집 시트의 `다른 박스로 이동`은 박스 목록 시트를 열어 선택한 박스의 맨 아래로 즉시 이동한다. 박스 헤더·시트 제목·저장 행동을 항목 중심 흐름에 맞춰 다시 설계한다. API와 데이터 모델은 유지한다.
- 수용 기준:
  - 새 사용자가 첫 진입에서 박스와 항목의 관계를 설명 없이 구분할 수 있다.
  - 기본 관리 화면에서 모든 박스와 그 안의 항목이 펼쳐져 있다.
  - 각 박스의 제목·항목·항목 추가 버튼이 하나의 카드 안에서 함께 보인다.
  - 박스 헤더에는 제목과 편집 버튼만 보이고 `n개 항목` 표시는 없다.
  - 박스 카드 안의 항목은 개별 카드 없이 행과 구분선으로만 나뉜다.
  - 각 항목 행은 연필 아이콘과 함께 항목 편집 진입을 분명히 보여 준다.
  - 각 항목 행 왼쪽의 작은 일반 순번으로 현재 순서를 바로 확인할 수 있다.
  - 긴 항목 문구는 생략되지 않고 목록에서 전체를 확인할 수 있다.
  - 새 박스가 필요할 때 목록 맨 아래의 `+ 박스 추가`에서 생성할 수 있다.
  - 각 박스의 마지막 줄에서 해당 박스에 항목을 바로 추가할 수 있다.
  - `+ 항목 추가`는 항목 행과 구분선으로 분리된 가운데 한 줄 행동으로 보인다.
  - 빈 박스에는 별도 설명 문구 없이 `+ 항목 추가`만 보인다.
  - 박스가 하나도 없는 제품에서는 화면 중앙의 `+ 박스 추가`로 시작할 수 있다.
  - 박스 사이 간격은 12px, 카드 안쪽 여백은 16px, 항목 행의 최소 높이는 52px이다.
  - `다른 박스로 이동`을 누르면 박스 목록에서 대상을 고를 수 있고, 선택한 박스의 맨 아래에 항목이 즉시 이동한다.
  - 새 항목과 새 박스를 만들 때 필요한 입력 단계가 중복되지 않는다.
  - 기존 박스·항목 데이터, 항목 이동, 정렬, 삭제 확인 동작은 유지된다.
- 브라우저 확인 시나리오: 빈 박스가 있는 제품과 기존 항목이 있는 제품에서 각각 새 박스·새 항목을 추가하고, 수정·이동·삭제 진입 대상이 분명한지 확인한다.
- 우선순위: 높음

### 7. 마지막 콘텐츠와 하단 탭 바 사이 여백을 32px로 통일

- 화면/영역: 모바일 > 더보기, 불량, 입출고, 체크리스트 관리의 마지막 카드·버튼 아래와 고정 하단 탭 바 위.
- 증상: 화면마다 마지막 콘텐츠와 하단 탭 바 사이의 빈 공간이 62px, 74px처럼 크게 달라 보이며, 입출고 화면에서 사용자가 지정한 약 32px보다 넓다.
- 사용자 불편: 마지막 카드·버튼이 탭 바와 분리돼 화면 끝이 느슨하게 보이고, 탭마다 밀도가 달라 제품의 일관성이 깨진다.
- 정정 정책: 701×856 모바일 뷰포트에서 마지막 콘텐츠의 외곽선 하단부터 고정 하단 탭 바 컨테이너 외곽선 상단까지 정확히 32 CSS px를 유지한다. 고정 하단 탭 바의 레이아웃·디자인·높이·선택 표시 전환은 변경하지 않는다.
- 구현 방향: 화면별 `pb-*`, 스크롤 컨테이너, `flex-1`/`min-h-full` 확장 규칙을 실제 DOM 좌표로 측정한 뒤 조정한다. 하나의 패딩 값을 기계적으로 적용하지 말고, 각 화면에서 마지막 콘텐츠와 탭 바 경계가 32px가 되도록 공통 안전 여백 규칙을 정한다.
- 수용 기준:
  - 더보기, 불량, 입출고, 체크리스트 관리의 마지막 콘텐츠와 탭 바 사이 간격이 701×856에서 각각 32 CSS px다.
  - 마지막 콘텐츠는 탭 바와 겹치지 않고, 마지막 버튼의 44px 터치 영역과 스크롤 끝 도달이 유지된다.
  - 탭 바 자체의 모양, 높이, 그림자, 선택 표시 전환은 변경되지 않는다.
- 브라우저 확인 시나리오: 701×856 뷰포트에서 더보기·불량·입출고·체크리스트 관리의 마지막 콘텐츠까지 스크롤하고, DOM `getBoundingClientRect()`로 마지막 콘텐츠 하단과 탭 바 상단의 차이를 각각 32 CSS px로 확인한 뒤 스크린샷으로 교차 확인한다.
- 우선순위: 높음
