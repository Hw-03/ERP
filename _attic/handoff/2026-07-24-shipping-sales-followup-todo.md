## 확정 결정 요약

- 출하 요청 상세의 PA 구성품·PF 구성품·카톤·동반 출하품은 각 카드 내부가 아니라 요청 상세 페이지 전체가 세로로 늘어나도록 표시한다.
- 요청 메모는 상단 요약 영역이 아니라 하단 작업 영역의 왼쪽에 배치하고, 작업 버튼은 같은 영역의 오른쪽에 유지한다.
- 수정 이력의 BOM·동반 출하품 변경은 제외를 왼쪽, 추가를 오른쪽에 같은 품목 카드 양식으로 나누어 읽을 수 있게 한다.
- 출하 완료 이력에서는 완제품 SN을 제목 행의 중앙 독립 카드로, `픽업 완료 취소`를 우측 상태 영역으로 이동한다. 기존의 전체폭 SN 카드와 별도 취소 버튼 행은 제거해 아래 정보가 위로 이어지게 한다.
- 생산 가능수량 데스크톱 모달에서는 모델 그룹 행과 PF 상세 행의 `자동 기준` 보조 문구를 제거하되, 기준 출하품의 강조와 수량 계산은 유지한다.
- 대시보드 재고 KPI의 네 숫자는 MES 코드에 `-PA-` 또는 `-PF-`를 포함한 품목을 제외해 계산하되, 재고 목록과 카드 클릭 필터의 표시 대상은 바꾸지 않는다.
- 출하 허브에서는 `출하 관리` 또는 `출하 이력` 카드를 눌러 진입할 때만 불량 탭과 같은 기존 내부 전환 애니메이션을 한 번 적용한다.
- 준비 완료 요청의 완제품 SN은 요청 제목 행 바로 아래에 두고, 수정 이력·구성품보다 먼저 확인할 수 있게 한다.
- 전체 일보에서 작성한 직원을 선택했을 때는 본인·타인 여부와 무관하게 MES 작업 기록 아래의 작업 내역 카드가 남은 화면 높이를 채운다. 타인 일보는 읽기 전용으로 유지한다.
- 전체 일보의 작성한 직원 선택으로 조회 대상을 바꿀 때만 기존 내부 슬라이드·페이드 전환을 한 번 적용한다.

## 확정 정책

- 인보이스는 선택 입력으로 시작하되 `준비 완료`에는 필수입니다.
- 인보이스는 공백 제거·대문자화 후 최대 100자로 저장하며, 같은 번호를 여러 요청에서 사용할 수 있습니다.
- 모든 보존 상태에서 번호를 정정할 수 있지만 한 번이라도 준비 완료된 요청은 공란으로 되돌릴 수 없습니다.
- 취소는 물리 삭제가 아니라 `CANCELLED` 전환이며 요청·수정 이력·취소자를 보존합니다.
- 수정 권한은 부서·직급으로 막지 않고, `X-MES-Employee-Code`로 확인한 활성 직원을 기록합니다.
- 모바일 `수정됨`은 준비 작업에 영향을 주는 최신 수정만 보여 주며 별도 읽음 처리는 없습니다.
- 중요 품목은 `PC 관리 > 품목 관리 > 기본 정보 > 영업 확인 필요`에서 설정합니다.
- 별도 출고처 필드를 만들지 않고 PF 품명으로 이력을 검색합니다.

### 9. [완료] 수정 이력 구성품 변경을 제외·추가 좌우 카드로 표시

- 화면/영역: PC 출하 > 요청 상세 > `수정 이력` > BOM 구성 또는 동반 출하품 변경 이력 펼침
- 증상: 현재 BOM·동반 출하품 변경은 품명·MES 코드·수량을 카드에 표시하지만, 제외·추가·변경 전후가 하나의 세로 카드 목록 안에 섞인다. 변경이 많아지면 어느 품목이 제외되고 무엇이 추가됐는지 가로로 바로 대조하기 어렵다.
- 사용자 불편: 수정 이력 폭이 넓어져도 품목 변경의 방향을 위아래로 훑어야 해, 출하 구성의 교체 내용을 빠르게 검산하기 어렵다.
- 확정 정책: PA·PF·카톤·동반 출하품 그룹마다 `제외`를 왼쪽, `추가`를 오른쪽에 같은 품목 카드 양식(품명, MES 코드, 수량)으로 배치한다. 하나의 품목이 변경 전·후를 모두 가진 수량/구성 변경은 같은 좌우 문법으로 변경 전을 왼쪽, 변경 후를 오른쪽에 둔다. 한쪽에 실제 변경이 없으면 빈 큰 카드나 빈 목록은 만들지 않는다.
- 구현 방향: 구성품 변경 전용 렌더러가 각 변경의 이전·이후 스냅샷을 좌측 제외/변경 전과 우측 추가/변경 후 흐름으로 분류하고, 두 쪽 모두 현재 `RevisionArrayChangeCard`와 같은 정보 밀도·상태 색을 사용하게 한다. PA/PF/기타 또는 카톤·동반 출하품 그룹 구분과 비-BOM 필드 이력의 기존 표시 방식은 유지한다.
- 수용 기준: BOM 또는 동반 출하품 이력을 펼치면 제외·변경 전 품목은 왼쪽, 추가·변경 후 품목은 오른쪽에서 같은 카드 형식으로 비교할 수 있다. 각 카드에서 품명·MES 코드·수량·변경 상태가 식별되며, 한쪽 변경이 없는 경우에는 불필요한 빈 카드가 없다. 비-BOM 필드 이력의 표시와 각 이력의 펼치기 동작은 유지한다.
- 브라우저 확인 시나리오: `shippingRequestId=6e39e949-f5a2-482f-9ab9-f076e61ebf7c`의 카톤·동반 출하품 변경과 PA/PF 구성품에 추가·제외·수량 변경이 섞인 요청을 각각 펼친다. 제외·변경 전과 추가·변경 후가 좌우 같은 양식으로 표시되고, 품목·코드·수량·상태를 바로 대조할 수 있는지 확인한다.
- 우선순위: 높음

### 11. [완료] 인보이스 번호를 요청 상세 헤더로 이동하고 수정 이력을 전체 폭으로 확장

- 화면/영역: PC 출하 > 요청 상세(`shippingView=requestDetail`) > 요청 제목 헤더, `인보이스 번호`, `수정 이력`.
- 증상: 인보이스 번호 입력·저장 카드가 요청 제목 바로 아래의 왼쪽 열을 단독으로 차지하고, 수정 이력은 오른쪽 열에만 배치된다. 수정 이력이 여러 건인 요청에서도 이력 카드가 절반 폭에 묶이며, 펼친 이력은 내부 최대 높이와 스크롤에 갇혀 아래 구성품·작업 영역을 자연스럽게 밀어내지 못한다.
- 사용자 불편: 요청을 식별하고 인보이스 번호를 관리하는 정보가 제목과 분리되어 상단 시선 흐름이 끊긴다. 수정 이력이 많은 요청은 정작 넓게 보여야 할 이력 영역이 인보이스 입력 카드 때문에 불필요하게 좁고, 펼친 상세를 읽으려면 이력 안에서 다시 스크롤해야 한다.
- 확정 정책: 인보이스 번호의 라벨·입력·저장 동작을 요청 제목 행에서 품명 정보와 상태 배지 사이의 빈 영역으로 이동한다. 기존의 독립 인보이스 카드는 제거한다. 준비 완료 요청의 `완제품 SN`은 요청 제목 행 바로 아래에 전체 폭으로 표시하고, 그 아래에 수정 이력 카드를 요청 상세 폭 전체로 둔다. 수정 이력은 고정 높이나 내부 세로 스크롤을 두지 않고, 이력을 펼친 내용만큼 요청 상세 패널 전체가 세로로 늘어나 아래 구성품·메모·작업 영역을 자연스럽게 아래로 민다. 준비 완료 요청에서도 수정 잠금·상태 배지와 겹치지 않게 같은 배치를 유지한다.
- 구현 방향: `RequestDetailEntry`의 상단 헤더에 인보이스 편집기를 인라인으로 배치하고, 독립 카드용 여백·테두리 표현은 제거한다. `InvoiceNumberEditor`의 저장, 미변경 비활성화, 준비 완료 이력 보유 시 번호 삭제 차단, 오류/필수 안내의 기존 동작은 보존한다. 준비 완료 조건의 완제품 SN `Notice`를 현재 수정 이력 아래 위치에서 제목 헤더 직후로 옮긴다. 인보이스 편집기와 수정 이력의 2열 grid를 없애고 `RevisionHistory`를 전체 폭 섹션으로 렌더링한다. 수정 이력 목록의 `max-height`·`overflow-y-auto` 제약을 제거해 바깥 요청 상세 스크롤만 사용하며, 각 이력의 펼치기 동작은 유지한다. 좁은 데스크톱 폭에서는 인보이스 입력과 상태 영역이 자연스럽게 줄바꿈되어 겹치지 않게 한다.
- 수용 기준:
  - 요청 상세 상단에서 인보이스 번호의 라벨, 현재 값, 저장 버튼을 품명 정보와 상태 배지 사이에서 바로 확인하고 수정할 수 있다.
  - 제목 아래에는 독립적인 인보이스 입력 카드나 그 카드 때문에 생긴 왼쪽 빈 영역이 없다.
  - `PREPARED` 요청에서는 요청 제목 행 바로 아래에 완제품 SN이 표시되고, 수정 이력·PA/PF/카톤·동반 출하품 요약보다 먼저 확인할 수 있다.
  - 수정 이력 카드는 요청 상세의 전체 가로 폭을 사용하며, 이력 1건 요청과 이력 3건 이상 요청 모두에서 제목·변경 요약·펼치기 동작이 기존보다 넓은 영역에 표시된다.
  - 이력을 펼치면 수정 이력 내부에 별도 세로 스크롤바가 생기지 않고, 열린 내용만큼 요청 상세 패널이 높아져 완제품 SN·구성품·요청 메모·작업 버튼이 아래로 자연스럽게 이동한다.
  - 인보이스 저장, 저장 중/미변경 비활성화, 준비 완료 이력 보유 시 기존 번호를 비울 수 없는 규칙, 수정 이력 갱신과 각 이력 펼치기 동작은 기존과 동일하다.
  - `PREPARED` 요청의 수정 잠금·상태 배지와 완제품 SN 안내의 내용, PA/PF/카톤·동반 출하품 요약 및 하단 작업 버튼의 기존 동작은 보존된다.
- 브라우저 확인 시나리오:

### 14. [완료] 출하 허브 카드 진입에 기존 화면 전환 애니메이션 적용

- 화면/영역: PC 출하 > 작업 선택 허브 > `출하 관리`, `출하 이력` 카드 클릭 후 각각의 목록 화면.
- 증상: 출하 허브 카드를 누르면 `requestList` 또는 `historyList`가 즉시 교체되어 화면이 끊겨 보인다. 불량 탭의 `불량 격리` 카드와 입출고의 작업 유형 진입은 기존 슬라이드·페이드 전환으로 다음 화면에 자연스럽게 들어간다.
- 사용자 불편: 같은 형태의 업무 진입 카드인데 출하만 화면이 갑자기 바뀌어, 작업 맥락이 이어지는 느낌과 화면 간 일관성이 떨어진다.
- 확정 정책: `출하 관리`와 `출하 이력` 허브 카드를 눌러 각각의 첫 목록으로 들어갈 때만 기존 `animate-view-fade` 전환을 한 번 적용한다. 최초 허브 화면, 목록에서 허브로 돌아가기, 목록 내부의 요청 상세·작성·준비 체크·이력 상세 전환에는 이 항목 때문에 추가 애니메이션을 적용하지 않는다.
- 구현 방향: 허브 카드 클릭 경로(`openSection` → `requestList`/`historyList`)만 식별해, 해당 목적지 렌더링을 기존 전환 클래스와 재마운트 키로 감싼다. 공통 CSS의 200ms 전환과 `prefers-reduced-motion` 비활성화 규칙을 재사용하며, URL·브라우저 뒤로가기 동기화와 기존 목록 데이터 로딩은 바꾸지 않는다.
- 수용 기준:
  - `출하 관리` 카드를 누르면 요청 목록이 우측에서 부드럽게 나타나고, `출하 이력` 카드를 누르면 이력 목록에도 같은 전환이 적용된다.
  - 처음 출하 탭을 열었을 때의 두 허브 카드와 목록에서 허브로 돌아온 화면에는 이 내부 전환이 재생되지 않는다.
  - 목록에서 요청 상세·작성·준비 체크·이력 상세로 이동하거나 브라우저 뒤로가기를 사용할 때 기존 URL, 선택 상태, 데이터 로딩, 목록 스크롤 동작은 바뀌지 않는다.
  - 동작 줄이기 환경에서는 기존 전역 규칙에 따라 애니메이션 없이 즉시 전환된다.
- 브라우저 확인 시나리오: PC 출하 허브에서 두 카드를 각각 누르고 목록에서 허브로 돌아온다. 이어서 요청 상세·작성·준비 체크·이력 상세와 브라우저 뒤로가기를 실행해, 카드 진입에만 전환이 한 번 재생되고 기존 출하 동선과 URL이 유지되는지 확인한다.
- 우선순위: 중간

#### 12. [완료] 생산 가능수량 표의 중복 `자동 기준` 문구 제거

- 화면/영역: PC 대시보드 > `생산 가능수량` 모달 > 모델 그룹 행의 기준 출하품 이름 끝, 펼친 PF 상세 행의 상태 배지.

- 사용자 불편: 생산 가능 수량을 빠르게 비교할 때 같은 의미의 보조 문구가 반복되어 품명과 병목·수량 정보보다 불필요하게 눈에 띈다.
- 확정 정책: 사용자가 표시한 두 데스크톱 위치에서만 `자동 기준` 문구를 제거한다. 기준 PF의 청록색 강조, 모델 그룹의 대표 PF 선택, 출하 대기·빠른 생산·총생산 수량 계산은 그대로 유지한다. 열 제목 `자동 기준 출하품`과 모바일의 별도 설명·표시는 이 항목의 변경 범위에서 제외한다.
- 구현 방향: 모델 그룹 행의 대표 PF 이름 뒤 텍스트와 PF 상세 행의 상태 배지만 조건부 렌더링에서 제거한다. 대표 PF 여부를 판단하는 `autoRepresentative`/`isAutoRepresentative` 값과 그에 따른 배경·외곽선·수량 셀은 유지한다.
- 수용 기준:
  - 대표 출하품이 있는 모델 그룹 행에서 PF 이름만 보이고 `자동 기준` 문구는 보이지 않는다.
  - 펼친 PF 상세 행에서도 `자동 기준` 배지는 보이지 않지만, 대표 PF의 청록색 강조와 생산 가능 아이콘은 그대로 보인다.
  - 대표 PF가 없는 모델의 `출하 경로 없음`, 열 제목, 출하 대기·빠른 생산·총생산 값과 모달의 접기·펼치기 동작은 바뀌지 않는다.
- 브라우저 확인 시나리오: PC 대시보드에서 `생산 가능수량`을 열고 대표 출하품이 있는 모델 그룹과 그 PF 상세 행을 차례로 확인한다. 두 위치에 `자동 기준`이 없고, 대표 PF 강조·수량·병목 정보 및 다른 모델의 펼치기 동작이 그대로인지 확인한다.
- 우선순위: 중간

#### 13. [완료] 재고 KPI 숫자에서 PA·PF 중간 품목 제외

- 화면/영역: PC·모바일 대시보드 > 상단 재고 KPI `전체`, `정상`, `부족`, `품절` 숫자.
- 증상: 현재 KPI는 삭제되지 않은 모든 품목 또는 현재 범위의 모든 품목을 대상으로 계산해, MES 코드에 `-PA-` 또는 `-PF-`가 포함된 중간 공정 품목까지 네 숫자에 포함한다.
- 사용자 불편: 완제품·일반 자재의 재고 운영 현황을 보려는 상단 KPI가 PA/PF 중간 품목 수까지 더해져 전체·정상·부족·품절의 운영 판단용 숫자가 커진다.
- 확정 정책: MES 코드가 정확히 `-PA-` 또는 `-PF-`를 포함하는 품목은 상단 네 KPI 숫자에서 모두 제외한다. 이 예외는 KPI 숫자 계산에만 적용하며, 재고 목록, 검색·부서·공정 필터, KPI 카드 클릭 후 목록에 표시되는 품목과 생산 가능수량 계산은 기존대로 유지한다. MES 코드가 없거나 다른 코드인 품목, 삭제 품목 제외 규칙은 기존 정책을 따른다.
- 구현 방향: 공통 대시보드 KPI 파생 훅에서 MES 코드 패턴을 판별하는 작은 순수 조건을 두고, 기본·필터 상태의 KPI용 집합과 전체 KPI 수를 그 집합으로 계산한다. 목록 필터에 사용하는 `matchesKpi`와 경고 전달용 기존 집계는 그대로 두어, 요청 범위를 카드 숫자에 한정한다.
- 수용 기준:
  - MES 코드에 `-PA-` 또는 `-PF-`가 있는 품목은 `전체`, `정상`, `부족`, `품절` 어느 카드 숫자에도 포함되지 않는다.
  - 다른 품목의 재고 상태 판정, 소프트 삭제 품목 제외, 검색·부서·공정 필터 적용 후의 KPI 숫자 계산은 기존 규칙을 유지한다.
  - KPI 카드를 눌렀을 때 재고 목록의 기존 필터 결과와 PA/PF 품목의 목록 표시 여부는 바뀌지 않는다.
  - 데스크톱과 모바일이 같은 KPI 파생 로직을 사용하므로 같은 데이터에서 네 카드 숫자가 일치한다.
- 브라우저 확인 시나리오: MES 코드가 각각 `-PA-`, `-PF-`, 그 외 코드인 품목을 포함한 데이터에서 PC와 모바일 대시보드를 열어 네 KPI 숫자를 비교한다. PA/PF 품목의 재고 상태를 바꿔도 상단 네 숫자가 변하지 않고, 재고 목록 및 KPI 카드 클릭 결과에는 해당 품목이 기존처럼 남는지 확인한다.
- 우선순위: 높음

### 일일 작업 일보

#### 15. [완료] 전체 일보의 읽기 전용 작업 내역도 남은 화면 높이를 채우기

- 화면/영역: PC 일일 작업 일보 > `전체 일보` > `작성한 직원`에서 본인 또는 다른 직원을 선택한 뒤의 `MES 작업 기록`·`작업 내역` 영역.
- 증상: 본인을 선택하면 편집 가능한 `작업 내역` 카드와 입력창이 MES 작업 기록 아래의 남은 높이를 채운다. 다른 직원을 선택하면 읽기 전용 카드가 내용 높이만큼만 렌더링되고, 카드 아래에 큰 빈 화면 영역이 남는다. 개발 코드도 편집 가능 여부에 따라 바깥 스크롤·카드 `flex-1` 적용을 갈라 이 차이가 난다.
- 사용자 불편: 같은 날짜·같은 전체 일보 조회에서 선택한 직원이 본인인지 타인인지에 따라 핵심 작업 내역 상자의 크기와 화면 밀도가 달라져, 타인 일보를 읽을 때 내용이 화면에 자연스럽게 이어지지 않는다.
- 확정 정책: `전체 일보`에서 작성한 직원을 선택한 뒤 MES 거래 상세가 닫혀 있으면, 본인·타인 모두 `MES 작업 기록`을 상단에 두고 `작업 내역` 카드가 남은 데스크톱 높이를 채운다. 타인 일보는 계속 읽기 전용이며 저장·입력 기능을 만들지 않는다. 긴 타인 일보의 본문은 채워진 카드 안에서만 스크롤하고, MES 거래 상세를 펼칠 때는 기존처럼 페이지 본문이 세로로 흐르게 한다.
- 구현 방향: `DailyWorkReportScreen`의 편집 가능 여부 중심 높이·스크롤 분기를 MES 거래 상세 열림 여부 중심으로 통일하고, `DailyWorkReportEditor`의 읽기 전용 분기에도 남은 높이를 채우는 카드·본문 제약을 적용한다. 읽기 전용의 입력 금지, 저장 버튼 부재, 현재 장문 본문 내부 스크롤과 MES 거래 상세의 바깥 스크롤 규칙은 보존한다.
- 수용 기준:
  - 전체 일보에서 본인 또는 다른 직원을 선택해도 MES 작업 기록 아래의 작업 내역 카드 하단이 같은 화면 하단 흐름까지 이어져 큰 빈 영역이 남지 않는다.
  - 다른 직원의 작업 내역은 읽기 전용 텍스트로만 보이고, 입력창·저장 버튼·수정 상태는 표시되지 않는다.
  - 긴 타인 일보는 채워진 읽기 전용 카드의 본문에서 스크롤해 끝까지 읽을 수 있으며, 카드 자체가 화면 밖으로 불필요하게 늘어나지 않는다.
  - MES 거래 상세를 펼치면 본인·타인 모두 기존처럼 일보 본문을 세로로 스크롤해 상세와 작업 내역을 확인할 수 있다.
- 브라우저 확인 시나리오: 개발 서버(`:3001`)의 PC 일일 작업 일보에서 `전체 일보`를 열고 작성자 칩으로 본인과 다른 직원을 차례로 선택한다. 각 경우 MES 작업 기록·작업 내역 카드의 하단 정렬을 비교하고, 타인의 짧은/긴 일보와 MES 거래 상세 펼침 상태에서 읽기 전용·내부 본문 스크롤·페이지 스크롤을 확인한다. 직원 서버(`:3000`)는 레이아웃 참고만 하고 수정하지 않는다.
- 우선순위: 중간

#### 16. [완료] 전체 일보의 작성자 전환에 기존 내부 애니메이션 적용

- 화면/영역: PC 일일 작업 일보 > `전체 일보` > `작성한 직원` 칩에서 다른 작성자를 선택할 때의 MES 작업 기록·작업 내역 결과 영역.
- 증상: 작성자 칩을 누르면 선택 상태와 조회 결과가 즉시 교체된다. 불량 작업 흐름 등에는 이미 기존 슬라이드·페이드 내부 전환이 있지만, 일보의 작성자 전환에는 결과 영역의 전환 효과가 없다.
- 사용자 불편: 여러 직원의 일보를 연속으로 읽을 때 이전 결과와 다음 결과의 맥락이 갑자기 바뀌어, 선택한 직원과 결과가 연결되는 느낌이 약하다.
- 확정 정책: `전체 일보`에서 작성자 칩으로 이미 열어 둔 다른 작성자 결과를 바꿀 때만 기존 `animate-view-fade` 전환을 한 번 적용한다. 최초 일보 탭 진입, `내 일보`·`전체 일보` 탭 전환, 날짜 변경, MES 거래 상세 펼침·접힘, 저장 및 데이터 갱신에는 이 항목 때문에 전환을 추가하지 않는다.
- 구현 방향: 작성자 선택으로 바뀌는 결과 묶음에 선택 직원 ID 기반 재마운트 키와 기존 `animate-view-fade` 클래스를 적용한다. 공통 CSS의 200ms 전환과 `prefers-reduced-motion` 비활성화 규칙을 재사용하며, 선택 칩 상태, 읽기 전용 권한, 조회·저장·더티 가드의 기존 동작은 변경하지 않는다.
- 수용 기준:
  - 전체 일보에서 한 작성자 결과를 연 뒤 다른 작성자 칩을 누르면 MES 작업 기록과 작업 내역 결과가 기존과 같은 방향·속도의 전환으로 한 번 자연스럽게 나타난다.
  - 최초 화면 진입, 일보 탭·날짜 변경, MES 거래 상세 토글과 저장 후에는 불필요하게 전환이 반복되지 않는다.
  - 작성자 칩의 선택 강조, 조회 로딩·오류·빈 일보 표시, 읽기 전용 규칙과 본인 일보의 저장·더티 가드 동작은 기존과 동일하다.
  - 동작 줄이기 환경에서는 기존 전역 규칙에 따라 애니메이션 없이 즉시 결과가 바뀐다.
- 브라우저 확인 시나리오: 개발 서버(`:3001`)의 PC 일일 작업 일보에서 전체 일보를 열고 서로 다른 작성자 칩을 연속 선택한다. 매 선택 때 결과 영역의 전환이 한 번만 재생되는지 확인하고, 이어서 탭·날짜를 바꾸고 MES 거래 상세를 열고 닫고 본인 일보를 저장해 불필요한 전환과 기존 동작 회귀가 없는지 확인한다.
- 우선순위: 낮음
