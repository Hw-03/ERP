## 자율 점검 기준

- 같은 작업 탭 안의 빈 목록 영역은 같은 높이 문법을 사용한다.
- 빈 상태도 실제 목록이 표시될 자리의 가용 영역을 명확하게 보여 준다.
- 실제 요청 행, 로딩, 오류 상태와 모바일 레이아웃은 이번 변경으로 의도치 않게 달라지지 않는다.

## 확정 결정 요약

- 데스크톱 입출고의 `작성 중`, `창고 승인함`, `부서 승인함`에서 데이터가 없을 때 공용 빈 작업영역은 탭 아래 가용 높이를 모두 사용한다.
- 입출고 품목 전환의 기존 품목·대상 품목 후보 목록은 `_attic/docs/EXTERNAL_SCROLLBAR_RAIL_GUIDE.md`의 방식으로 데스크톱 스크롤바를 각 카드 바깥 레일에 표시한다.
- 품목 전환의 카드 안내는 실제 대상 범위에 맞춰 `기존 품목 재고를 대상 품목 재고로 전환합니다.`로 표시한다.
- 기준 크기는 `요청 작성` 첫 화면의 작업 유형 카드 영역이며, 하단의 별도 여백 때문에 빈 작업영역이 짧아 보이지 않아야 한다.
- 범위는 사용자가 지정한 세 빈 상태로 한정한다. `내 요청`, 인수인계, 모바일 및 데이터가 있는 목록의 레이아웃은 변경하지 않는다.
- 데스크톱 입출고내역의 선택된 상세 패널은 목록과의 좌측 간격 및 콘텐츠 우측 경계와의 우측 간격을 같은 시각적 여백으로 맞춘다.
- 출하 요청 상세의 상태 표시는 헤더 우측 행동 영역과 균형을 이루도록 확장한다.
- 출하 상세 이력의 완제품 SN과 인보이스 번호는 인보이스 입력 카드 배치 문법으로 통일해 같은 선상에 놓는다.
- 관리자 BOM의 상위 품목·하위 품목·현재 구성 목록은 `_attic/docs/EXTERNAL_SCROLLBAR_RAIL_GUIDE.md`의 shell·viewport·고정 frame 방식으로 데스크톱 세로 스크롤바만 각 카드 오른쪽 바깥 레일로 옮긴다.
- F705-02 생산일지 다운로드는 관리자 내보내기와 주간보고에 모두 제공하며, 주간보고에서는 생산 현황 카드 우측에 버튼 하나만 추가한다. 이는 주간보고 동결 범위에 대한 사용자 승인 예외이며, 그 외 동결된 파일·디렉터리의 레이아웃·내용·동작은 수정하지 않는다.
- 출하 요청 작성의 PF·PA·PF 구성품 내부 목록과 출하 요청 상세·이력 목록·상세 이력의 세로 스크롤은 `_attic/docs/EXTERNAL_SCROLLBAR_RAIL_GUIDE.md`를 적용한다. 실제 스크롤되지만 `scrollbar-hide`로 레일이 보이지 않는 상세 이력에는 같은 가이드 방식으로 보이는 바깥 레일을 추가한다.
- 출하 요청 목록과 상세 이력의 흰색 둥근 외곽 작업 표면을 출하 화면의 기준으로 삼고, 프레임이 빠진 요청 상세·이력 목록에 같은 표면 문법을 적용한다.
- 직원 선택 검색의 영문 자판 한글 조립은 Shift를 포함한 두벌식 키를 보존해 `ㅒ`·`ㅖ`와 쌍자음도 올바르게 입력·검색한다.
- 대시보드 다크모드 BOM 상세 행은 들여쓰기·연결선 변경 없이, 깊어질수록 표면이 점진적으로 진해지는 라이트 모드와 같은 방향의 계층 색상 규칙을 사용한다.
- 출하 요청 목록의 모든 요청 카드에는 기존 `request_quantity`를 사용한 `출하 수량: N대` 정보를 요청 일시·요청자와 같은 메타데이터 위계로 표시한다.
- 출하 요청·이력 목록 카드는 품목 정체성과 상태를 상단에 두고 일시·요청자·수량·인보이스를 라벨/값 정보 블록으로 분리한다. 좁은 요청 보드와 넓은 이력 목록은 같은 시각 문법을 유지하되 각 폭에 맞는 2열/4열 배치를 사용한다.

- 증상: 부모·자식·손자 BOM 행이 매우 비슷한 표면색과 구분선으로 연속 표시되어, 들여쓰기와 펼침 화살표만으로는 행의 깊이를 빠르게 판별하기 어렵다.
- 사용자 불편: 긴 BOM에서 어떤 행이 상위 조립품이고 어떤 행이 하위 구성품인지 한눈에 읽히지 않아, 재고 수량과 부족 행을 계층 맥락으로 판단하기 어렵다.
- 확정 정책:
  - 들여쓰기, 펼침 화살표, 행 높이, 경계·연결선 규칙은 유지하고 행 배경색만 깊이별로 구분한다.
  - 다크모드에서도 depth가 깊어질수록 표면이 점진적으로 진해져 라이트 모드와 같은 방향의 계층 의미를 갖게 한다.
  - 밝은 모드의 현재 파란색 혼합 비율은 유지한다. 다크모드에서는 현재의 파란색 혼합이 표면을 연하게 만드는 방향이므로, 어두운 중성/잉크 색을 섞는 별도 테마 비율로 전환한다.
  - 부족·0 재고 경고, 선택·hover·focus 상태는 기존 우선순위를 유지한다.
- 구현 방향: 기존 depth별 tint 퍼센트 계산을 재사용하되, 테마별 혼합 대상 색을 분리한다. 라이트 모드는 현행 blue→surface 혼합을 유지하고, 다크모드는 같은 depth 비율로 dark ink→surface 혼합을 적용해 단계가 깊어질수록 명도만 낮아지게 한다. 열 그리드, 품목·수량·현재 재고 정보, 행 조작과 스크롤은 변경하지 않는다.
- 수용 기준:
  - 다크모드에서 연속한 부모·자식·손자 행의 표면이 깊어질수록 점진적으로 진해져, 수평 들여쓰기 외에도 깊이를 즉시 구분할 수 있다.
  - 정상 재고 행의 계층 표현이 부족/0 재고 경고색, 선택 테두리, hover·focus와 의미적으로 충돌하지 않는다.
  - 긴 품목명·코드·소요량·현재 재고의 가독성과 행 클릭·펼치기·접기 동작이 유지된다.
  - 밝은 모드와 다른 BOM 표시 화면은 의도치 않게 바뀌지 않는다.
- 브라우저 확인 시나리오: 다크모드에서 대시보드 BOM 구성 보기를 열어 3단계 이상 중첩된 BOM을 상단·중간·하단에서 확인한다 → 인접 부모·자식·손자, 정상 재고·부족 재고·0 재고, 선택·hover·focus 상태를 비교한다 → 펼치기·접기와 행 클릭 뒤 계층 표현이 유지되는지 확인한다 → 밝은 모드와 입출고/재고 상세의 BOM 표시를 비교한다.
- 우선순위: 중간

- 수용 기준:
  - 검색 입력에서 Shift+P는 `ㅖ`, Shift+O는 `ㅒ`로 표시된다.
  - Shift+R/E/Q/T/W는 각각 `ㄲ/ㄸ/ㅃ/ㅆ/ㅉ`로 조립된다.

  - 기존 기본 자모와 복합 모음·받침 조합 결과가 회귀하지 않는다.
- 브라우저 확인 시나리오: 로그인 화면에서 직원 검색을 열어 영문 자판 상태로 Shift+P와 Shift+O, Shift 자음을 입력해 기대 한글이 표시되는지 확인한다 → Shift 자모가 포함된 이름·부서와 일반 이름·직원 코드를 각각 검색해 결과를 선택한다 → Backspace·공백·혼합 라틴 입력, Enter·Tab·Shift+Tab·Escape를 확인한다 → 한국어 IME로 직접 입력한 완성형 한글 검색도 비교한다.

- 브라우저 확인 시나리오: 데스크톱 `?tab=warehouse` 요청 작성 첫 화면에서 품목 전환 카드의 설명을 확인한다 → 카드를 열어 AA와 PA 후보 품목을 각각 선택할 수 있는지 기존 동작을 확인한다 → 원자재 입고·창고 입출고·부서 입출고·AS·연구 사용출고·수량보정 카드 문구와 클릭 동작이 변하지 않는지 확인한다.

### 2. 선택 상세 패널의 좌우 바깥 여백 통일

- 화면/영역: 데스크톱 입출고내역 > 거래 목록 우측의 선택 상세 패널.
- 증상: 선택된 상세 패널의 목록 쪽 왼쪽 간격과 패널 오른쪽에서 콘텐츠 경계까지의 간격이 서로 달라 보인다. 사용자 표시 기준에서 두 간격은 각각 약 15px와 28px로 지정됐다.
- 사용자 불편: 한 화면 안에서 같은 상세 패널의 양옆 여백 문법이 달라, 패널이 목록과 콘텐츠 영역 사이에서 수평으로 정렬되지 않은 것처럼 보인다.
- 확정 정책:
  - 데스크톱 입출고내역에서 상세 패널 왼쪽과 오른쪽의 바깥 여백은 같은 시각적 간격으로 통일한다.
  - 기준은 목록 우측 경계(스크롤 영역 포함)와 상세 패널 사이의 현재 간격이다.
  - 상세 패널의 내부 padding, 폭, 둥근 모서리, 목록 열 너비와 스크롤 동작은 변경하지 않는다.
- 구현 방향: `DesktopHistoryView.tsx`의 전체 작업영역 우측 padding과 `SlidePanel.tsx`의 패널 시작 여백이 합쳐지는 경로를 확인한 뒤, 상세 패널이 열린 데스크톱 입출고내역에서만 좌우 바깥 여백이 동일해지도록 한쪽의 외부 spacing을 조정한다. 다른 `SlidePanel` 사용처와 패널 내부 레이아웃에는 영향을 주지 않도록 history 화면의 조정 지점을 우선한다.
- 수용 기준:
  - 선택된 상세 패널의 왼쪽 바깥 여백과 오른쪽 바깥 여백이 육안으로 동일하다.
  - 1920px 데스크톱 화면에서 목록·세로 스크롤바·상세 패널·콘텐츠 우측 경계가 균형 있게 정렬된다.
  - 상세 패널을 닫았을 때 목록 영역의 폭과 스크롤 동작은 기존과 같다.
  - 상세 패널의 제목·닫기 버튼·본문 스크롤·하단 취소 동작은 유지된다.
  - 다른 화면의 우측 슬라이딩 패널과 모바일 레이아웃은 변경하지 않는다.
- 브라우저 확인 시나리오: 데스크톱 `?tab=history`를 열어 목록 행을 선택한다 → 목록 우측 경계와 상세 패널 왼쪽 간격, 상세 패널 오른쪽과 콘텐츠 경계 간격이 동일한지 확인한다 → 서로 다른 거래·BOM 묶음 상세를 선택해 패널 내용 길이가 바뀌어도 간격이 유지되는지 확인한다 → 닫기 버튼과 ESC로 패널을 닫아 목록이 원래 폭으로 복원되는지 확인한다 → 다른 메뉴의 슬라이딩 패널과 모바일 폭에서 회귀가 없는지 확인한다.

## 출하

### 3. 요청 상세의 상태 표시 영역을 헤더 우측 공간에 맞게 확장

- 화면/영역: 데스크톱 출하 > 출하 요청 상세(`shippingView=requestDetail`) 헤더 우측의 `준비 중` 상태 표시와 인접 빈 영역.
- 증상: 상태 표시는 작은 pill 형태라, 헤더 우측에 남는 높이·너비에 비해 작게 떠 보인다.
- 사용자 불편: 요청 상세의 핵심 상태가 헤더 영역에서 충분한 시각적 비중을 갖지 못하고, 상태 표시 주변의 빈 공간이 어색하게 남는다.
- 확정 정책:
  - 요청 상세 헤더의 상태 표시는 우측 행동 영역 안에서 자연스럽게 공간을 채우는 충분한 크기로 확장한다.
  - 상태명·색상·상태 전이 권한과 동작은 유지한다.
  - 다른 화면에서 쓰는 작은 상태 pill은 이번 범위에 포함하지 않는다.
- 구현 방향: 요청 상세 헤더에서만 `StatusBadge`를 감싸는 우측 행동 영역의 사용 가능 폭·높이를 확인한다. 공용 상태 pill의 전역 크기를 일괄 변경하지 않고, 해당 화면 전용 외부 컨테이너 또는 변형을 추가해 `준비 중` 등 상태가 헤더의 빈 공간과 균형을 이루도록 한다.
- 수용 기준:
  - 요청 상세 헤더의 상태 표시가 현재 pill보다 충분히 커져 우측 빈 공간을 자연스럽게 채운다.
  - `요청`, `준비 중`, `준비 완료`, `픽업 완료`, `요청 취소` 상태에서 라벨·색상 구분이 유지된다.
  - 헤더의 인보이스 입력, 수정 잠김 안내, 준비 완료·픽업·취소 동작은 겹치거나 줄바꿈이 깨지지 않는다.
  - 목록, 준비 작업, 이력, 모달의 상태 pill 크기는 기존대로 유지한다.
- 브라우저 확인 시나리오: 데스크톱 `?tab=shipping&shippingView=requestDetail&shippingRequestId=<준비 중 요청>`를 열어 상태 영역이 우측 헤더 공간과 균형을 이루는지 확인한다 → 각 상태의 요청을 열어 라벨·색상·헤더 줄바꿈을 비교한다 → 인보이스 저장, 준비 완료/취소, 픽업 완료 버튼과 함께 표시될 때 겹침이 없는지 확인한다 → 출하 목록·준비 작업·이력·모달에서 기존 상태 pill을 확인한다.
- 우선순위: 중간

### 4. 출하 상세 이력의 완제품 SN·인보이스 번호 입력 카드를 같은 배치로 통일

- 화면/영역: 데스크톱 출하 > 출하 상세 이력(`shippingView=historyWork`) 헤더 우측의 `완제품 SN`과 `인보이스 번호`.
- 증상: 완제품 SN은 별도 요약 카드이고 인보이스 번호는 저장 버튼을 포함한 편집 카드라, 두 식별번호가 같은 선상에 정렬되지 않고 높이·내부 여백·정보 시작점이 다르게 보인다.
- 사용자 불편: 함께 확인하는 핵심 식별번호 두 개가 서로 다른 배치 문법을 사용해, 시선이 한 줄로 흐르지 않고 정렬이 불편하다.
- 확정 정책:
  - 완제품 SN과 인보이스 번호는 현재 인보이스 번호 편집 카드의 배치 문법을 기준으로 통일한다.
  - 두 카드는 같은 최소 높이, 라벨 위치, 값 시작선, 외곽선·내부 여백을 사용해 같은 선상에 놓인다.
  - 완제품 SN은 읽기 전용이며, 인보이스 번호의 입력·저장·유효성 정책은 변경하지 않는다.
- 구현 방향: `ViewHeader`의 우측 flex 영역에서 `shipping-history-serial-summary`와 `InvoiceNumberEditor`가 같은 basis·grow·최소 높이와 카드 shell을 쓰도록 조정한다. 필요하면 읽기 전용 식별번호 카드 전용 표현을 만들되, 인보이스 번호 편집기의 저장 로직·오류 안내는 재사용하거나 그대로 유지한다.
- 수용 기준:
  - 픽업 완료 이력에서 완제품 SN과 인보이스 번호 카드의 상단·하단·라벨·값 기준선이 정렬된다.
  - 완제품 SN 값이 길어도 잘림 처리와 전체 값 확인 방식은 유지되고, 인보이스 번호 저장 버튼은 카드 안에서 기존대로 동작한다.
  - 완제품 SN이 없는 이력에서는 인보이스 번호 카드가 기존처럼 자연스럽게 남은 폭을 사용한다.
  - 다른 출하 헤더와 모바일의 인보이스 입력·SN 표시는 의도치 않게 바뀌지 않는다.
- 브라우저 확인 시나리오: 데스크톱 `?tab=shipping&shippingView=historyWork&shippingHistoryStatus=PICKED_UP&shippingRequestId=<픽업 완료 요청>`를 열어 완제품 SN과 인보이스 번호가 같은 선상·같은 카드 높이인지 확인한다 → 긴 SN 값에서 truncate·전체 값 title을 확인한다 → 인보이스 번호를 수정·저장해 저장 버튼, 오류 안내, 이력 갱신이 유지되는지 확인한다 → SN이 없는 이력, 요청 상세·준비 작업·모바일 화면을 비교한다.
- 우선순위: 중간

### 7. 출하 요청 작성 1·2단계 품목 목록의 스크롤바를 카드 바깥 레일로 통일

- 화면/영역: 데스크톱 출하 > 출하 요청 작성(`shippingView=requestWork`) > 1단계 `기준 PF 선택` 목록 및 2단계 `BOM 구성 조정`의 PA 구성품·PF 구성품 목록.
- 증상: 기준 PF와 PA·PF 구성품 목록의 세로 스크롤바가 각 카드 내부 우측에 표시된다.
- 사용자 불편: 긴 품목명·수량·제외 조작이 있는 목록에서 마지막 열과 스크롤 레일이 같은 카드 내부 공간을 사용해 읽기·조작 여유가 적다.
- 확정 정책:
  - 데스크톱에서 1단계 기준 PF, 2단계 PA 구성품, 2단계 PF 구성품 목록의 세로 스크롤바만 각 카드 오른쪽 바깥 레일로 이동한다.
  - `_attic/docs/EXTERNAL_SCROLLBAR_RAIL_GUIDE.md`의 shell·viewport·고정 frame·모서리 마스크 구조를 그대로 따른다.
  - 품목 행, 검색, 수량, `제외` 조작, 기존 카드 크기·테두리·곡률·열 너비·행 높이와 step 이동 동작은 바꾸지 않는다.
  - 모바일의 내부 스크롤 위치와 레이아웃은 유지한다.
- 구현 방향: 각 실제 overflow viewport를 guide 구조로 감싸고, 데스크톱에서만 viewport 우측을 얇은 레일 너비만큼 확장한다. sticky 또는 목록 헤더·검색과 행은 실제 viewport 안에 유지하며, 고정 frame·코너 마스크는 기존 카드 배경 토큰을 사용한다. PA/PF 두 목록은 같은 레일 폭·프레임 규칙을 공유한다.
- 수용 기준:
  - 1920px 데스크톱에서 세 목록의 스크롤바가 각 카드 테두리 바깥에 동일한 폭으로 표시된다.
  - 긴 품목명, 수량, `제외` 버튼과 목록의 마지막 행이 레일에 가려지지 않는다.
  - 상단·중간·하단 스크롤 위치에서 카드 네 모서리와 테두리가 유지되며, 하단이 각져 보이지 않는다.
  - PF 선택, PA/PF 라인 추가·제외·수량 변경, 동반 출하품·다음 단계 이동은 기존대로 동작한다.
  - 모바일과 3단계 이후 요청 작성 화면은 변경하지 않는다.
- 브라우저 확인 시나리오: 데스크톱 `?tab=shipping&shippingView=requestWork&shippingStep=1`에서 PF 목록을 상단·중간·하단까지 스크롤한다 → `shippingStep=2`에서 PA와 PF 구성품을 각각 스크롤해 바깥 레일·마지막 열·모서리를 확인한다 → 긴 품목명, 수량 변경, 제외·추가·다음 버튼을 확인한다 → 모바일 폭과 3단계 이상 화면을 비교한다.
- 우선순위: 중간

### 8. 출하 요청 상세·이력 화면의 스크롤 레일을 보이도록 추가하고 바깥으로 분리

- 화면/영역: 데스크톱 출하 > 요청 상세(`requestDetail`), 출하 이력 목록(`historyList`), 출하 상세 이력(`historyWork`)의 화면 세로 스크롤.
- 증상: 세 화면의 실제 스크롤 루트는 `scrollbar-hide`를 사용한다. 특히 출하 상세 이력은 내용이 스크롤되지만 사용자가 조작할 수 있는 세로 스크롤 레일이 보이지 않는다.
- 사용자 불편: 긴 요청 상세·이력 내용을 보고 있는지와 현재 위치를 알기 어렵고, 화면마다 스크롤바 표시 문법이 달라 탐색 예측성이 떨어진다.
- 확정 정책:
  - 데스크톱 출하 요청 상세·이력 목록·상세 이력에는 보이는 세로 스크롤 레일을 제공하고, 레일은 콘텐츠 표면/카드 우측 바깥에 둔다.
  - `_attic/docs/EXTERNAL_SCROLLBAR_RAIL_GUIDE.md`의 구조를 따르되, 기존 layout-only 화면에는 새 카드·배경·테두리·여백을 추가하지 않는다.
  - 스크롤이 없는 짧은 콘텐츠에는 불필요한 레일을 강제하지 않으며, 스크롤이 생겨도 콘텐츠 폭이 흔들리지 않게 gutter를 고정한다.
  - 요청 작성 내부 목록(7번)과 다른 출하 화면의 독립 목록은 이 항목에서 변경하지 않는다.
- 구현 방향: 각 화면의 실제 세로 overflow 소유자를 확인해 `scrollbar-hide`를 제거하고, guide의 relative shell과 데스크톱 전용 확장 viewport를 적용한다. 테두리가 있는 표면은 고정 frame·마스크로 기존 곡률을 복원하고, layout-only 표면은 기존 상위 레이아웃 경계를 유지한 채 레일만 바깥으로 뺀다. 이력 목록의 내부 body와 루트 중 이중 스크롤이 발생하지 않도록 하나의 실효 viewport만 선택한다.
- 수용 기준:
  - 데스크톱 요청 상세·이력 목록·상세 이력에서 콘텐츠가 넘칠 때 우측의 세로 레일이 보인다.
  - 상세 이력은 현재처럼 마우스휠·터치패드로 스크롤될 뿐 아니라 레일로도 현재 위치를 알 수 있다.
  - 레일은 기존 내용·카드의 우측 테두리 안쪽 마지막 열을 가리지 않고 바깥에 위치한다.
  - 스크롤 상단·중간·하단에서 기존 콘텐츠 폭·곡률·테두리·버튼·이력 행 선택·인보이스 저장 동작이 유지된다.
  - 짧은 콘텐츠, 모바일과 요청 작성·준비 작업 화면은 의도치 않게 달라지지 않는다.
- 브라우저 확인 시나리오: 데스크톱에서 `requestDetail`의 긴 요청, `historyList`의 여러 달·행, `historyWork`의 긴 상세 이력을 각각 연다 → 휠과 레일 드래그로 상단·중간·하단을 이동하며 레일 위치·콘텐츠 폭·모서리를 확인한다 → 이력 행 선택, 상세 이력의 인보이스 저장·픽업 취소 등 기존 조작을 확인한다 → 내용이 짧은 요청과 모바일 폭, 요청 작성·준비 작업 화면을 비교한다.
- 우선순위: 중간

### 9. 출하 요청 상세·이력 목록의 외곽 작업 표면을 상세 이력과 통일

- 화면/영역: 데스크톱 출하 > 출하 요청 목록(`requestList`, 기준), 출하 요청 상세(`requestDetail`, 대상), 출하 이력 목록(`historyList`, 대상), 출하 상세 이력(`historyWork`, 기준)의 전체 작업영역.
- 증상: 요청 목록과 상세 이력은 하위 컴포넌트가 흰색의 둥근 테두리 작업 표면 안에 배치되지만, 요청 상세·이력 목록은 layout-only 루트를 사용해 같은 외곽 표면이 빠져 있다.
- 사용자 불편: 같은 출하 메뉴에서 화면마다 콘텐츠의 최상위 경계·배경·여백 계층이 달라, 하위 카드와 목록이 어느 작업영역에 속하는지 시각적으로 일관되지 않다.
- 확정 정책:
  - 현재 요청 목록·상세 이력의 흰색 둥근 외곽 프레임을 데스크톱 출하 작업영역의 기준으로 사용한다.
  - 요청 상세와 이력 목록만 같은 외곽 작업 표면 안에 현재 컴포넌트를 배치한다.
  - 요청 목록·상세 이력의 기존 외곽 표면과 각 화면의 데이터·행·버튼·상태·스크롤 동작은 변경하지 않는다.
  - 8번의 바깥 스크롤 레일은 새 외곽 표면의 우측 바깥에서 동작하도록 함께 정렬하며, 이 항목만으로 별도 내부 카드·중복 padding을 추가하지 않는다.
- 구현 방향: `DesktopShippingView.tsx`의 루트 표면 클래스 조건에서 `requestDetail`·`historyList`가 layout-only가 되는 이유와 필요한 여백을 확인한다. 기존 요청 목록·상세 이력의 surface 배경·테두리·곡률·padding 문법을 재사용해 두 대상 화면에만 적용하고, 8번의 실제 viewport·frame 구조와 충돌하지 않도록 하나의 외곽 경계만 유지한다.
- 수용 기준:
  - 데스크톱 요청 상세·이력 목록은 요청 목록·상세 이력과 동일한 흰색 배경, 둥근 테두리, 바깥 여백 안에 표시된다.
  - 대상 화면의 헤더·검색·이력 행·PA/PF 카드·인보이스 입력·상태/행 선택 조작이 겹치거나 잘리지 않는다.
  - 스크롤이 생겼을 때 레일은 외곽 표면의 마지막 열을 가리지 않고, 표면의 곡률과 테두리가 상단·중간·하단에서 유지된다.
  - 요청 목록·상세 이력의 현재 디자인과 모바일, 요청 작성·준비 작업 화면은 변하지 않는다.
- 브라우저 확인 시나리오: 데스크톱에서 `shippingView=requestList`, `requestDetail`, `historyList`, `historyWork`를 각각 연다 → 요청 목록·상세 이력을 기준으로 요청 상세·이력 목록의 최상위 흰색 표면, 모서리, padding을 비교한다 → 긴 요청 상세와 여러 이력 행에서 스크롤 상단·중간·하단을 확인한다 → 이력 행 선택, 요청 상세의 인보이스 저장·상태 조작을 확인한다 → 모바일 폭과 요청 작성·준비 작업 화면의 회귀가 없는지 확인한다.
- 우선순위: 중간

### 14. [완료] 출하 요청 목록 카드에 출하 수량 표시

- 상태: 구현 완료 (2026-08-21). `RequestRow` 메타데이터에 기존 `request_quantity`를 사용한 `출하 수량: N대`를 추가했고, 세 진행 상태 회귀 테스트 129개와 실제 브라우저의 20대·10대 요청 카드 표시를 확인했다.

- 화면/영역: 데스크톱 출하 관리 > 출하 요청 목록(`shippingView=requestList`)의 `출하 요청`, `준비 중`, `준비 완료` 열에 표시되는 요청 카드.
- 증상: 요청 카드에는 품명·품목코드·상태·요청 일시·요청자·인보이스 번호가 표시되지만, 요청마다 이미 저장된 출하 수량은 카드에서 확인할 수 없다. 카드 우측 정보 영역에는 수량을 표시할 여유가 남아 있다.
- 사용자 불편: 동일 품목의 여러 요청을 목록에서 비교할 때 카드마다 몇 대를 출하하는 요청인지 상세 화면을 열기 전에는 판단할 수 없다.
- 확정 정책:
  - 요청 목록의 모든 상태 열에서 각 카드에 `출하 수량: N대`를 표시한다.
  - 수량 기준은 요청 응답의 기존 `request_quantity`이며, BOM 구성품 수량·동반 출하품 합계·시리얼번호 개수를 별도로 계산하지 않는다.
  - 출하 수량은 요청 일시·요청자와 같은 메타데이터 위계로 카드의 남는 우측 정보 영역에 배치한다.
  - 카드 높이·상태 배지·품명·품목코드·요청 일시·요청자·인보이스 번호·선택 및 상세 진입 동작은 유지한다.
  - 이번 범위는 데스크톱 요청 목록 카드로 한정하며, 요청 상세·준비 작업·출하 이력·모바일의 기존 수량 표시는 변경하지 않는다.
- 구현 방향: `RequestRow`의 기존 메타데이터 flex 행에 `request.request_quantity`를 사용하는 명시적 수량 텍스트를 추가한다. 작은 화면 폭이나 긴 날짜·요청자에서도 겹치지 않도록 현행 `flex-wrap`을 유지하고, 새 API 호출이나 서버 스키마 변경 없이 기존 목록 응답을 사용한다. 기존 요청 카드 메타데이터 테스트에 1대 및 여러 대 요청의 표시를 먼저 추가해 실패를 확인한 뒤 최소 JSX 변경으로 통과시킨다.
- 수용 기준:
  - 요청 목록의 `출하 요청`, `준비 중`, `준비 완료` 카드마다 실제 `request_quantity`와 일치하는 `출하 수량: N대`가 보인다.
  - 1대는 `출하 수량: 1대`, 여러 대는 해당 정수 값으로 표시되며 다른 수량 합계로 바뀌지 않는다.
  - 긴 품명·품목코드·요청자·인보이스 번호가 있어도 수량과 상태 배지가 겹치거나 잘리지 않고, 메타데이터가 필요하면 자연스럽게 줄바꿈된다.
  - 카드 높이와 세 열 레이아웃, 요청 카드 선택·상세 진입, 기존 상태별 색상과 정보는 유지된다.
  - 요청 상세·준비 작업·출하 이력·모바일의 기존 수량 표기와 동작은 회귀하지 않는다.
- 브라우저 확인 시나리오: 데스크톱 `?tab=shipping&shippingView=requestList`를 열어 `출하 요청`, `준비 중`, `준비 완료` 열에서 1대 요청과 여러 대 요청의 카드 수량을 확인한다 → 각 카드를 열어 상세의 출하 수량과 목록 값이 같은지 대조한다 → 긴 품명·요청자·인보이스가 있는 카드에서 줄바꿈·상태 배지·카드 높이를 확인한다 → 카드 선택과 상세 진입을 확인하고 모바일 폭 및 출하 이력 화면에 의도치 않은 변화가 없는지 비교한다.
- 우선순위: 중간

### 15. [완료] 출하 요청·이력 목록 카드를 폭에 맞는 정보 블록형 디자인으로 통일

- 상태: 구현 완료 (2026-08-21). 요청 목록은 빈 상태 카드와 같은 136px 높이의 2열 정보 블록, 출하 이력은 112px 높이의 4열 정보 블록으로 분리했다. 준비 목록 등 기본 카드 사용처는 기존 136px 렌더를 보존했고, 출하 뷰 테스트 132개·엄격 린트 및 라이트/다크 브라우저 표시를 확인했다.

- 화면/영역: 데스크톱 출하 > 출하 관리 요청 목록(`shippingView=requestList`)의 3열 요청 카드와 출하 이력 목록(`shippingView=historyList`)의 연·월 아래 넓은 완료/취소 카드.
- 증상: 두 화면은 같은 `RequestRow`를 사용해 품명·품목코드·상태·일시·요청자·출하 수량·인보이스를 작은 텍스트로 연속 나열한다. 좁은 요청 카드에서는 정보가 한 줄에 몰리고, 넓은 이력 카드에서는 정보가 좌측에만 모여 우측 빈 공간과 불필요한 세로 높이가 남는다.
- 사용자 불편: 핵심 품목과 업무 판단 정보의 위계가 약해 카드를 훑을 때 품명, 상태, 수량, 인보이스를 다시 찾아 읽어야 하며, 요청과 이력이 같은 거래를 보여 주면서도 각 화면 폭을 제대로 활용하지 못해 완성도가 낮아 보인다.
- 확정 정책:
  - 두 화면은 같은 시각 문법을 사용하되, `요청 보드`와 `넓은 이력` 두 레이아웃 변형으로 각 카드 폭에 맞게 재배치한다.
  - 상단은 품명을 가장 강한 위계로 두고 품목코드를 그 아래 보조 정보로 표시하며, 상태 배지는 우측 상단에 고정한다. 긴 품명은 상태 배지를 밀지 않고 요청 보드에서는 최대 두 줄, 넓은 이력에서는 한 줄 말줄임으로 처리한다.
  - 하단은 일시·요청자·출하 수량·인보이스를 `라벨 + 값` 정보 블록으로 분리한다. 요청 보드는 2열로 자연스럽게 감싸고, 이력 카드는 넓은 폭을 사용하는 4열 한 줄로 정렬한다.
  - 최종 PF와 기준 PF가 다를 때 기준 품목명은 일시 문자열 뒤에 붙이지 않고 품목코드 주변의 별도 보조 정보로 분리한다.
  - 인보이스 미입력은 값만 기존 경고색을 사용하고, 다른 정보까지 경고 카드·색상 pill로 만들지 않는다. 장식은 얇은 경계, 중성 토큰 표면, 상태/선택 강조와 가벼운 hover·press 피드백으로 제한한다.
  - 넓은 이력 카드는 4열 정보 블록에 맞춰 현재의 불필요한 세로 여백을 줄이고, 요청 보드의 세 열은 카드 높이를 서로 일관되게 유지한다.
  - 적용 범위는 사용자가 지정한 출하 요청 목록과 출하 이력 목록으로 한정한다. 같은 `RequestRow`를 사용하는 준비 목록·준비 상세 선택 목록·상세 이력 보조 목록과 모바일은 기존 밀도·선택 동작을 유지한다.
- 구현 방향: `RequestRow`에 데이터나 클릭 로직을 바꾸지 않는 명시적 레이아웃 변형을 추가하고, `RequestListEntry`와 `HistoryListEntry`에서 각각 요청 보드/넓은 이력 변형을 전달한다. 공통 상단 identity 영역과 라벨/값 메타데이터 모델은 한 번만 구성하되, 요청 보드는 2열 grid, 이력은 4열 grid와 더 작은 세로 padding을 사용한다. `LEGACY_COLORS`/기존 tint, `StatusBadge`, `SummaryCode`, 12px 이상 메타 타이포, semantic button과 focus-visible 상태를 유지하며 준비 관련 호출부의 기본 렌더는 변경하지 않는다.
- 수용 기준:
  - 출하 요청 카드에서 품명·코드·상태와 네 메타정보가 두 구역으로 명확히 나뉘고, 일시·요청자·수량·인보이스가 2열 정보 블록으로 빠르게 읽힌다.
  - 출하 이력 카드에서는 네 메타정보가 카드 폭을 고르게 사용하는 한 줄 4열로 정렬되고, 현재처럼 우측이 비거나 카드가 필요 이상으로 높게 보이지 않는다.
  - 요청과 이력에서 같은 필드명·값 위계·간격·상태 배지 문법을 사용하며, 완료·취소·준비 상태의 의미색과 인보이스 미입력 경고가 유지된다.

  - 마우스 hover·press, 키보드 focus-visible, 카드 클릭 후 상세 진입, 연·월 폴더 열기/접기와 선택 상태가 유지된다.
  - 준비 목록·준비 상세·상세 이력 보조 목록, 모바일과 동결 영역은 의도치 않게 바뀌지 않는다.
- 브라우저 확인 시나리오: 1918×910 데스크톱에서 `?tab=shipping&shippingView=requestList`를 열어 세 상태 열의 짧은/긴 품명, 1대/여러 대, 인보이스 있음/없음 카드를 비교한다 → hover·키보드 focus·클릭 상세 진입을 확인한다 → `?tab=shipping&shippingView=historyList&shippingHistoryStatus=PICKED_UP`에서 연·월을 펼쳐 긴 품명의 넓은 카드가 4열 정보를 사용하고 세로 여백이 줄었는지 확인한다 → 요청 취소 이력과 검색 결과도 비교한다 → 준비 목록·준비 상세·상세 이력 보조 목록 및 모바일 폭에서 기존 카드가 유지되는지 확인한다 → 라이트·다크 테마에서 토큰 대비를 확인한다.

## 관리자

### 5. BOM 관리 세 목록의 데스크톱 세로 스크롤바를 카드 바깥 레일로 통일

- 화면/영역: 데스크톱 관리자 > BOM 관리 > `상위 품목 선택`, `하위 품목 추가`, `현재 구성` 목록의 세로 스크롤바.
- 증상: 세 목록의 스크롤바가 각 카드 내부 우측에 표시된다. 사용자는 세 카드의 스크롤바를 기존 입출고 품목 선택 표와 같은 방식으로 카드 바깥 레일에 배치하길 요청했다.
- 사용자 불편: 표의 마지막 열·추가/삭제 조작점과 스크롤 레일이 같은 카드 안에 있어, 넓이가 좁은 세 열 레이아웃에서 마지막 열을 읽거나 조작할 때 여유가 적다.
- 확정 정책:
  - 데스크톱에서 상위 품목·하위 품목·현재 구성 세 목록의 세로 스크롤바만 각각 카드 오른쪽 바깥 레일로 이동한다.
  - 적용 방식은 `_attic/docs/EXTERNAL_SCROLLBAR_RAIL_GUIDE.md`의 shell·viewport·고정 frame·모서리 마스크 구조를 따른다.
  - 카드의 기존 크기·배경·테두리·둥근 모서리·표 열 너비·행 높이·sticky 헤더·가로 스크롤과 목록 조작은 유지한다.
  - 스크롤이 생기는 경우 `현재 구성`에도 같은 레일 규칙을 적용한다.
  - 모바일에서는 기존 내부 스크롤 위치와 동작을 유지한다.
- 구현 방향: 세 컴포넌트의 `overflow-y-auto` 요소를 guide의 실제 viewport로 옮기고, 각 카드가 차지하던 원래 크기에 relative shell과 pointer-events-none 고정 frame을 둔다. 데스크톱에서만 viewport를 얇은 레일 너비만큼 오른쪽으로 확장하고 `scrollbar-gutter: stable`을 적용한다. 표 본문·열 템플릿·sticky 헤더 JSX는 viewport의 자손으로 유지하며, frame과 코너 마스크는 실제 주변 배경 토큰을 사용한다.
- 수용 기준:
  - 1920px 데스크톱 BOM 관리에서 세 목록의 세로 스크롤바가 각 카드의 우측 테두리 바깥 레일에 표시된다.
  - 스크롤바가 없어도/생겨도 표 열 너비, 마지막 `추가`·`삭제` 열, 수량 값, 행 높이가 흔들리지 않는다.
  - 스크롤 상단·중간·하단에서 네 모서리와 테두리가 계속 둥글고, 하단이 각져 보이거나 마지막 행이 잘리지 않는다.
  - 상위 품목 선택, 하위 품목 추가·수량 입력·추가/취소, 현재 구성 수량 편집·삭제, 표의 sticky 헤더·가로 스크롤이 유지된다.
  - 모바일과 다른 관리자 목록의 스크롤바는 바뀌지 않는다.
- 브라우저 확인 시나리오: 데스크톱 `?tab=admin`에서 BOM 관리를 열어 세 목록 각각을 스크롤한다 → 상단·중간·하단에서 레일 위치와 테두리·모서리를 확인한다 → 마지막 열의 추가/삭제 버튼과 수량 편집을 실행해 레일에 가려지지 않는지 확인한다 → 목록을 필터링해 스크롤 유무가 바뀔 때 열 너비가 고정되는지 확인한다 → 현재 구성이 길어진 경우에도 같은 레일이 생기는지 확인한다 → 모바일 폭과 다른 관리자 탭을 비교한다.
- 우선순위: 중간

## 주간보고

### 6. 생산 현황 카드에 F705-02 생산일지 다운로드 버튼 하나 추가

- 화면/영역: 데스크톱 관리자 > 내보내기의 기존 `F705-02 생산일지 다운로드`와 데스크톱 주간보고 > 생산 현황 카드 우측 빈 영역.
- 증상: F705-02 연간 생산일지는 관리자 내보내기에서만 다운로드할 수 있고, 주간보고의 생산 현황 카드에는 같은 기능으로 바로 갈 수 있는 진입점이 없다.
- 사용자 불편: 주간 생산 실적을 확인하는 흐름에서 연간 생산일지를 내려받으려면 관리자 내보내기까지 이동해야 한다.
- 확정 정책:
  - F705-02 생산일지 다운로드는 관리자 내보내기에 계속 유지하고, 주간보고 생산 현황 카드 우측에 같은 기능의 버튼 하나를 추가한다.
  - 주간보고 버튼은 현재 선택된 보고 주의 시작일(`weekMon`) 연도를 사용해 해당 연도의 F705-02 파일을 다운로드한다. 연도 입력·추가 필터·보조 설명은 넣지 않는다.
  - 기존 서버의 관리자 PIN 권한 검증과 파일명·생성 로직은 변경하지 않는다.
  - 주간보고 동결 범위의 사용자 승인 예외는 이 버튼 하나의 추가로만 한정한다. `DesktopWeeklyReportView.tsx`와 `_weekly_sections/`의 다른 레이아웃·텍스트·데이터 계산·상호작용은 수정하지 않는다.
- 구현 방향: 기존 `adminApi.downloadF705ProductionLog(year)`와 Blob 다운로드 방식을 재사용해, `DesktopWeeklyReportView.tsx`의 생산 현황 카드 헤더 우측에 최소한의 다운로드 버튼만 둔다. 현재 선택 주의 시작 연도를 전달하고, 다운로드 중 비활성/진행 라벨 및 실패 메시지는 기존 내보내기와 같은 사용자 피드백 수준으로 처리한다. 관리자 내보내기 구현과 서버 라우터는 변경하지 않는다.
- 수용 기준:
  - 관리자 내보내기의 `F705-02 생산일지 다운로드` 버튼은 기존 위치·동작 그대로 유지된다.
  - 주간보고 생산 현황 카드 우측에 F705-02 다운로드 버튼 하나만 추가된다.
  - 예를 들어 2026년 주간을 보고 있을 때 버튼은 `downloadF705ProductionLog(2026)`을 호출하고 `F705-02 (R01) 2026 생산일지.xlsx` 다운로드를 시작한다.
  - 다운로드 중 중복 클릭을 막고, 실패 시 기존 수준의 오류 피드백을 제공한다.
  - 생산 행렬, KPI, 공정별 변화, 품목 상세, 주 선택기와 주간보고의 다른 동결된 UI·동작은 변경되지 않는다.
  - 관리자 PIN 권한 검증은 기존과 동일하게 유지된다.
- 브라우저 확인 시나리오: 관리자에서 내보내기 탭을 열어 기존 F705-02 버튼으로 현재 연도 파일이 내려받아지는지 확인한다 → 데스크톱 주간보고에서 2026년 주를 선택해 생산 현황 카드 우측의 단일 버튼을 누른다 → 같은 연도의 F705-02 파일명·다운로드 시작·진행 중 중복 클릭 방지를 확인한다 → 다른 연도의 주를 선택해 연도가 함께 바뀌는지 확인한다 → 권한 없는 세션의 기존 서버 응답, 주간보고의 KPI·표·공정 카드·품목 상세 및 모바일 화면이 변하지 않는지 확인한다.
